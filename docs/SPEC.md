# Steadhand — Product & Technical Spec

**Status:** Draft v0.3 (2026-11-21)
**Owner:** MAKR Holdings LLC
**Repo:** `makr-holdings/steadhand`: the free plugin, private during development, made public at the WordPress.org launch. Pro (M5) will be a separate add-on plugin in its own private repo; see §9.1.

> Display name: **Steadhand – Secure AI Agent Access for WordPress**
> Slug / text domain: `steadhand` · PHP namespace: `Steadhand\` · Prefix: `steadhand_` / `STEADHAND_`

---

## 1. What Steadhand is

Steadhand lets AI agents (Claude, ChatGPT, Cursor, any MCP client) work on a WordPress site **safely**: each agent gets only the permissions it needs, known-dangerous writes are blocked or fixed before they land, and every action is logged and can be undone.

It is **not** an AI plugin. Steadhand never calls an LLM, stores no AI provider keys, and adds no chatbot or content generator. It is an access and governance layer. The AI lives in the client.

### Why it exists
- Existing WordPress MCP plugins tend to give an agent a single, never-expiring token with **admin** rights. One leaked token means full site compromise.
- Agents keep making the same site-breaking mistakes: writing JSON into PHP-serialized options, using color slugs that break block validation, overwriting widget and sidebar options. Today the only defense is instructions in a prompt file. Steadhand enforces them in code.
- Site owners can't currently see which agent did what, or easily roll it back.

### Positioning
"The safe one." Built by a security consultancy and used on its own sites first. Least privilege, guardrails and an audit trail are the product, not add-ons.

## 2. Goals and non-goals

**Goals (v1)**
1. Expose a focused, well-described set of WordPress tools over MCP, built on core's Abilities API and the official MCP Adapter.
2. Least privilege by default: a dedicated agent user and role, per-tool-group capabilities, nothing admin-level unless deliberately granted.
3. Enforce guardrails against known site-breaking writes.
4. Log every agent action with enough detail to audit it and undo it.
5. Pass WordPress.org review and Plugin Check on the first submission.

**Non-goals (v1)**
- Generating content, images or embeddings, or calling any AI provider.
- Installing, activating or updating plugins or themes; editing theme or plugin files; running PHP or SQL; managing users. These may never ship, and if they do, it will be Pro-only behind approvals.
- Replacing a full security plugin (firewall, malware scanning, login hardening).
- WooCommerce-specific tools (possible later add-on).

## 3. Architecture

```
MCP client (Claude, etc.)
   │  HTTPS + WordPress Application Password (Basic auth)
   ▼
MCP Adapter (official plugin): transport, protocol, errors
   │  custom server "steadhand" (explicit tool list)
   ▼
Steadhand
   ├─ Transport gate: the request user must hold `steadhand_connect`
   ├─ Abilities (steadhand/*): schema-validated input → permission check → guardrails → log reservation → execute → log completion (writes); permission check → execute → log (reads)
   ├─ Guardrail engine: rules evaluated before any write
   ├─ Change log + snapshots: audit trail and undo
   └─ Admin UI: agents, permissions, guardrails, log
```

### 3.1 Dependencies
- **WordPress 6.9+** (Abilities API in core). Target: tested against the current release (7.1.x).
- **MCP Adapter, required as a separate plugin** (decided, D1). Declared with the `Requires Plugins:` header so WordPress installs and enforces it. Not bundled, which avoids version conflicts with other plugins that bundle it. Its confirmed WordPress.org slug is `mcp-adapter` (0.7.2 at time of writing).
- **PHP 8.1+** (decided, D2).

### 3.2 MCP server
- Steadhand registers its **own** server on `mcp_adapter_init` using `$adapter->create_server(...)`, with an **explicit tool list**. Agents see each tool directly in `tools/list` with its full schema, with no discover/execute indirection through the default server.
- Server ID `steadhand`, REST namespace `steadhand`, route `mcp`, so the endpoint is `/wp-json/steadhand/mcp`.
- The **transport permission callback** checks the request user's own resolved capabilities directly (`WP_User::$allcaps`, role defaults merged with user-level overrides) for `steadhand_connect`. It does not call `current_user_can()`: on multisite that returns true for super admins for any capability, and `user_has_cap` filters from other plugins could grant Steadhand capabilities. Steadhand access must only ever come from a deliberate grant. Every Steadhand capability check works this way. Admins do *not* get this capability automatically. Only users deliberately set up as agents connect. The request user must also be a dedicated agent, meaning `steadhand_agent` is its only role (`Agents::is_agent()`, D14). Trade-off: a `user_has_cap` filter that revokes capabilities (for example a security plugin's lockdown mode) is not honoured by this check, so to cut off an agent, revoke its capability or its application password instead.
- The lockdown (§4.1) is registered by `Plugin::boot()` before its requirements check, so it holds when the MCP Adapter or the Abilities API is missing.
- Steadhand's abilities are **not** marked `meta.public = true`, so they don't leak into the adapter's default server or other consumers. They are exposed only through the Steadhand server. Abilities also set `meta.mcp.public = false` and `show_in_rest = false` explicitly.

### 3.3 Abilities
- Category `steadhand`, registered on `wp_abilities_api_categories_init`. Abilities are registered on `wp_abilities_api_init`. (If the category isn't registered, the ability fails *silently* when `WP_DEBUG` is off. Add a self-check in the admin UI.)
- Naming: `steadhand/<verb>-<noun>`, e.g. `steadhand/get-post`, `steadhand/update-post`.
- Each ability declares: `label`, a **description written for an LLM** (what it does, when to use it, what it will refuse), `input_schema`, `output_schema`, `permission_callback`, `execute_callback`, and MCP annotations (`readonly`, `destructive`, `idempotent`).
- Every `execute_callback` runs through one shared pipeline. A read runs **validate → authorize → execute → log**. A write runs **validate → authorize → guardrails → log reservation → snapshot → execute → log completion** (§7). A write whose log row cannot be reserved is not performed. No ability writes to the database outside that pipeline.

## 4. Identity, authentication, permissions

### 4.1 Agent users
- Admins create **agent users** from Steadhand's admin screen. Each gets the custom role `steadhand_agent`, which has *no* native WordPress capabilities beyond `read`, plus Steadhand capabilities.
- Agents authenticate with **WordPress core Application Passwords**: no custom token scheme, revocable per password, and stored hashed by core.
- The **application password's name is the agent label** ("Claude Desktop – Rick", "Ops agent", and so on). It appears in the log, so you can tell agents apart even under the same user.
- **Dedicated agents:** only a user whose sole role is `steadhand_agent` is an agent (D14). A user who also holds another role (a *mixed-role* user) is not an agent, and it cannot connect to Steadhand.
- **Lockdown (M1):** Steadhand refuses agent credentials everywhere except the Steadhand endpoint, by four mechanisms (`includes/Lockdown.php`, which states each rule in a table in its class docblock). The rules are registered before the requirements check (§3.2). The table below gives what each rule does to a dedicated agent and to a mixed-role user:
  - *Password sign-in* (`authenticate`): a dedicated agent's password sign-in is refused, whether through wp-login.php, `wp_signon()` or XML-RPC. A mixed-role user's Application Password sign-in is refused too (it works nowhere, as the identity rule says), but its account-password sign-in is not affected.
  - *Identity* (`determine_current_user`): a dedicated agent is the current user only when it authenticated with its own Application Password, on a REST request whose route is the Steadhand endpoint. Anywhere else it resolves to no user, so the request is treated as not logged in. A mixed-role user whose request carries its own Application Password resolves to no user everywhere. Cookie sessions of a mixed-role user are not affected.
  - *REST routes* (`rest_pre_dispatch`, and a second check on `rest_request_before_callbacks`): a dedicated agent may reach only the Steadhand endpoint. On any other route, its Application Password makes the request anonymous (identity rule above), so core answers as it would to a logged-out visitor. If the request still carries the agent as its user, every other route gets 403, including `/batch/v1` sub-requests and the MCP Adapter's default server. A mixed-role user whose request carries an Application Password gets 403 on every route except the Steadhand endpoint, where the transport gate refuses it. The second check runs for every matched request, after all `rest_pre_dispatch` filters, so a later filter cannot lift the first. A callback added at the same priority on `rest_request_before_callbacks` after Steadhand boots can still undo the second check (see `docs/HOOKS.md`).
  - *wp-admin* (`admin_init`): a dedicated agent that reaches wp-admin, admin-ajax.php or admin-post.php gets 403. Mixed-role users are not affected, so a human administrator given the agent role keeps wp-admin.
  - *Limits:* the lockdown runs only while Steadhand is active and loadable. If Steadhand is deactivated, or cannot load (PHP older than 8.1, or a source checkout without its autoloader), agent users and their Application Passwords still exist and work as ordinary low-privilege WordPress accounts on core REST and wp-login until they are revoked. Uninstalling revokes them. To take a site out of service safely, revoke the agents' Application Passwords first, or uninstall rather than deactivate.
  - *Do not give the agent role to a person's account.* That account's Application Passwords stop working everywhere (see the mixed-role rule above).
- Optional IP allowlist per agent user: in Free, off by default (decided, D3).

### 4.2 Capabilities (tool groups)
Each tool belongs to a group. Each group is a capability the admin toggles per agent user:

| Capability | Tools | Default for a new agent |
|---|---|---|
| `steadhand_connect` | can reach the server at all | on |
| `steadhand_read` | site info, posts/pages (any status except trash), blocks, terms, menus, media lists, diagnostics, the agent's own change log | on |
| `steadhand_write_drafts` | create posts (always as `draft`); edit posts of any author while they are `draft`, `pending` or `auto-draft`, including their blocks; may set `draft` to `pending`; never publish, schedule or make private; never change the author | on |
| `steadhand_publish` | edit published, scheduled or private posts; set those statuses | **off** |
| `steadhand_media` | upload media, set featured image, edit alt/captions | off |
| `steadhand_menus` | edit navigation menus | off |
| `steadhand_trash` | move to trash and restore (never permanent delete) | off |
| `steadhand_settings` | read/write **allowlisted** options only (site title, tagline, and similar) | off |

Publishing a draft needs both `steadhand_write_drafts` (to edit the draft) and `steadhand_publish` (to set the live status). Editing a live post needs `steadhand_publish` only (`update-post` and `edit-blocks` also need `steadhand_read` to read the post they edit). Moving a live post back to draft needs `steadhand_publish`. `create-post` with any status other than `draft`, including `pending`, needs `steadhand_publish`.

`set-post-terms` needs `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` by the post's status, as `update-post` does. A taxonomy whose own assign capability is not core's default also needs that capability (D21).

User-level capabilities override the role defaults, and a user-level deny overrides a capability the role grants.

Each ability's `permission_callback` checks **both** the Steadhand capability **and** the native WordPress check for the specific object (e.g. `edit_post` for *this* post ID), carried out by a `map_meta_cap` filter. The `read_post` mapping applies while a Steadhand pipeline request is running, and `edit_post` and `publish_post` apply only during a write call (§14.1). The `steadhand_agent` role never holds WordPress's general editing capabilities (see §14.1). Defense in depth: neither check alone is enough.

**Exception: `create-post`.** `create-post` has no object yet, so there is no post for WordPress's object check (`edit_post`) to check. It is guarded by the Steadhand capabilities and the allowed post types only. This is an explicit exception to the two-layer rule.

**Capability guard.** `includes/CapabilityGuard.php` filters `user_has_cap` at priority `PHP_INT_MAX`, registered in `Plugin::boot()` before the requirements check. For every Steadhand capability (`Capabilities::all()`), the answer is the value stored for the user, read by `Capabilities::user_has()`. `Capabilities::NO_GRANT` (`steadhand_no_grant`) is in no user and is always false. So no `user_has_cap` filter can grant a Steadhand capability, and none can remove one. Other capabilities are not touched, so a filter may still change core's answers for an administrator. "The value stored for the user" means the user's capabilities as WordPress loaded them. Code that runs inside the site and rewrites those values is trusted, as the site's own administrator is.

## 5. Tool catalog (v1)

Read (`readonly: true`):
- `get-site-info`: name, URL, WordPress/PHP versions, active theme, Steadhand version, what this agent is allowed to do.
- `list-posts` / `get-post`: allowed post types only (`post` and `page` by default, extendable through the `steadhand_allowed_post_types` filter; fixed exclusions in §14.1), with filters (status, type, search, date), paged. Built in M1 as follows:
  - `list-posts` takes `status` as a set of `publish`, `future`, `draft`, `pending` and `private`. `trash`, `auto-draft`, `inherit` and `any` are refused. It also takes `search` (up to 200 characters), `after` and `before` (ISO 8601 date-times, read as instants, so a value without an offset is UTC; compared with the post date in the site's time zone, which also covers drafts whose GMT date is zero), `orderby` (`date`, `modified` or `title`), `order`, `page` (1 to 10000) and `per_page` (1 to 50, default 20). It returns `items`, `total`, `total_pages`, `page` and `per_page`. A page past the end is empty, not an error. An item's excerpt is plain text of about 55 words.
  - `get-post` returns the raw `post_content` as stored, with its excerpt, comment and ping status, menu order, page template, featured media ID and sticky flag. Neither tool returns post meta (meta comes later, behind an allowlist), the password, or anything about users beyond the author's display name. Trashed, missing and disallowed IDs get the same refusal text.
  - Content over 256 KB (`MAX_CONTENT_BYTES`) is cut on a UTF-8 boundary, with `truncated: true` and `content_bytes` giving the full size.
- `get-blocks`: the parsed block tree of a post. Each node has `path`, `name` (`null` for freeform HTML), `attrs` (always a JSON object), `inner_html` and `inner_blocks`. A path is a dot-separated index: `0` is the first block, `1.0` the first block inside the second. Indexes count the nodes at each level, and whitespace-only freeform nodes between blocks are not counted, so a path names the same block while the content is unchanged. Truncation only drops trailing nodes, so a kept node's path is the same with or without the limits. Later edit tools use the same walker and the same paths. Limits: 2000 nodes and 20 levels (beyond either, `truncated: true`), and at most 256 KB of `inner_html` and `attrs` together.
- `get-rendered`: the HTML the content produces through the front end's `the_content` filters, as a fragment. The site's own blocks and shortcodes run, so their output appears. It is not a full page, and it runs no theme template. While the post renders, Steadhand blocks every request made through the WordPress HTTP API, every oEmbed fetch and discovery, and every oEmbed cache write (`_oembed_*` post meta, and `oembed_cache` posts), so an embed appears as its plain URL. It omits three kinds of block whose output is data the agent cannot read directly: `core/loginout` (a logout URL with a nonce), every `core/avatar` block with or without a `userId` (an `isLink` avatar wraps its empty image in a link to the user's author archive, which names the user), and `core/navigation` with a `ref` that is not a published `wp_navigation` post. All avatar images are omitted wherever they come from (a shortcode, or another plugin): while the post renders, `get_avatar()` returns an empty string, including on the early `pre_get_avatar` path and through the `get_avatar` filter, and `get_avatar_data()` yields no URL, so no Gravatar hash of anyone's email address is printed. `core/post-author` is not omitted: the author's name is already part of the tool's output. Third-party shortcodes and blocks may still have side effects of their own, and they run with the agent's read grant. Output printed by shortcodes is discarded. A rendering error returns a generic message, never the exception text. The caller's global post is restored afterwards. Password-protected posts render their real content, and the password form is not included. The ability is annotated `readonly`.
- `list-terms` / `get-post-terms`: built in M1 as follows:
  - Taxonomies: a taxonomy is readable only when it is public, is attached to at least one allowed post type (§14.1), and is not one of the fixed exclusions `nav_menu`, `link_category`, `wp_theme`, `wp_template_part_area` or `wp_pattern_category`. There is no separate filter, so `steadhand_allowed_post_types` also decides which taxonomies agents may read. By default that is `category` and `post_tag`, with `post_format` (public and attached to `post`) and any public custom taxonomy attached to `post` or `page`.
  - `list-terms` takes `taxonomy` (required), `search` (up to 200 characters, matched against names and slugs), `parent` (0 for top-level terms only), `orderby` (`name`, `count` or `id`), `order`, `page` (1 to 10000) and `per_page` (1 to 100, default 50). It returns `items`, `total`, `total_pages`, `page` and `per_page`, with the total from a count query. Terms with no posts are included. A description is plain text, cut at 2000 bytes on a UTF-8 boundary.
  - `get-post-terms` takes a post `id`, read by the rule `get-post` uses. It returns the allowed taxonomies its type uses, grouped, with their terms. Each taxonomy returns at most 500 terms (`TermReader::MAX_TERMS_PER_TAXONOMY`), in name order, fetched with the query's own limit. Each entry also has `total`, the number of the post's terms in that taxonomy, counted in the database, and `truncated`, true when `total` is above 500. Terms of any other taxonomy are never returned.
- `list-menus` / `get-menu`: both kinds of menu are readable, and only through these tools, because the post and term tools exclude their types:
  - Classic menus (terms in `nav_menu`, items in `nav_menu_item`) and block navigation (`wp_navigation` posts). `list-menus` lists classic menus first, with their `item_count` and theme locations, then block navigation in the statuses `MenuReader::BLOCK_STATUSES`: `publish`, `draft`, `pending`, `future` and `private`. `get-menu` reads block navigation in exactly the same statuses, from the same constant. Trashed and auto-draft navigation is never listed or read. The list is capped at 200 menus, and `truncated` is set when more exist. A classic `item_count` is the count WordPress stores on the menu term (`count`), so it is not a count of loaded items, and it can include an item that `get-menu` leaves out.
  - `get-menu` takes `kind` (`classic` or `block`) and `id`. A classic menu loads the whole menu and returns a flat list of at most 500 items in menu order (`truncated` when there are more), each with its parent item ID, type, linked object type and ID, title and URL. The title is plain text, tags removed, entities decoded, cut at 1000 bytes. The URL and title are those the public menu prints. Items whose linked object is trashed or missing are left out. A linked object may be a draft, a private post or a type the post tools refuse. Only its type, its ID, and the item's title and URL are returned. A block navigation post returns its raw content (cut at 256 KB, as `get-post` does) and its block tree, with the same paths as `get-blocks`.
  - Neither kind returns users, post meta, or anything about a linked object beyond the title and URL that the menu itself shows.
- `list-media` / `get-media`: built in M1 as follows:
  - `list-media` takes `media_type` (`image`, `video`, `audio`, `application` or `text`, matched against the top-level MIME type), `search` (up to 200 characters), `parent` (0 for unattached media only, or the ID of a post the agent may read through the post rule; any other parent, including a trashed, missing or attachment ID, refuses the call with the standard text), `after` and `before` (ISO 8601 date-times, checked as real calendar dates, compared with the post date in the site's time zone), `orderby` (`date` or `title`), `order`, `page` (1 to 10000) and `per_page` (1 to 50, default 20). It returns `items`, `total`, `total_pages`, `page` and `per_page`. The query names the `inherit` status only, and it also applies the media rule's parent condition in SQL (a join on the parent's primary key), so `total` and the pages count only the rows the rule keeps. Each row is checked again. A page past the end is empty.
  - `get-media` takes `id` and returns the list fields: `id`, `title`, `slug`, `mime_type`, `media_type`, `url` (the public URL of the file), `alt`, `caption`, `date_gmt`, `modified_gmt`, `author` (`id` and display name), `parent` (the parent post ID, or 0), `width` and `height` (images and videos, from metadata, otherwise null), `filesize` (from metadata when stored, otherwise null; the file is never read from disk) and `duration` (seconds, for audio and video, otherwise null). It adds `description` (the content as plain text, cut at 5000 bytes on a UTF-8 boundary, with `truncated`) and `sizes` (the generated image sizes, at most 30, each with `name`, `url`, `width`, `height` and `mime_type`; an empty array for non-images).
  - Never returned: server file paths (`file`, `_wp_attached_file`, upload directories; only URLs), raw attachment metadata, `image_meta` (EXIF, IPTC and GPS fields such as camera, location, author and copyright), any post meta except the alt text, and user email or login.
  - The media rule (`MediaReader::within_rule()`): an attachment is listed and readable only when its own status is exactly `inherit` and its parent passes `MediaReader::parent_permits()`. That holds when the parent is 0, when the parent post no longer exists, or when the parent is of an allowed post type (`PostTypes::is_allowed()`) and is not in the trash. The parent's status is otherwise irrelevant (a draft, pending, private, future or published parent is fine), and so is its author. A private-status attachment, or one under a trashed post, a `wp_block`, a draft `wp_navigation`, or a private post of a registered type that is not allowed, is refused with the standard text by get-media and is neither listed nor counted by list-media. The parent's ID is returned; nothing else about the parent is.
  - `get-media` returns `url` as '' when `_wp_attached_file` is empty, blank or the falsy value `0` (core would fall back to the post GUID, which can be any stored string), when it is an absolute path (a leading slash, a backslash, or a Windows drive letter: core would embed that server path in the URL), and when core's URL is the post GUID but does not end with the stored file's name. Other hosts are not checked, because offloaded media uses them. Size URLs are the URL of the original with each size's own file name (`basename()` of the stored file), so `sizes` never holds a path.
  - Metadata is clamped, not trusted. A non-finite or negative `duration` is null. `width`, `height` and `filesize` are null unless they are positive integers, and dimensions are at most 1000000. A generated size whose name or MIME type is over 100 characters, or whose file name is empty, is skipped. A MIME type over 100 characters is cut to 100 and its `media_type` is ''; a malformed MIME type (not type/subtype of token characters) gives a `media_type` of ''. `title`, `alt` and `caption` are plain text, cut at 1000 bytes.
- `get-diagnostics`: built in M1 as follows. It takes `max_errors` (1 to 50, default 20) and nothing else: no path, URL or option name. It returns seven sections: `environment`; `theme`; `plugins` (active plugins by name and version, at most 100; update status comes only from the existing `update_plugins` transient, and no check is run); `php_errors`; `cron` (overdue counts and hook names, read from the stored option without writing it; hook arguments are never returned); `site_health` (the counts already stored in the `health-check-site-status-result` transient; no Site Health test is run); and `steadhand`, a self-check against core's ability registry, the MCP Adapter's server registry, the lockdown hooks, and whether the change-log table exists (`change_log_ready`). `php_errors` reads only the last 256 KB of the log that `WP_DEBUG_LOG` names. It never reads the server-wide `error_log` or any other file, and it refuses a symlink or a path outside `WP_CONTENT_DIR` or `ABSPATH` unless the owner configured that exact path. It keeps only standard PHP engine error lines, and skips and counts everything else, including stack traces and free-form `error_log()` output. Messages go through `Steadhand\Redactor`, which is best-effort (see §10). Site directories are removed from messages and every other absolute path in a message is reduced to its file name; a stack trace is cut at its first frame, so no call argument is returned; the database user and host in a connection error are masked. The `file` field is relative to the site, never holds a `..` segment or a leading slash, and is reduced to its base name otherwise. Identical entries are counted once, and the newest `max_errors` items are returned. The ability writes nothing and makes no outbound request: every HTTP request is blocked for the duration of the call by a guard that is removed in `finally`. Before any filesystem call, a `WP_DEBUG_LOG` value that core would not read as a plain path (a stream-wrapper or URL scheme, a relative path, a NUL byte) is refused, and so is any real path under `/proc`, `/sys` or `/dev`. The values core reads as the default log (`true`, `1`, `'1'`, `'true'`) mean `wp-content/debug.log`.
- `get-change-log`: built in M2 as follows. It shows the calling agent's own change-log entries (see §7).
  - Inputs: `page` (1 to 10000, default 1); `per_page` (1 to 50, default 20); `result` (`ok`, `blocked`, `fixed` or `error`); `ability` (a Steadhand ability name: `steadhand/` followed by up to 80 lowercase letters, digits or hyphens); `after` and `before` (ISO 8601 date-times, inclusive; read as instants, so a value without an offset is UTC). Any other argument is refused.
  - Output: `items`, `total`, `total_pages`, `page` and `per_page`. Each item has `id`, `created_at` (ISO 8601, UTC), `ability`, `object_type`, `object_id`, `result`, `message`, `guardrail_notes`, `undoable` and `undone`. `undone` is always false until undo exists. A page past the end is empty, not an error.
  - Own entries only. The query is bound to the calling user's ID, and no argument can widen it. Another agent's entries are never returned.
  - Never returns the stored `input` of a call.
  - Successful calls to this ability are not logged. Its refusals and failures are.
  - If the change-log table is missing, the ability itself returns `steadhand_log_unavailable` (503). Through the pipeline, though, the failed call is logged, that write fails too, and the caller receives `steadhand_log_failed` (see the known gaps in §7).

Write:
- `create-post` and `update-post`: built in M2 as follows. Both are writes, so they run the guardrails and the change log (§6, §7).
  - `create-post` takes `title`, `content`, `excerpt`, `slug`, `status`, `date` and `post_type`. The author is always the calling agent. `status` defaults to `draft` and may be `draft`, `pending`, `publish`, `future` or `private`. Any status other than `draft`, pending included, needs `steadhand_publish`; without it the call is refused. `date` (ISO 8601, read as UTC without an offset) is allowed only with status `future`, where it is required, and must be at least 60 seconds and at most 10 years ahead. `post_type` must be an allowed type (`post` and `page` by default). Title or content must be non-empty.
  - `update-post` takes `id` and at least one of `title`, `content`, `excerpt`, `slug`, `status` and `date`, with the same limits and status rules. It changes only the fields sent, and only where they differ from what is stored. `content` replaces the whole content; partial edits belong to `edit-blocks` (below). The post's type, author, password and parent cannot be changed.
  - Limits: title 400 characters, excerpt 5,000, slug 200 (lowercase letters, digits and single hyphens), content 262,144 characters and 256 KB in bytes (the content guardrail).
  - Output (both): `id`, `post_type`, `status`, `title`, `slug`, `link`, `modified`, `changed` (whether the write changed anything), `content_modified_on_save` (true when WordPress stored a title, content or excerpt that differs from what was sent, for example after KSES), `warnings` and `guardrail_notes`.
  - Refusals: a status other than `draft` without `steadhand_publish` (403); a post the caller may not edit, including one that is missing, trashed, of a type that is not allowed, or not readable, all with one text (403, `steadhand_forbidden`); a live status on a post the caller may not publish (403); invalid input, including a misplaced or out-of-range date, and a title and content that are both empty (400, `steadhand_invalid_input`); a guardrail block (422, `steadhand_guardrail_blocked`); a write whose row cannot be reserved (500, `steadhand_log_failed`, not performed); a write whose outcome cannot be recorded afterwards (500, `steadhand_log_incomplete`; the change was made). Added to `update-post` in review: `steadhand_refused_invalid_template` (409), for a post whose page template the active theme does not have, refused before any write; `steadhand_update_partial` (500), when WordPress reports an error after it has changed the post, or when a field the call did not send is changed after the write; `steadhand_update_failed` (500, "nothing was changed"), only when the post did not change.
  - Not supported in M2: post meta (D18). No write tool accepts meta keys, and no allowlist is defined.
  - Post date: a write sets the post date only when a date is sent. WordPress gives a draft with no set date the time it is published, so publishing an old draft does not backdate it. A scheduled update keeps the requested date.
  - Warnings for values WordPress stores differently: `Making a post private removes its password.` when a post with a password is made private; `WordPress stored the status "<stored>" instead of "<requested>".` when WordPress stores another status. Both tools return the status warning. A publish with a future date is stored as `future`, so `update-post` cannot publish a scheduled post early. `This site keeps too few revisions for Steadhand to undo this change.` when the site keeps one revision or none (see §7).
  - Known limits of `update-post`: `wp_update_post()` re-normalises some values that an administrator stored in an unusual way, by a direct database write, whatever fields the call sends. An empty `comment_status` on an update becomes `closed`. A non-canonical slug is sanitised. A post with no category gains the default category when its type is `post`. `to_ping` is sanitised. Steadhand does not restore these values. The title, content, excerpt and filtered content it does not send are kept byte for byte, as described above.
  - Unsent fields and save filters: WordPress's `wp_update_post()` saves every stored field again, not only the fields a call sends. The four post-field KSES filters are in place for the whole write, for every field, as they are on create, and no Steadhand code removes a KSES filter or the Global Styles filter. So code that runs during the save (a `save_post` listener, a revision insert, a nested write) is filtered too. To keep the fields a call does not send byte for byte, `update-post` records their stored values (title, content, excerpt and filtered content) before the write. A `wp_insert_post_data` filter at `PHP_INT_MAX` then sets each one back, slashed as core expects, after the save filters have run. It acts only on this post's own update (the update flag, the ID and the stored post type must match), only once (it disarms on its first match, so a nested update of the same post is filtered as usual), and it is removed in `finally`. The fields the call sends keep the value the KSES filters compute. After the write, `update-post` reads each unsent field again. If one differs from the value stored before the write, the error is `steadhand_update_partial`, not a success. Remaining limit: code that changes the row after `wp_insert_post_data`, at the same priority or a later one, or that writes the table directly, can still change an unsent field. Steadhand reports that as `steadhand_update_partial`; it does not prevent it. See §14.1.
  - Execute failure: for `update-post`, when WordPress reports an error, or the write throws, the post is read again, uncached. If it changed, the error is `steadhand_update_partial` (500): "The post was changed, but the save did not finish as expected, so the change was at least partly applied. Check the post before you continue." The same error and message are returned when a field the call did not send differs from what was stored, after a write that reported no error. If it did not change, the error is `steadhand_update_failed` (500): "WordPress could not update the post, so nothing was changed. Try again." For `create-post`, a WP_Error from `wp_insert_post()` is returned before the row is written (for example `db_insert_error`), so its message says nothing was saved. The one core error that comes after the row is written, `invalid_page_template`, needs a `page_template` value, which `create-post` never sends. For any other write, when its execute step throws, the call fails with `steadhand_error` and the message "The change could not be completed and may have been partly applied. Check the result before you continue." The read path's message is unchanged.
  - Post fields and KSES: on create, every post-field KSES filter is in place for the save, so everything the agent sends is filtered. On update, the same four are in place for the whole write, for every field (added where they are missing, and removed afterwards only if this call added them). A filter another component added stays. Steadhand never removes a KSES or Global Styles filter during a write, and never calls `kses_init_filters()` or `kses_remove_filters()`. The fields an update does not send are put back by the restore described above.
- `edit-blocks`: built in M2 as follows. It changes some blocks of one existing post or page, by path, without resending the whole content. It is a write, so it runs the guardrails and the change log (§6, §7).
  - Inputs: `id`, and `operations`, one to 20 objects. Each has `op`: `replace` (the block at `path` becomes `markup`), `insert_before` or `insert_after` (`markup` is added next to the block at `path`), `remove` (the block at `path` is deleted), or `append` (`markup` is added at the end of the content). Every op except `append` takes `path` (a dot-separated index, as `get-blocks` returns it, at most 100 bytes and 20 levels) and `name` (the block name `get-blocks` returned at that path, or `null` for classic HTML, at most 200 bytes). `append` takes neither. `markup` is required except for `remove`, which takes none. It must not be blank, must be valid UTF-8, and is block markup or classic HTML.
  - Semantics: every path refers to the content as stored before the call, not to the content after the other operations, so the order of the operations does not change the result. A path may be named once, and no path may lie inside a block another operation names. Paths are the ones `get-blocks` gives. The edits are byte splices: everything outside the edited spans is kept byte for byte. Inserted and appended markup gets one `\n\n` between it and an adjacent piece of content, only where neither side of that boundary is whitespace. Replacement markup gets no separator. Replacing or removing a root classic-HTML node replaces the whole gap, including the whitespace around it.
  - Name check: an operation whose `path` names no block, or a block with another name, is refused. A stale path therefore cannot edit a different block that now sits at the same index.
  - Reused from `update-post`: the object check and the permissions (`steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` as for `update-post`), the revision rule, the template refusal, the partial-failure errors (`steadhand_update_partial`, `steadhand_update_failed`), `warnings`, `changed` and the output fields. `edit-blocks` delegates the write to `update-post`, so every rule `update-post` has applies. The write itself is `PostWriter::splice()`, which stores the kept bytes as they are and filters the sent runs (see the storage rule below).
  - Storage rule (decided by Rick, 2026-11-23): bytes the call does not send are stored exactly as they are, and are not passed through the save filters. Only the markup the call sends, and the separators Steadhand adds next to it, are filtered, and each run of adjacent sent text is filtered once, as one piece (`PostWriter::assemble()`). The filters are the ones a save runs on `post_content`: the KSES filter; the custom CSS strip, which removes the `css` in a block's `style` attribute (where WordPress has the strip, from WordPress 7.0; Steadhand then puts it in place for every write, at core's priority 8, also for an agent user that holds `edit_css`, which core would not do); the invalid entity conversion (`&#128;` becomes `&#8364;`); tag balancing, when the `use_balanceTags` option is on; the emoji step, on a utf8 or utf8mb3 column; and any filter a plugin adds to `pre_post_content` or `content_save_pre`. The filtered result is what is stored. The call still succeeds, with `content_modified_on_save` true and a warning that WordPress changed part of the markup sent. The guardrails see exactly the bytes that will be stored. A call whose new content equals the stored content writes nothing.
  - Complete blocks, per operation: the markup an operation sends must be complete blocks on its own. Every block it opens is closed in the same markup, and it closes no block it did not open. Otherwise the call is refused with `steadhand_invalid_input` (400). After filtering, each run of sent text must still be complete blocks, or the call is refused with `steadhand_refused_unsupported_markup` (409): the markup does not stay complete blocks once WordPress has filtered it.
  - Open HTML before a sent run: the content before each sent run is read with `WP_HTML_Tag_Processor` (WordPress 6.5 and later; this plugin needs 6.9, so the method is always there). If the HTML is left open there (an unterminated `script`, `style`, `textarea`, `title`, `xmp`, `iframe`, comment, tag or attribute value), the call is refused with `steadhand_refused_unsupported_markup` (409). The stored content is not changed, and the message says a person must fix the post in the block editor. A closed `<script>` in a block before the edit is not refused.
  - Structure of the result: the content the segments produce must be complete blocks that agree with core (the same check `apply` uses on the stored content). Every stored block the edit keeps must still be there, with the same name at its new offset; a block whose whole span is kept must keep its length. Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409). A block that is replaced or removed, or that lies inside one, is not checked.
  - Split delimiters (token alignment): the block delimiters of the final content are checked against the stored bytes and the sent runs. Every delimiter of the final content must lie wholly inside one kept range or one sent run. The delimiters inside each kept range must be exactly the stored delimiters that lie wholly inside it, with the same offsets and bytes, and no stored delimiter may be cut by a kept range's edge. The delimiters inside each sent run must be exactly the ones core finds when it reads that run alone. A sent run that leaves HTML open (an unclosed script, textarea or comment) is refused when stored content follows it, with the same code and a message of its own. Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409): the markup would form a block that neither is on its own. This stops a delimiter completed across two places, or one that is only whole once bytes from outside a run are joined to it (`BlockEditor::aligned()`).
  - No stray HTML comments: in each operation's markup (`steadhand_invalid_input`, 400), and again in each sent run after filtering (`steadhand_refused_unsupported_markup`, 409), every `<!--` must start a block delimiter, or be a break comment inside its break block. `<!--more…-->` (including `<!--more-->` with custom text) and `<!--noteaser-->` are allowed only as the content of a `core/more` block; `<!--nextpage-->` only as the content of a `core/nextpage` block. Every `-->` must lie inside a block delimiter or one of those comments. A bare break comment is refused, because core removes a break comment when it displays content, so bytes that were not adjacent at save time would become adjacent. The 400 message says to use the `core/more` or `core/nextpage` block for a break. Ordinary HTML comments such as `<!-- note -->` cannot be sent. Stored ones, in bytes the call does not send, are kept as they are, bare break comments included.
  - Preview check: the guardrails see the content as it will be stored. The guard records the SHA-256 of the content it returns to the guardrails. The plan refuses, with `steadhand_update_failed` (500), unless its own preview has that hash, and the write refuses when the content it assembles differs from the plan's preview. So nothing is written that the guardrails did not see. A call with no recorded hash (the per-operation fallback) is refused the same way.
  - A call that would leave the post with no title, no excerpt and no content is refused before the write with `steadhand_invalid_input` (400).
  - Joins over removed content: where two kept ranges are not contiguous, because the call removes the content between them, the stored bytes before the join must not leave HTML open (the check a sent run gets). Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409): the stored content leaves HTML open where the edit removes the content between two of its parts. A remove-only call is checked this way too.
  - Break comments: a break comment (`<!--more-->`, `<!--more text-->`, `<!--noteaser-->` or `<!--nextpage-->`) is allowed only as the sole inner content of its owner block. `more` and `noteaser` need a `core/more` block, whose inner content must match `<!--more( [^>\n]*)?-->(\s*<!--noteaser-->)?`. `nextpage` needs a `core/nextpage` block, whose inner content must be `<!--nextpage-->`. Anywhere else it is refused: `steadhand_invalid_input` (400) in the sent markup, or `steadhand_refused_unsupported_markup` (409) in the sent run after filtering.
  - Display-time `more` split: WordPress shows a post by cutting its content at a `<!-- wp:more` delimiter (`get_the_content()`). The pattern Steadhand checks is `BlockEditor::DISPLAY_MORE`, copied from core. The check runs on the whole result, not only on sent runs: every match in the final content must be exactly one whole delimiter token, or lie wholly inside one kept range and be byte-identical to a match of the stored content at the offset that range maps to. Anything else would make WordPress drop stored bytes when it shows the post, so it is refused with `steadhand_refused_unsupported_markup` (409): "This edit would make WordPress drop part of the content when it shows the post, so nothing was changed. If you sent a core/more block, send it with its opening and closing comments, not as a self-closing block." The raw markup of each operation is checked the same way first (`steadhand_invalid_input`, 400: "The markup of operation N would make WordPress drop part of the content when it shows the post..."). A PCRE failure in either check refuses the call.
  - Known limits of the storage rule: stored bytes are kept as they are. Stored HTML that is closed but malformed, or that core reads differently from the tag processor, is kept and not reported. A plugin that changes the post during the save is reported by `content_modified_on_save`, not prevented. The filters run on the sent markup more than once per call (for the preview and for the save), with the same result each time.
  - Guardrails: they see the whole resulting content as `content`. When the operations cannot be applied, they see each operation's markup as `operations.<n>.markup`, so the rules still judge what was sent. Nothing is written in that case. The guardrails run before the checks below, so a markup the rules refuse gets a 422 even when its path would also be refused.
  - Refusals, all with nothing written: `steadhand_refused_unsupported_markup` (409: Steadhand cannot read the block structure the way WordPress does; use `update-post` with the complete content); `steadhand_refused_block_mismatch` (409: a path names no block with that name; call `get-blocks` again); `steadhand_refused_content_changed` (409: the post changed between the guardrail check and the write; call `get-blocks` again); `steadhand_refused_unsupported_markup` (409, from the complete-blocks, open-HTML and structure checks above; each has its own message). Shape errors are `steadhand_invalid_input` (400): the operation count, the fields each op takes or refuses, the path and name grammar, blank or missing markup, a path sent twice, and a path inside another named block. A guardrail block is `steadhand_guardrail_blocked` (422), as for `update-post`.
  - Log: each call keeps the `op`, `path` and `name` of each operation. Each operation's markup is stored as a digest, not as text (§7). A refusal raised while the write is prepared (snapshot or execute) is logged with result `error`. A guardrail or input refusal is logged as `blocked`.
  - Limits: a post whose resulting content is over the content limits (§6.1: 2,000 blocks, 20 levels, 256 KB) cannot be edited with this tool, even for a small change. The tool cannot add the first child of an empty container block, because that block has no path: it replaces the container instead.
- `set-post-terms`: built in M2 as follows. It is a write, so it runs the guardrails and the change log (§6, §7).
  - Inputs: `id`; `taxonomy` (lowercase letters, digits, `_` and `-`, at most 32 characters); `terms`, an array of up to 100 distinct term IDs (positive integers, from `list-terms` or `get-post-terms`; it may be empty); and `mode`: `replace` (the default: the post's terms in the taxonomy become exactly `terms`), `add` (the current terms and `terms`) or `remove` (the current terms without `terms`). Names and slugs are refused by the schema. The tool never creates, renames or deletes a term.
  - Rules, all checked before a write and again immediately before it: the post must pass `update-post`'s object check, and its post type must register meta mapping (`map_meta_cap` true). The taxonomy must be allowed (§5, §14.1) and attached to the post's type. Every term ID must be a term of that taxonomy. A call may leave the post with at most 100 terms in the taxonomy only when it does not add terms: a `remove` from a post that already has more is allowed, and an `add` or `replace` that would take it over 100 is refused. A post format takes at most one term. A post that already has more than 500 terms in the taxonomy is refused until a person reduces them. Terms are written only when the final set differs from the current one.
  - Lost updates: the final set is computed from the terms read at the start of the call. Immediately before the write, the assigned IDs are read again; if they differ, nothing is written (`steadhand_refused_content_changed`). The post is read again before the write too, and the permission check runs on that fresh copy, so a status change made during the call (for example a publish) is refused.
  - Permissions: `steadhand_read` (to read the post), and `steadhand_write_drafts` for a draft, pending or auto-draft post, or `steadhand_publish` for a published, scheduled or private post, as `update-post` does. A taxonomy whose own assign capability is not core's default also needs that capability, held by the caller (D21). Steadhand never grants that capability, and adds no mapping to MetaCaps.
  - Refusals, all with nothing changed: a taxonomy that is not allowed, or not attached to the post's type (400, `steadhand_invalid_input`; the allowed taxonomies for the post's type are listed only when the caller may read the post; for a missing or unreadable post the refusal is `steadhand_forbidden`); a term ID that is not a term of the taxonomy, a repeated ID, two post formats, or a call that adds terms and leaves more than 100 (400, `steadhand_invalid_input`); a post that is missing, trashed, of a type that is not allowed, unreadable, not editable by the caller, or of a type that does not register meta mapping (403, `steadhand_forbidden`, one text); a taxonomy whose assign capability the caller does not hold (403, `steadhand_forbidden`); the terms changing while the call runs (409, `steadhand_refused_content_changed`); a post someone is editing in the block editor, and the rate limit (422, `steadhand_guardrail_blocked`); more than 500 terms already in the taxonomy (409, `steadhand_refused_too_many_terms`). A schema violation (more than 100 IDs, repeats, a string, an extra property) is refused before any rule runs.
  - Refusal logging: refusals of the input and the permission check are logged as `blocked`. Refusals made at execute time, because they depend on the state of the post (the 500-term guard, the 100-term cap, the one-format rule, a change made during the call), are logged as `error`.
  - Output: `id`, `taxonomy`, `term_ids` (the result, ascending, at most 500), `terms` (`id`, `name`, `slug` and `parent`, in name order, at most 500), `previous_term_ids` (the IDs before the call, ascending), `changed`, `link` (the permalink after the call), `warnings` and `guardrail_notes`. `previous_term_ids` is what a caller uses to put the terms back. `link` is empty when WordPress cannot give the post a permalink.
  - Warnings: when `changed` is true, "Steadhand cannot undo a change to a post's terms yet. previous_term_ids holds the terms the post had before." When a published post's permalink changes, "This change moved the post to a new address. WordPress does not redirect the old one." (a permalink follows the categories with `%category%`). For a `post` that ends with no category, "WordPress gives a post with no category the default category the next time the post is saved."
  - Not undoable yet: the snapshot is 0 and there is no undo for terms (M3).
  - Failures: `steadhand_update_partial` (500, "The terms were changed, but not as asked … Call steadhand/get-post-terms to check the post before you continue."), when WordPress reports an error from the write and the terms changed or cannot be read, when the terms cannot be read back after the write, or when the terms after the write are not the ones asked for (for example after a `set_object_terms` listener changed them). `steadhand_update_failed` (500, "WordPress could not set the terms, so nothing was changed. Try again."), when WordPress reports an error from the write and the terms did not change. A refusal made by the writer before any write is returned as it was, never as one of these two.
  - Known limits: `save_post` does not run, and the post's modified date does not change, so plugins that listen only to `save_post` (caches, search indexes, sitemaps) are not told. On a taxonomy registered with `sort`, the term order is rewritten, and `previous_term_ids` cannot restore it. WordPress's `wp_set_object_terms()` does no capability check of its own, so the checks above are Steadhand's. A taxonomy registered with its default capabilities is refused on a post type whose edit capability is not the one it assigns (for example a page, or a type with its own capabilities). That is the safe direction, and it is stated in the tool's description. A taxonomy whose assign capability is a meta capability is checked by WordPress with no term, which WordPress reports as an incorrect-usage notice. The call is still refused for an agent that does not hold it; Steadhand cannot detect that case precisely without core's internals. A new post may already hold the default category, so `previous_term_ids` can contain it. Two calls that overlap in time can leave a post with more than 100 terms, because the comparison and the write are not atomic: the later call usually reports `steadhand_update_partial`, and further adds are then refused. `link` is empty when WordPress cannot give the post a permalink, and then no moved-address warning is given. The moved-address warning is given for published posts only.
- `upload-media`: from a base64 payload or an https URL (SSRF-safe: no private IP ranges, size/type limits, using core's sideload functions).
- `set-featured-image`
- `update-menu`
- `trash-post` / `restore-post`
- `update-option`: only options on the allowlist; everything else is refused with an explanation.
- `undo-change`: reverse a logged change by ID (only changes this agent can see and that are still undoable).

Explicitly **not** in v1: user create/update/delete, plugin/theme management, file editing, arbitrary option writes, raw SQL, permanent delete, comments (deferred to v1.1).

## 6. Guardrail engine

Runs on every write, before execution. Each rule has a **mode**: `block` (refuse, with a clear message the agent can act on), `fix` (rewrite input safely, then log what changed), or `warn` (allow, but flag it in the log and the response). A `fix` is checked again with the ability's schema, its input rule and its object check. A fix that changes `object_type` or `object_id` is refused with "A guardrail changed which object this call is about, so it was refused." A fix whose input fails the schema is refused with "A guardrail changed this call into one that is not allowed, so it was refused." (see `docs/HOOKS.md`, Rules of engagement).

### 6.1 Built-in rules (Free, always on)
| Rule | Mode | Why |
|---|---|---|
| Never write `widget_block`, `sidebars_widgets`, `theme_mods_*` | block | JSON-vs-serialized corruption; site-wide fatal errors |
| Never write options a plugin stores as PHP-serialized arrays (detected by reading the existing value) | block | The plugin silently ignores the value, or corrupts it |
| Option writes limited to the allowlist | block | Arbitrary options can break sites or escalate privileges |
| Block markup must re-validate (parse → serialize round-trip; block validation check) | block | Prevents "This block contains unexpected content" damage |
| Post content size and nesting limits | block | Runaway or looping agents |
| Rate limit per agent (writes/minute) | block | Runaway agents |
| Never touch `wp_users`, roles, capabilities, `active_plugins`, `siteurl`/`home` | block (hard-coded, not configurable) | Privilege escalation and takeover |
| A post that another user has open in the block editor (live `_edit_lock`); added in M2, not in the original table | block | Two people overwriting each other's open edit |

**Status in M2.** The built-in rules that exist, all in block mode (none uses `fix` or `warn` yet; the engine supports both, see `docs/HOOKS.md`):

- Post content size and nesting: `steadhand/content-limits`. Content over 256 KB (262,144 bytes), more than 2,000 blocks (nested blocks counted), nesting deeper than 20 levels, or content that is not valid UTF-8 is refused. Exactly at a limit passes. Only fields that hold block markup are checked: `content`, and for `edit-blocks` each `operations.<n>.markup` when the operations cannot be applied (see §5).
- Block markup: `steadhand/block-markup`. **Structural check only.** It checks that block comment delimiters are well formed and balanced, that each closing comment matches the block on top of the stack, and that each delimiter's JSON attributes decode. It cannot run the editor's JavaScript validation (the save-output comparison behind "This block contains unexpected or invalid content"), because that needs the block's JavaScript, and it does not check that a block name is registered or that attributes match a block's schema. The round-trip check in the table above is not built. Decision D17 (§14) records this. Delimiters are matched case-sensitively, with whitespace after `<!--`, as core's parser reads them, so `<!-- WP:Engine cache note -->` and `<!--wp:x-->` are not delimiters and are not refused. Known false positive: text that looks like a malformed delimiter (for example `<!-- wp:x` with no closing comment) inside a `core/html` block, or inside an ordinary HTML comment that starts with `<!-- wp:`, is refused.
- Rate limit: `steadhand/rate-limit`. 30 writes per agent in any rolling 60 seconds, counted from the change log. A reserved write counts, and a refused call does not. The `steadhand_rate_limit_per_minute` filter sets 1 to 600 and cannot turn the limit off.
- Edit lock: `steadhand/edit-lock` (added in M2). A write to a post that another user holds open in the block editor is refused while WordPress's lock is live. The window is WordPress's (150 seconds, changeable with `wp_check_post_lock_window`, 1 to 3,600 seconds). The lock is parsed as WordPress's `wp_check_post_lock()` parses it: the text before the first colon is the time and the text after it is the user, both read as numbers, so a lock with a leading space or a trailing newline means what WordPress makes of it. A lock in the older format (a timestamp with no user) takes its holder from `_edit_last`. A fresh one with no holder, holder 0 or another user blocks; the agent's own holder passes. A lock that is not a number is not live.

Not built yet:

- The option rules (no write to `widget_block`, `sidebars_widgets` or `theme_mods_*`; no write to plugin options stored as serialized arrays; option writes limited to the allowlist). They arrive with `update-option`, which does not exist yet.
- The hard-coded block on users, roles, capabilities, `active_plugins`, `siteurl` and `home`. No tool that could reach these exists yet, so the rule is not needed yet. It must be built before any tool can write to one of them.
- Block markup checks beyond the structural check above.
- Presets (§6.2) are not built in M2.

### 6.2 Presets (Free, toggleable)
- **Color slugs → hex** (`fix`): converts named color slugs in block attributes (e.g. `"backgroundColor":"white"`) to explicit hex `style` values. This catches a known cause of block validation errors with some themes.
- **Kadence preset:** block `theme_mods_kadence`; refuse unsupported attributes such as column `border.radius`.
- **Rank Math preset:** block writes to `rank-math-options-*`; route SEO meta through per-post meta keys only.

### 6.3 Custom rules (Pro)
Admin-defined rules: protected posts/pages (e.g. "never modify the homepage or legal pages"), option/meta allow and block lists, content rules (regex/blocklist), per-agent overrides, and scheduled "read-only windows".

## 7. Change log and undo

- Custom table `{prefix}steadhand_log`: `id`, `created_at`, `user_id`, `agent_label` (application password name), `ability`, `object_type`, `object_id`, `input` (secrets redacted, size-capped), `result` (ok / blocked / fixed / error), `guardrail_notes`, `snapshot_id`, `undoable`, `undone_by`.
- Snapshots: posts use **core revisions** (store the revision ID); menus, terms, options and meta store a compact before-state in `{prefix}steadhand_snapshots`.
- **Undo** restores the snapshot if the object hasn't changed since (otherwise it refuses and explains, like AI Engine's "edited again since").
- Admin screen: filterable log (agent, ability, result, date), single-change view with a diff, undo button.
- Retention: Free keeps 30 days; Pro is configurable, with CSV/JSON export.
- Logging must not fail open: if the log write fails, the change is rolled back or not executed. Refused calls are logged too (result `blocked`), including calls refused at the permission check before execution.

**Status in M2.** This is what exists now. Undo and the admin log screen are not built yet.

- The table `{prefix}steadhand_log` (`includes/Log/Schema.php`), with the columns listed above: `id`, `created_at` (UTC), `user_id`, `agent_label`, `ability`, `object_type`, `object_id`, `input`, `result`, `message`, `guardrail_notes`, `snapshot_id`, `undoable` and `undone_by`. It has keys on `created_at`, on `(user_id, created_at)` and on `(user_id, id)`. `snapshot_id` is the ID of the snapshot revision (see below), or 0. `undone_by` is reserved and always 0. `guardrail_notes` holds the notes a write's guardrails recorded, joined by newlines, or is empty.
- What is logged, for every tool: every refused call (`blocked`), every failed call (`error`) and every successful write (`ok`, or `fixed` when a guardrail rewrote its input). A successful read call is not logged when its ability is read-only and needs `steadhand_read`, unless the `steadhand_log_read_calls` filter returns true (`docs/HOOKS.md`). Every other successful call is logged.
- Writes are recorded in two steps. Before the change, the write reserves its row: the row is stored with result `error` and the message "The call started, but no outcome was recorded.", so a crash leaves an honest row. After the change, the outcome is written to that row. If the reservation fails, the write is not performed and the caller gets `steadhand_log_failed`. If the change was made but the outcome cannot be recorded, the caller gets `steadhand_log_incomplete` and is told the change was made. A write refused by a guardrail, or at the permission check, writes one `blocked` row instead and reserves none.
- Snapshots for posts are core revisions. Each revision mirrors the post's row as it is stored when the revision is saved: its title, content and excerpt are read from the row, never from the call. The save filters therefore never change a revision, for `update-post` and `edit-blocks` alike, and an administrator's stored markup survives in every revision. Autosaves are not changed, and a revision of another post is filtered as usual. `update-post` saves a revision of the post immediately before it changes the post, when revisions are available. The snapshot is the newest non-autosave revision whose title, content and excerpt equal the post's current ones exactly, as they were before the change. The revision limit is ignored when it is looked up. The row's `snapshot_id` is that revision's ID whenever one is found, even when `undoable` is 0. `undoable` is 1 only when a revision was found, the site keeps two or more revisions (or unlimited ones), and the call changes only title, content and excerpt (no status, slug or date key in the input). With one revision kept, WordPress removes the revision taken before a change on the save that follows, so no snapshot is taken and the call warns "This site keeps too few revisions for Steadhand to undo this change." `undoable` is 0 in every other case where no revision was found, for example when revisions are off for the post or the site, or the post type does not support them. A snapshot is never an autosave. If no revision matches, the snapshot ID is 0 and the call returns a warning. A call that sets status, slug or date returns this warning: "This change includes status, slug or date, which Steadhand cannot undo yet." A revision does not restore status, slug or date; the snapshot table for those is later work. A call that changes nothing takes no revision. The check is `Snapshots::post_revision()`, which returns the newest matching revision only: an older revision that matches does not count.
- `create-post` rows are stored with `undoable` 0, because there is no earlier state to save. Steadhand does not undo a created post yet, and no revision is saved for it. Undo is M3.
- The object an entry names. For `get-post`, `get-blocks`, `get-rendered` and `get-post-terms` the type is `post`; for `get-media` it is `attachment`. The ID is the one the caller asked for. It is recorded before the access check, so a refused call keeps the ID even when no such post exists, and the agent can read that ID back through `get-change-log`. For `create-post` the type is `post`, and the ID is the new post's ID once the write completes, or 0 when the call is refused or fails. For `update-post` the type is `post`, and the ID is the one the caller asked for.
- Input. It is redacted with `Redactor::value()`, with every key redacted as well as every value (a key that is a secret is masked, and two keys that redact to the same text both keep their values, the later as `#2`), and then capped at 16 KB of JSON. Input over 256 KB of JSON is not scanned at all. Larger input, and input that cannot be encoded, is stored as `{"truncated":true,"bytes":N,"keys":[...]}`, with the original size and up to 50 top-level key names, each key redacted. Input that passed schema validation is stored sanitized. A call refused for invalid input stores its input with the same digests, then redacted, so the text of its content is not kept either. Post content is stored as a digest, not as text, whatever its length: the stored `content` field is `{"bytes": <n>, "sha256": "<digest>"}`. The digest is of the text as submitted, before WordPress filters it on save, so it matches the stored content only when `content_modified_on_save` is false. An excerpt over 500 bytes is stored the same way; a shorter excerpt keeps its text. A value that is not text (an input that failed validation can hold one) is stored as `{"bytes": 0, "type": "<gettype>"}`. The digest is the SHA-256 written as eight groups of eight hex digits separated by spaces, so the log redactor does not mask it as a token. The revisions hold the text. An ability can change its log copy with `Ability::log_input()`, a public method of the internal base class, which is not an extension point. If it throws, an empty input is recorded and the row is still written.
- Refusal throttle. For each agent user, at most 60 refused calls (`blocked` entries only) are stored in any rolling minute. Then one marker row (`blocked`) is stored, and nothing more until the minute has passed. Errors are never throttled or dropped: an `error` entry is written after the call ran, and it is always stored. The count and the insert are not locked together, so concurrent requests can store slightly more than 60.
- Retention. Entries are kept 30 days, or the number of days the `steadhand_log_retention_days` filter returns (at most 3650). Pruning runs when an entry is written, at most once a day. A pass deletes in batches of 1,000 rows, up to 20 batches. A pass that ends on a short batch is recorded for the day. A pass that runs out of batches is not recorded, so the next write continues it. It does not use WP-Cron, so while nothing is written, entries past the period stay.
- Schema version. The option `steadhand_db_version` holds the layout version (`1`). The table is created by the activation hook. It is also created on the first request after the plugin is updated, whenever that option is missing or differs from the code's version, which covers an update from 0.1.0 (where the table did not exist). If that create fails, no version is recorded, and the request-time retry waits an hour (a transient, `steadhand_schema_retry`). Activation always tries. Database errors from the create and from the table check are never printed. Uninstall drops the table, removes the version and prune options, and removes the retry transient.
- The agent label is the name of the Application Password used for the request, as stored in the entry. Redaction is best-effort (§10).
- Known gaps, open:
  1. Input rejected by core's own schema validation, before the permission callback runs, is not logged. The pipeline class docblock says so.
  2. Closed for writes: a write's row is reserved before the change (see above). Read calls still log after they run. For a read call that ran, a failed log write returns `steadhand_log_failed` in place of the result. That is harmless for reads, because nothing changed. The message says the action was not performed, which is true only for a refused call.
  3. With the table missing, the pipeline cannot store the entry for a failed call, so the caller receives `steadhand_log_failed`. For a write, the write is then not performed. The tests cover this with the real logger and failing inserts. `get-change-log` returns `steadhand_log_unavailable` (503), not an empty list, when the log cannot be read: when the table check fails, or when its SELECT or COUNT fails. That error is itself a failed call, so one `error` row is stored for it. If that row cannot be stored either, the caller receives `steadhand_log_failed`.
  4. Revisions can be pruned. `wp_save_post_revision()` deletes old revisions beyond the site's revision limit, so an older log row's `snapshot_id` can point at a revision that no longer exists. Undo (M3) must check that the revision exists before it restores anything.
  5. Outside the MCP path, a schema refusal's message can contain a property name the caller sent. The MCP Adapter validates the schema first, so MCP calls do not reach it. To be fixed separately.

## 10. Security requirements (non-negotiable)

- Every REST/ability entry point: capability check → schema validation → sanitization. Every output escaped by context.
- All SQL through `$wpdb->prepare()`; no dynamic table or column names from input.
- Admin UI: nonces on every form and action; `manage_options` required to manage agents and guardrails.
- No secrets in logs (redact any field matching password/token/key/secret patterns). The one redaction helper is `Steadhand\Redactor` (`includes/Redactor.php`). `text()` masks secrets inside free text: `Authorization` and `Cookie` header values, URL userinfo, sensitive key/value pairs (query, form, JSON, PHP array-dump and serialized shapes, with bracketed values masked whole), the authentication schemes Basic, Bearer, Negotiate and Digest, JSON Web Tokens, PEM private-key blocks, password hashes, GitHub, AWS, Slack, Stripe, Google, GitLab, Twilio, Mailgun, SendGrid, npm, Hugging Face, OpenAI and Anthropic tokens, WordPress application passwords, salt and key constants, long opaque strings that mix letters and digits (32 characters or more), payment card numbers that pass Luhn (as `[card]`), the database user and host in connection errors, and email addresses, including internationalised ones (replaced with `[email]`). It also removes control characters and ANSI escape sequences. The class docblock lists what it does not catch. `value()` walks an array and masks any value under a sensitive key. Redaction is best-effort pattern matching. It reduces the chance of a leak and cannot guarantee there is none, so callers must still avoid collecting secrets. A regular expression that fails masks the whole string rather than returning it. The change log uses the same helper.
- SSRF protection on any URL fetch (`wp_safe_remote_get`, block private/reserved ranges, size and type limits).
- No `eval`, no dynamic includes, no shell calls, no unserialize of untrusted input.
- Uninstall (`uninstall.php`, which runs only when the Composer autoloader is present): remove our table (`{prefix}steadhand_log`), our options (`steadhand_db_version` and `steadhand_log_last_prune`) and the `steadhand_agent` role, strip every Steadhand capability from every user, and revoke the application passwords of users whose only role was the agent role (those credentials exist only for agent access). Users are never deleted, and users who also hold another role keep their application passwords. No orphans are left behind.
- `SECURITY.md` with a disclosure policy. GitHub private vulnerability reporting is available only once the repository is public (M4); until then reports go privately to the maintainers. Security fixes are released within 7 days of a confirmed report.
- Before each release: PHPCS (WordPress Coding Standards + security sniffs), Plugin Check, the test suite, and a MAKR pentest pass against a staging site (auth bypass, capability escalation, guardrail bypass, injection, SSRF).

### 14.1 D6 — what an agent can edit

Edit rights depend on the post's status, not on who wrote it.

- **Post types:** `post` and `page` by default, through the filter `steadhand_allowed_post_types` (an extension point, documented in `docs/HOOKS.md`). Always excluded, even if added to that list: attachments (the media tools handle those), `wp_template`, `wp_template_part`, `wp_navigation`, `wp_block`, `wp_global_styles`, `nav_menu_item` and `revision`. In addition, every built-in post type other than `post` and `page` is excluded (every type WordPress registers with `_builtin` true, such as `custom_css`, `customize_changeset`, `oembed_cache`, `user_request`, `wp_font_family` and `wp_font_face`, and any core type added later). A custom type that is not built in can be added, but only if it is registered with `map_meta_cap` on. A type registered with `map_meta_cap` off is never allowed, even when the filter adds it (§14.1).
- **Taxonomies:** the term tools follow the post types. A taxonomy is readable only when it is attached to an allowed post type, is public, and is not in the fixed exclusions listed in §5. So changing `steadhand_allowed_post_types` changes the taxonomies too, and no separate filter exists for them. The menu types (`nav_menu`, `nav_menu_item`, `wp_navigation`) are read only by the menu tools, which do their own status and type checks.
- **`steadhand_read`:** read allowed-type posts in any status except trash.
- **Object check:** every single-post tool gets its post from one function, `PostReader::readable_post()`, both in its object check and in its execute step. The function returns the post only when all of these hold: it exists, it is not in the trash, its type is allowed, and the current user passes `read_post`. list-posts checks each row the same way. The type and trash rules live in that function because MetaCaps cannot always see them. A type registered with `map_meta_cap` false is never allowed, so the type rule refuses it. For such a type whose `read_post` capability is set to another one (here `read`), WordPress passes that capability to the `map_meta_cap` filter, not `read_post`, so MetaCaps never sees the call, and the type rule is the only layer for it. For the other types registered with `map_meta_cap` false, MetaCaps is the second layer and refuses `read_post` (see the bullet on those types below). Every refusal from these tools has one text.
- **`steadhand_write_drafts`:** create posts, saved as `draft` unless the agent also holds `steadhand_publish` (§5). Edit existing posts of any author while their status is `draft`, `pending` or `auto-draft`. May change a draft to pending, never to publish, future or private. May never change `post_author`.
- **`steadhand_publish`:** edit posts that are published, scheduled (`future`) or private, and set those statuses.
- **`update-post` and `edit-blocks` also need `steadhand_read`:** their object check reads the post through `read_post`, which needs `steadhand_read`. They also need `steadhand_write_drafts` or `steadhand_publish`, as above.
- **`set-post-terms` follows the same rules:** the object check reads the post with `read_post` (`steadhand_read`), and the status decides between `steadhand_write_drafts` and `steadhand_publish`, as for `update-post`. Its taxonomy must be allowed and attached to the post's type (§5). A taxonomy with its own assign capability is checked as D21 says (§14).
- **Unsent fields (`update-post`):** WordPress re-saves every stored field on each save, and an agent's saves are filtered by KSES because it lacks `unfiltered_html`. `update-post` puts back the stored title, content, excerpt and filtered content of the post for each one the call does not send, after the save filters have run, so those bytes are kept (§5, Unsent fields and save filters). It does not refuse a call because of a filter on this site. A change to an unsent field that is made after the restore is detected after the write, and reported as `steadhand_update_partial`. `edit-blocks` applies the same principle to the blocks it does not name: they are stored as they are, and only the markup it sends is filtered (D20).
- **Invalid page template (`update-post`):** WordPress validates a page template after it has written the row, so a post whose template the active theme does not have would change and then be reported as an error. `update-post` checks the template the way core does, before any write, and refuses (409, `steadhand_refused_invalid_template`). An administrator must set a valid template.
- **Attachments (media tools):** media library items are readable through the media tools only, by two layers, and both apply the same media rule (`MediaReader::within_rule()`, described under §5): the attachment's own status is `inherit`, and its parent is none, missing, or of an allowed type and not trashed. Layer one is `MediaReader::readable_attachment()`, which returns an attachment only when it exists, its type is `attachment`, it passes the media rule, and the current user passes `read_post`. Layer two is the `map_meta_cap` rule in `MetaCaps`: inside a Steadhand call, for a dedicated agent, `read_post` on an attachment requires `steadhand_read` only and passes the media rule; otherwise it is refused. Core resolves an attachment to its parent's status and would refuse a draft parent, so the rule replaces that answer. Outside a call, and for every other user, core's answers stand for layer two, and layer one still applies the media rule. `edit_post`, `publish_post` and `delete_post` are never granted on an attachment by this rule. The post tools still refuse attachments, because `PostReader::readable_post()` checks the type itself, and `attachment` stays in `PostTypes::ALWAYS_EXCLUDED`.
- **How:** a `map_meta_cap` filter maps `read_post`, `edit_post`, `publish_post` and `delete_post` to Steadhand capabilities for agent users. The role never gets WordPress's general editing capabilities (`edit_posts`, `edit_others_posts` and so on). The status of the mapping in M2 is set out in the table after this list.
- **Post types registered with `map_meta_cap` false are never allowed.** Such a type is never an allowed type, even when the owner adds it to `steadhand_allowed_post_types`. Core makes none of its per-post checks for such a type (author, status, privacy page), and for some of them core renames `read_post`, `edit_post` or `publish_post` to a capability the agent may hold (for example `read`), so the mapping would not see the call. So every Steadhand tool refuses its posts and the parents of its attachments. The allowlist (`PostTypes::allowed()`) decides this, and every list, count and check uses that one list. Where core keeps the capability names, MetaCaps refuses `read_post`, `edit_post` and `publish_post` for such a type as well, as a second layer. It never grants `delete_post`. A type registered with `map_meta_cap` on, as `post` and `page` are, is not affected.
- **Security requirement:** the mapping applies only while a Steadhand pipeline request is running (a context flag the pipeline sets and clears). Application Passwords also work against WordPress's own REST API; if the mapping applied everywhere, an agent could edit posts through `/wp/v2/posts` and skip the guardrails and the log. So in M1 agent users' credentials are refused everywhere except the Steadhand MCP endpoint (core REST, XML-RPC, wp-admin, and the MCP Adapter's default server at `/wp-json/mcp/mcp-adapter-default-server`). Negative tests cover both the mapping and the block. It is also off once WordPress is shutting down, so a shutdown hook that runs after a `wp_die()` or `exit` inside an ability does not see a call in progress. A `do_not_allow` from core or from an earlier `map_meta_cap` callback is returned unchanged, so Steadhand never turns another component's denial into a grant. The order of the pipeline steps is fixed: defaults, schema, sanitizing, the caller's identity and Steadhand capabilities, the ability's input rule, and then the object check. A caller without the capability learns nothing from the input rule.

**Mapping in M2** (`includes/MetaCaps.php`), for a dedicated agent during a Steadhand call. `edit_post` and `publish_post` are mapped only during a write call (an ability that is not read-only; the innermost Steadhand call decides, via `Pipeline::is_write_call()`). `read_post` is mapped in every Steadhand call:

| Capability | Post (not an attachment) | Attachment |
|---|---|---|
| `read_post` | `steadhand_read`, for any status except trash, of an allowed type | `steadhand_read`, when the media rule passes; otherwise refused |
| `edit_post` | `steadhand_write_drafts` for `draft`, `pending` and `auto-draft`; `steadhand_publish` for `publish`, `future` and `private`; refused for any other status | refused |
| `publish_post` | `steadhand_publish`, whatever the status | refused |
| `delete_post` | not mapped: core's answer stands, and the agent role holds nothing that grants it, so it is refused | refused |

A post that is missing, in the trash, or of a type that is not allowed is refused for every mapped capability. Outside a Steadhand call, WordPress's own answers stand. Inside a read tool, such as `get-rendered` when a shortcode runs, core's answers stand for `edit_post` and `publish_post`, so they are false for an agent. The mapping replaces only the post type's own capabilities. If core asks for anything else (for example `manage_privacy_options` for the privacy policy page, or a capability another plugin adds to `edit_post` or `publish_post`), the answer is refused, so a draft privacy policy page cannot be edited or published by an agent. The status-to-capability decision is in one place, `MetaCaps::edit_capability()`, which `UpdatePost` also uses.

Where Steadhand refuses edit, publish or delete on an attachment, or edit on a status it does not map, it returns the capability name `steadhand_no_grant` rather than `do_not_allow`. Core's `read_post` check, for a post that is neither public, private nor the agent's own, returns the answer it gets for `edit_post`, so a `do_not_allow` there would also refuse reads of such a post. The name `steadhand_no_grant` is held by no user, so it refuses in the same way without that side effect.
