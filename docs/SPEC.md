# Steadhand — Product & Technical Spec

**Status:** Draft v0.3 (2026-11-21)
**Owner:** MAKR Holdings LLC
**Repo:** `makr-holdings/steadhand`: the free plugin, private during development, made public at the WordPress.org launch. Pro (M5) will be a separate add-on plugin in its own private repo; see §9.1.

> Display name: **Steadhand – Secure AI Agent Access for WordPress**
> Slug / text domain: `steadhand` · PHP namespace: `Steadhand\` · Prefix: `steadhand_` / `STEADHAND_`

---

## 1. What Steadhand is

Steadhand lets AI agents (Claude, ChatGPT, Cursor, any MCP client) work on a WordPress site **safely**: each agent gets only the permissions it needs, known-dangerous writes are blocked or fixed before they land, and every action is logged and can be undone.

It is **not** an AI plugin. Steadhand never calls an LLM, stores no AI provider keys, and adds no chatbot or content generator. It is an access and governance layer. The AI lives in the client.

### Why it exists
- Existing WordPress MCP plugins tend to give an agent a single, never-expiring token with **admin** rights. One leaked token means full site compromise.
- Agents keep making the same site-breaking mistakes: writing JSON into PHP-serialized options, using color slugs that break block validation, overwriting widget and sidebar options. Today the only defense is instructions in a prompt file. Steadhand enforces them in code.
- Site owners can't currently see which agent did what, or easily roll it back.

### Positioning
"The safe one." Built by a security consultancy and used on its own sites first. Least privilege, guardrails and an audit trail are the product, not add-ons.

## 2. Goals and non-goals

**Goals (v1)**
1. Expose a focused, well-described set of WordPress tools over MCP, built on core's Abilities API and the official MCP Adapter.
2. Least privilege by default: a dedicated agent user and role, per-tool-group capabilities, nothing admin-level unless deliberately granted.
3. Enforce guardrails against known site-breaking writes.
4. Log every agent action with enough detail to audit it and undo it.
5. Pass WordPress.org review and Plugin Check on the first submission.

**Non-goals (v1)**
- Generating content, images or embeddings, or calling any AI provider.
- Installing, activating or updating plugins or themes; editing theme or plugin files; running PHP or SQL; managing users. These may never ship, and if they do, it will be Pro-only behind approvals.
- Replacing a full security plugin (firewall, malware scanning, login hardening).
- WooCommerce-specific tools (possible later add-on).

## 3. Architecture

```
MCP client (Claude, etc.)
   │  HTTPS + WordPress Application Password (Basic auth)
   ▼
MCP Adapter (official plugin): transport, protocol, errors
   │  custom server "steadhand" (explicit tool list)
   ▼
Steadhand
   ├─ Transport gate: the request user must hold `steadhand_connect`
   ├─ Abilities (steadhand/*): schema-validated input → permission check → guardrails → log reservation → execute → log completion (writes); permission check → execute → log (reads)
   ├─ Guardrail engine: rules evaluated before any write
   ├─ Change log + snapshots: audit trail and undo
   └─ Admin UI: agents, permissions, guardrails, log
```

### 3.1 Dependencies
- **WordPress 6.9+** (Abilities API in core). Target: tested against the current release (7.1.x).
- **MCP Adapter, required as a separate plugin** (decided, D1). Declared with the `Requires Plugins:` header so WordPress installs and enforces it. Not bundled, which avoids version conflicts with other plugins that bundle it. Its confirmed WordPress.org slug is `mcp-adapter` (0.7.2 at time of writing).
- **PHP 8.1+** (decided, D2).

### 3.2 MCP server
- Steadhand registers its **own** server on `mcp_adapter_init` using `$adapter->create_server(...)`, with an **explicit tool list**. Agents see each tool directly in `tools/list` with its full schema, with no discover/execute indirection through the default server.
- Server ID `steadhand`, REST namespace `steadhand`, route `mcp`, so the endpoint is `/wp-json/steadhand/mcp`.
- The **transport permission callback** checks the request user's own resolved capabilities directly (`WP_User::$allcaps`, role defaults merged with user-level overrides) for `steadhand_connect`. It does not call `current_user_can()`: on multisite that returns true for super admins for any capability, and `user_has_cap` filters from other plugins could grant Steadhand capabilities. Steadhand access must only ever come from a deliberate grant. Every Steadhand capability check works this way. Admins do *not* get this capability automatically. Only users deliberately set up as agents connect. The request user must also be a dedicated agent, meaning `steadhand_agent` is its only role (`Agents::is_agent()`, D14). Trade-off: a `user_has_cap` filter that revokes capabilities (for example a security plugin's lockdown mode) is not honoured by this check, so to cut off an agent, revoke its capability or its application password instead.
- **Refusal codes over MCP.** The MCP Adapter sends only the text and `isError` of a tool result, so a `WP_Error`'s code and HTTP status never reach the client. At the ability boundary, `Registry::with_code()` appends ` (<code>)` to the message of each refusal or failure that Steadhand returns, in the permission and execute callbacks, so the text ends with the code (for example `(steadhand_forbidden)`). The suffix is added for any caller of those callbacks, not only MCP. The HTTP status is not sent to the client. The change log is written before the callback returns, so its `message` has no suffix. Some refusals and failures carry no code, and none is changed: core's input-schema refusal (`ability_invalid_input`), core's output-schema failure, core's own permission error when its second check fails (`ability_invalid_permissions`), errors the MCP Adapter raises itself, and the refusals of `Lockdown`.
- **Exception text.** Steadhand never returns an exception's message to the agent, and never stores it. A throw during the permission stage is refused with `steadhand_error` (500) and the fixed text "The permission check could not be completed, so the call was refused. Another plugin or the site raised an error during the check. Ask the site administrator.", and it is logged as `blocked` (§3.3). A throw during the revalidation of a guardrail's fix is refused as `steadhand_guardrail_blocked` (422, "A guardrail changed this call into one that is not allowed, so it was refused.") and logged as `blocked`. A throw that escapes the pipeline altogether is turned by the outer belt in `Registry` into the generic text, "The ability failed to complete. Try again, or check the site error log." (`steadhand_error`, 500) for a read or a permission check, or into "The change could not be completed and may have been partly applied. Check the result before you continue." (`steadhand_error`, 500) for the execute callback of a write. That is not logged. The MCP Adapter would otherwise pass the exception text to the client as the tool's error text.
- The lockdown (§4.1) is registered by `Plugin::boot()` before its requirements check, so it holds when the MCP Adapter or the Abilities API is missing.
- Steadhand's abilities are **not** marked `meta.public = true`, so they don't leak into the adapter's default server or other consumers. They are exposed only through the Steadhand server. Abilities also set `meta.mcp.public = false` and `show_in_rest = false` explicitly.

### 3.3 Abilities
- Category `steadhand`, registered on `wp_abilities_api_categories_init`. Abilities are registered on `wp_abilities_api_init`. (If the category isn't registered, the ability fails *silently* when `WP_DEBUG` is off. Add a self-check in the admin UI.)
- Naming: `steadhand/<verb>-<noun>`, e.g. `steadhand/get-post`, `steadhand/update-post`.
- Each ability declares: `label`, a **description written for an LLM** (what it does, when to use it, what it will refuse), `input_schema`, `output_schema`, `permission_callback`, `execute_callback`, and MCP annotations (`readonly`, `destructive`, `idempotent`).
- Every `execute_callback` runs through one shared pipeline. A read runs **validate → authorize → execute → log**. A write runs **validate → authorize → guardrails → log reservation → snapshot → execute → log completion** (§7). A write whose log row cannot be reserved is not performed. No ability writes to the database outside that pipeline. A throw from the permission stage fails closed. That covers `prepare()` and `authorize()` in `check()` and `run()`, including a `map_meta_cap` or `user_has_cap` filter from another plugin that throws (a PHP `\Error` included), and an ability's own input or object check that throws. The call is refused with `steadhand_error` (500) and the fixed text "The permission check could not be completed, so the call was refused. Another plugin or the site raised an error during the check. Ask the site administrator.", and it is logged once as `blocked` with that same message. A refused call is not counted toward the rate limits. Nothing runs after such a throw. An input rule (`validate_input()`) that returns `false`, which is neither `true` nor a `WP_Error`, is refused the same way as a `WP_Error` from it, with `steadhand_invalid_input` (400, "The input was refused.") and nothing run. A throw that escapes the pipeline altogether is turned by the `Registry` callbacks into the generic `steadhand_error` (500, "The ability failed to complete. Try again, or check the site error log.") for a read or a permission check, or into the "may have been partly applied" text (500, `steadhand_error`) for the execute callback of a write, and that one is not logged, because the pipeline could not log it. An exception message is never returned to the caller or written to the change log.

## 4. Identity, authentication, permissions

### 4.1 Agent users
- Admins create **agent users** from Steadhand's admin screen. Each gets the custom role `steadhand_agent`, which has *no* native WordPress capabilities beyond `read`, plus Steadhand capabilities.
- Agents authenticate with **WordPress core Application Passwords**: no custom token scheme, revocable per password, and stored hashed by core.
- The **application password's name is the agent label** ("Claude Desktop – Rick", "Ops agent", and so on). It appears in the log, so you can tell agents apart even under the same user.
- **Dedicated agents:** only a user whose sole role is `steadhand_agent` is an agent (D14). A user who also holds another role (a *mixed-role* user) is not an agent, and it cannot connect to Steadhand.
- **Lockdown (M1):** Steadhand refuses agent credentials everywhere except the Steadhand endpoint, by four mechanisms (`includes/Lockdown.php`, which states each rule in a table in its class docblock). The rules are registered before the requirements check (§3.2). The table below gives what each rule does to a dedicated agent and to a mixed-role user:
  - *Password sign-in* (`authenticate`): a dedicated agent's password sign-in is refused, whether through wp-login.php, `wp_signon()` or XML-RPC. A mixed-role user's Application Password sign-in is refused too (it works nowhere, as the identity rule says), but its account-password sign-in is not affected.
  - *Identity* (`determine_current_user`): a dedicated agent is the current user only when it authenticated with its own Application Password, on a REST request whose route is the Steadhand endpoint. Anywhere else it resolves to no user, so the request is treated as not logged in. A mixed-role user whose request carries its own Application Password resolves to no user everywhere. Cookie sessions of a mixed-role user are not affected.
  - *REST routes* (`rest_pre_dispatch`, and a second check on `rest_request_before_callbacks`): a dedicated agent may reach only the Steadhand endpoint. On any other route, its Application Password makes the request anonymous (identity rule above), so core answers as it would to a logged-out visitor. If the request still carries the agent as its user, every other route gets 403, including `/batch/v1` sub-requests and the MCP Adapter's default server. A mixed-role user whose request carries an Application Password gets 403 on every route except the Steadhand endpoint, where the transport gate refuses it. The second check runs for every matched request, after all `rest_pre_dispatch` filters, so a later filter cannot lift the first. A callback added at the same priority on `rest_request_before_callbacks` after Steadhand boots can still undo the second check (see `docs/HOOKS.md`).
  - *wp-admin* (`admin_init`): a dedicated agent that reaches wp-admin, admin-ajax.php or admin-post.php gets 403. Mixed-role users are not affected, so a human administrator given the agent role keeps wp-admin.
  - *Limits:* the lockdown runs only while Steadhand is active and loadable. If Steadhand is deactivated, or cannot load (PHP older than 8.1, or a source checkout without its autoloader), agent users and their Application Passwords still exist and work as ordinary low-privilege WordPress accounts on core REST and wp-login until they are revoked. Uninstalling revokes them. To take a site out of service safely, revoke the agents' Application Passwords first, or uninstall rather than deactivate.
  - *Do not give the agent role to a person's account.* That account's Application Passwords stop working everywhere (see the mixed-role rule above).
- Optional IP allowlist per agent user: in Free, off by default (decided, D3).
- **The Agents screen (M3).** Under Steadhand, **Agents** (`includes/Admin/AgentsScreen.php` for the screen, `includes/Admin/AgentsHandler.php` for its actions) creates an agent, adds or revokes its Application Passwords, and sets its capabilities. *Create* takes a username, which must match `^[a-z0-9][a-z0-9_-]{0,59}$` exactly and not exist, and the label of its first Application Password. A label is 1 to 60 characters, counted as Unicode code points (`mb_strlen()`), on one line. It must be valid UTF-8 with no control, format or line- or paragraph-separator characters (`\p{Cc}`, `\p{Cf}`, `\p{Zl}`, `\p{Zp}`, so no tab, newline, NUL, right-to-left override, zero-width space or byte-order mark), it may not start or end with a space or other separator character (`\p{Z}`, which includes the no-break space), and it may contain no markup. A value that would be changed is refused, not fixed. Because `user_login` has no unique index, two requests can both pass the existence check. So after the insert the exact login is counted, and if it is held twice, the request deletes the user it made and refuses (`username_taken`). A role that is not registered is refused up front (`role_missing`), since WordPress would otherwise create a user with no role. The agent gets the `steadhand_agent` role with `Capabilities::agent_defaults()` and nothing else. The email is left empty, because `wp_insert_user()` does not require one. The password is 64 random characters that nobody sees, since Lockdown refuses password sign-in for an agent anyway. The steps after the insert run in this order, and any refusal among them is undone by the rollback below: the exact login is counted; the user is checked; the Application Password is made; `steadhand_agent_created` fires; the user is checked again. A throw from a listener in any of these steps is caught, and the create is refused the same way (no exception reaches the screen).
  - **Rollback (create).** A refused create undoes what it wrote, in this order: (1) every Application Password of the user is revoked; (2) the posts (by `post_author`) and links (by `link_owner`) attributed to the user are counted, after the revoke, and a count that cannot be read counts as content; (3) if nothing is attributed, the user is deleted with core's `wp_delete_user()`, and the delete is checked; (4) otherwise, or when the delete fails, every role and capability is removed from the user, and that is checked. Core's delete also deletes attributed content (attachments with their files, custom post types), so Steadhand never calls it while content is attributed to the user. The refusal's code is `create_failed` (or the code of the check that failed) when the user was deleted. When the user is kept, the code is `create_failed_user_kept`: the user has no role, no capability and no password, and its notice tells the administrator to remove it on the Users screen. When any step failed (a revoke, the delete or the strip), the code is `create_failed_cleanup`, and its notice names the login for the administrator to check on the Users screen. No rollback result carries a password. If a listener throws before the user's ID is known (before the row is written), nothing is deleted, and a login that exists is reported as `create_failed_cleanup`.
  - **Result codes added with the rollback and the checks.** `extra_role`: the new user holds another role or stores another capability (any value), so another plugin added it. `create_failed_user_kept` and `create_failed_cleanup` (above). `revoke_failed`: a revoke, single or all, did not finish, so the password may still work. `capabilities_unverified`: the capabilities were written, and the user is then no longer a dedicated agent. `password_failed` now means only that core did not save the password, with nothing left behind. A password made by a request whose step then threw is revoked by its UUID, and the result is `password_failed`, or `revoke_failed` if that revoke fails.
  - **Verification after each write (create).** After the user is inserted, it is read again with its cache cleared. It must hold nothing but the agent role: its roles are exactly `steadhand_agent` (`Agents::is_agent()`), its stored capability map (`wp_capabilities`) has exactly one key, `steadhand_agent`, set to true, and its login is the posted one (a `pre_user_login` filter can rewrite it). Nothing else may be stored: not another role, not a capability, not one set to false. After the Application Password is made, the user is read again and must pass the same check. A mismatch refuses, and the rollback above undoes the request's writes. No password is returned in that case. The user is removed unless content is attributed to it, in which case it is kept with no role and no password, and the screen says so (`create_failed_user_kept`). The stored capability check is strict: a user that stores any extra capability, even one set to false, or a role name that is not registered, fails it, because it is stored in the caps but is not a role.
  - **Add password.** *Add* refuses a label the agent already uses (case-insensitively) and the eleventh password (at most 10 per agent). After the write, the target must still be a dedicated agent, and the list must still hold at most 10 passwords with that label at most once. Two requests can pass the limits together, so a failed re-check revokes the password this request made and refuses (`not_agent`, `too_many_passwords` or `label_taken`). If that revoke fails, the result is `revoke_failed`, because the password may still work.
  - **Set capabilities.** The target is read again just before the writes and again after them, and must be a dedicated agent both times. A check that fails before the writes refuses with `not_agent` and writes nothing. A check that fails after them refuses with `capabilities_unverified`, whose notice says the capabilities were saved but grant nothing, because the user is no longer a dedicated agent (every Steadhand gate requires one). A read-back that does not match refuses with `capabilities_mismatch`. A listener that throws during the writes, or a missing user after them, gives `capabilities_failed`, whose notice says the capabilities could not be confirmed.
  - *Revoke* removes one password by its UUID, which must be well formed and belong to that agent, or all of them. A revoke that fails, or a listener that throws during it, gives `revoke_failed`, and the password is reported as possibly still working.
  - Every action is a POST with a nonce bound to the action name and the target user ID. It is refused, with nothing changed, unless the caller passes the nonce, holds `manage_options` and `list_users`, holds no agent role, and holds the native WordPress capability for the act: `create_users` to create, and `edit_user` for the target to change anything. The checks run in that order, after the nonce check the site must not be a multisite network. On multisite every action returns the `multisite` code without any effect, and the screen shows only the notice "Agent management is not available on multisite networks.", with no forms and no list (D13).
  - A target must be a dedicated agent (`Agents::is_agent()`). An administrator, an editor, a mixed-role user (one that holds the agent role and another role), a user ID that does not exist and ID 0 are all refused, so no Steadhand capability or password can reach an account that is not an agent. No action gives the agent role to an existing user.
  - The list shows each agent's login, its capabilities, its Application Passwords (name, created, last used, last IP, never the hash) and a link to its change-log entries. A mixed-role user is listed with a warning and no forms. Forms are shown only to a viewer who passes `edit_user` for that agent, and the create form only to a viewer with `create_users`.
  - Application Passwords need HTTPS (`wp_is_application_passwords_available()`). Without them the screen says so, and it offers no create or add form.
  - Extension points: `steadhand_agent_created`, `steadhand_agent_capabilities_changed` and `steadhand_admin_agent_row` (`docs/HOOKS.md`).
- **The one-time password.** *Create* and *add password* answer their own POST: the screen shows the new password, with the username, the MCP endpoint and the sentence "This password is shown once. Copy it now. It cannot be shown again.", in that one response, and they do not redirect. A GET of the screen does not show it. Steadhand stores the password nowhere (core keeps only its hash), and it is never in a URL, an option, a transient, user meta, a log or the arguments of a Steadhand hook. Core's own `wp_create_application_password` action receives the plaintext, as it does for every Application Password. Steadhand listens to that action and to `wp_set_password` only during a create or add request, and only to read a user ID and a UUID from them, never the password. Their listeners are removed when the request ends. *Revoke* and *set capabilities* redirect with a fixed result code, which the screen turns into one fixed notice. The screen reads from the URL only the codes a redirect can carry (`AgentsHandler::REDIRECT_CODES`). The codes of the one-time panel, `created` and `password_added`, are shown only in the response to their own POST, never from a URL.

### 4.2 Capabilities (tool groups)
Each tool belongs to a group. Each group is a capability the admin toggles per agent user:

| Capability | Tools | Default for a new agent |
|---|---|---|
| `steadhand_connect` | can reach the server at all | on |
| `steadhand_read` | site info, posts/pages (any status except trash), blocks, terms, menus, media lists, diagnostics, the agent's own change log | on |
| `steadhand_write_drafts` | create posts (always as `draft`); edit posts of any author while they are `draft`, `pending` or `auto-draft`, including their blocks; may set `draft` to `pending`; never publish, schedule or make private; never change the author | on |
| `steadhand_publish` | edit published, scheduled or private posts; set those statuses | **off** |
| `steadhand_media` | upload media and set featured image (built in M2). An uploaded file is public at once, at its uploads URL, even without `steadhand_publish` (§5). Editing the alt text and captions of existing media is not built yet | off |
| `steadhand_menus` | edit navigation menus | off |
| `steadhand_trash` | move to trash and restore (never permanent delete) | off |
| `steadhand_settings` | read/write **allowlisted** options only (site title, tagline, and similar) | off |

Publishing a draft needs both `steadhand_write_drafts` (to edit the draft) and `steadhand_publish` (to set the live status). Editing a live post needs `steadhand_publish` only (`update-post` and `edit-blocks` also need `steadhand_read` to read the post they edit). Moving a live post back to draft needs `steadhand_publish`. `create-post` with any status other than `draft`, including `pending`, needs `steadhand_publish`.

`set-post-terms` needs `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` by the post's status, as `update-post` does. A taxonomy whose own assign capability is not core's default also needs that capability (D21).

User-level capabilities override the role defaults, and a user-level deny overrides a capability the role grants.

**Capabilities on the Agents screen (§4.1).** The screen offers `steadhand_connect` and every Steadhand capability that a registered ability uses (`Registry::capabilities_used()`, which reads each ability's `capability()` and `capabilities_any()`). Today that is `steadhand_connect`, `steadhand_read`, `steadhand_write_drafts`, `steadhand_publish` and `steadhand_media`. `steadhand_menus`, `steadhand_trash` and `steadhand_settings` are not offered until a tool needs them, and any stored value of one of them is left exactly as it is. The form posts the full set of checked boxes. Only offered names in the request are read; every other name, including `steadhand_no_grant`, `manage_options`, `edit_posts` and `administrator`, is ignored. Each offered capability is saved as an explicit true or false with `add_cap()`, so the stored user-level value is what the screen shows, and it is read back with `Capabilities::user_has()` and must match. Turning on `steadhand_publish` or `steadhand_media` changes the public site, and the screen says so.

Each ability's `permission_callback` checks **both** the Steadhand capability **and** the native WordPress check for the specific object (e.g. `edit_post` for *this* post ID), carried out by a `map_meta_cap` filter. The `read_post` mapping applies while a Steadhand pipeline request is running, and `edit_post` and `publish_post` apply only during a write call (§14.1). The `steadhand_agent` role never holds WordPress's general editing capabilities (see §14.1). Defense in depth: neither check alone is enough.

**Exception: `create-post`.** `create-post` has no object yet, so there is no post for WordPress's object check (`edit_post`) to check. It is guarded by the Steadhand capabilities and the allowed post types only. This is an explicit exception to the two-layer rule.

**Capability guard.** `includes/CapabilityGuard.php` filters `user_has_cap` at priority `PHP_INT_MAX`, registered in `Plugin::boot()` before the requirements check. For every Steadhand capability (`Capabilities::all()`), the answer is the value stored for the user, read by `Capabilities::user_has()`. `Capabilities::NO_GRANT` (`steadhand_no_grant`) is in no user and is always false. So no `user_has_cap` filter can grant a Steadhand capability, and none can remove one. Other capabilities are not touched, so a filter may still change core's answers for an administrator. "The value stored for the user" means the user's capabilities as WordPress loaded them. Code that runs inside the site and rewrites those values is trusted, as the site's own administrator is.

## 5. Tool catalog (v1)

Read (`readonly: true`):
- `get-site-info`: name, URL, WordPress/PHP versions, active theme, Steadhand version, what this agent is allowed to do.
- `list-posts` / `get-post`: allowed post types only (`post` and `page` by default, extendable through the `steadhand_allowed_post_types` filter; fixed exclusions in §14.1), with filters (status, type, search, date), paged. Built in M1 as follows:
  - `list-posts` takes `status` as a set of `publish`, `future`, `draft`, `pending` and `private`. `trash`, `auto-draft`, `inherit` and `any` are refused. It also takes `search` (up to 200 characters), `after` and `before` (ISO 8601 date-times, read as instants, so a value without an offset is UTC; compared with the post date in the site's time zone, which also covers drafts whose GMT date is zero), `orderby` (`date`, `modified` or `title`), `order`, `page` (1 to 10000) and `per_page` (1 to 50, default 20). It returns `items`, `total`, `total_pages`, `page` and `per_page`. A page past the end is empty, not an error. An item's excerpt is plain text of about 55 words.
  - `get-post` returns the raw `post_content` as stored, with its excerpt, comment and ping status, menu order, page template, featured media ID and sticky flag. Neither tool returns post meta (meta comes later, behind an allowlist), the password, or anything about users beyond the author's display name. Trashed, missing and disallowed IDs get the same refusal text.
  - Content over 256 KB (`MAX_CONTENT_BYTES`) is cut on a UTF-8 boundary, with `truncated: true` and `content_bytes` giving the full size.
- `get-blocks`: the parsed block tree of a post. Each node has `path`, `name` (`null` for freeform HTML), `attrs` (always a JSON object), `inner_html` and `inner_blocks`. A path is a dot-separated index: `0` is the first block, `1.0` the first block inside the second. Indexes count the nodes at each level, and whitespace-only freeform nodes between blocks are not counted, so a path names the same block while the content is unchanged. Truncation only drops trailing nodes, so a kept node's path is the same with or without the limits. Later edit tools use the same walker and the same paths. Limits: 2000 nodes and 20 levels (beyond either, `truncated: true`), and at most 256 KB of `inner_html` and `attrs` together.
- `get-rendered`: the HTML the content produces through the front end's `the_content` filters, as a fragment. The site's own blocks and shortcodes run, so their output appears. It is not a full page, and it runs no theme template. While the post renders, Steadhand blocks every request made through the WordPress HTTP API, every oEmbed fetch and discovery, and every oEmbed cache write (`_oembed_*` post meta, and `oembed_cache` posts), so an embed appears as its plain URL. It omits the blocks whose output is data the agent cannot read directly: `core/loginout` (a logout URL with a nonce); every `core/avatar` block with or without a `userId` (an `isLink` avatar wraps its empty image in a link to the user's author archive, which names the user); `core/navigation` with a `ref` that is not a published `wp_navigation` post; every `core/legacy-widget` (a stored widget with an `id` prints its settings, and a media gallery widget calls the gallery directly, past the shortcode guard); any block with a binding whose source is `core/post-meta` (the read tools return no post meta; a malformed `metadata` or `bindings` value counts as no bindings); `core/breadcrumbs` (the title and link of every ancestor, with no status check); `core/post-author-biography` (the author's biography); `core/post-author` when `showBio` or `isLink` is set; `core/post-author-name` when `isLink` is set (the author archive link); and `core/video` with an `id` unless that attachment is one the agent may read, because its width and height come from the attachment's metadata. A `core/video` without an `id` renders as stored. `core/navigation-link` and `core/navigation-submenu` with a binding whose source is `core/post-data` or `core/term-data` are omitted too: those sources read the block's own `id` and return the link or date of that post or term under core's rule, not Steadhand's. Other blocks that use `core/post-data` for the current post (for example `core/post-date`) are not affected. The omission has two layers. The first runs before a block renders (`pre_render_block`). Core's `navigation`, `navigation-submenu`, `navigation-link` and `widget-group` blocks render their inner blocks by calling `render()` directly, which skips the first layer, so a second layer (`render_block`, applied to each block's output) drops a guarded block's output inside them. The limit: on the second layer the block's own render code still runs, and only its output is dropped. Both layers are attached at the highest priority, so a callback at a lower priority cannot undo them. All avatar images are omitted wherever they come from (a shortcode, or another plugin): while the post renders, `get_avatar()` returns an empty string, including on the early `pre_get_avatar` path and through the `get_avatar` filter, and `get_avatar_data()` yields no URL, so no Gravatar hash of anyone's email address is printed. The plain author name of `core/post-author` and `core/post-author-name` is not omitted: it is already part of the tool's output. Third-party shortcodes and blocks may still have side effects of their own, and they run with the agent's read grant. Output printed by shortcodes is discarded. Core's `[gallery]` and `[playlist]` shortcodes render as nothing when they would list media that `get-media` refuses, or the children of a post that `get-post` refuses: each attachment named by `ids` or `include` must pass the media rule, and the post named by `id` (or the current post, when there is no `id`) must be readable. `[audio]`, `[video]` and `[caption]` take no attachment ID from their attributes; they use only the children of the current post (the post being rendered, or the post of a query loop), which the agent can read. A rendering error returns a generic message, never the exception text. The caller's global post is restored afterwards. Password-protected posts render their real content, and the password form is not included. The ability is annotated `readonly`.
- `list-terms` / `get-post-terms`: built in M1 as follows:
  - Taxonomies: a taxonomy is readable only when it is public, is attached to at least one allowed post type (§14.1), and is not one of the fixed exclusions `nav_menu`, `link_category`, `wp_theme`, `wp_template_part_area` or `wp_pattern_category`. There is no separate filter, so `steadhand_allowed_post_types` also decides which taxonomies agents may read. By default that is `category` and `post_tag`, with `post_format` (public and attached to `post`) and any public custom taxonomy attached to `post` or `page`.
  - `list-terms` takes `taxonomy` (required), `search` (up to 200 characters, matched against names and slugs), `parent` (0 for top-level terms only), `orderby` (`name`, `count` or `id`), `order`, `page` (1 to 10000) and `per_page` (1 to 100, default 50). It returns `items`, `total`, `total_pages`, `page` and `per_page`, with the total from a count query. Terms with no posts are included. A description is plain text, cut at 2000 bytes on a UTF-8 boundary.
  - `get-post-terms` takes a post `id`, read by the rule `get-post` uses. It returns the allowed taxonomies its type uses, grouped, with their terms. Each taxonomy returns at most 500 terms (`TermReader::MAX_TERMS_PER_TAXONOMY`), in name order, fetched with the query's own limit. Each entry also has `total`, the number of the post's terms in that taxonomy, counted in the database, and `truncated`, true when `total` is above 500. Terms of any other taxonomy are never returned.
- `list-menus` / `get-menu`: both kinds of menu are readable, and only through these tools, because the post and term tools exclude their types:
  - Classic menus (terms in `nav_menu`, items in `nav_menu_item`) and block navigation (`wp_navigation` posts). `list-menus` lists classic menus first, with their `item_count` and theme locations, then block navigation in the statuses `MenuReader::BLOCK_STATUSES`: `publish`, `draft`, `pending`, `future` and `private`. `get-menu` reads block navigation in exactly the same statuses, from the same constant. Trashed and auto-draft navigation is never listed or read. The list is capped at 200 menus, and `truncated` is set when more exist. A classic `item_count` is the count WordPress stores on the menu term (`count`), so it is not a count of loaded items, and it can include an item that `get-menu` leaves out.
  - `get-menu` takes `kind` (`classic` or `block`) and `id`. A classic menu loads the whole menu and returns a flat list of at most 500 items in menu order (`truncated` when there are more), each with its parent item ID, type, linked object type and ID, title and URL. The title is plain text, tags removed, entities decoded, cut at 1000 bytes. The URL and title are those the public menu prints. Items whose linked object is trashed or missing are left out. A linked object may be a draft, a private post or a type the post tools refuse. Only its type, its ID, and the item's title and URL are returned. A block navigation post returns its raw content (cut at 256 KB, as `get-post` does) and its block tree, with the same paths as `get-blocks`.
  - Neither kind returns users, post meta, or anything about a linked object beyond the title and URL that the menu itself shows.
- `list-media` / `get-media`: built in M1 as follows:
  - `list-media` takes `media_type` (`image`, `video`, `audio`, `application` or `text`, matched against the top-level MIME type), `search` (up to 200 characters), `parent` (0 for unattached media only, or the ID of a post the agent may read through the post rule; any other parent, including a trashed, missing or attachment ID, refuses the call with the standard text), `after` and `before` (ISO 8601 date-times, checked as real calendar dates, compared with the post date in the site's time zone), `orderby` (`date` or `title`), `order`, `page` (1 to 10000) and `per_page` (1 to 50, default 20). It returns `items`, `total`, `total_pages`, `page` and `per_page`. The query names the `inherit` status only, and it also applies the media rule's parent condition in SQL (a join on the parent's primary key), so `total` and the pages count only the rows the rule keeps. Each row is checked again. A page past the end is empty.
  - `get-media` takes `id` and returns the list fields: `id`, `title`, `slug`, `mime_type`, `media_type`, `url` (the public URL of the file), `alt`, `caption`, `date_gmt`, `modified_gmt`, `author` (`id` and display name), `parent` (the parent post ID, or 0), `width` and `height` (images and videos, from metadata, otherwise null), `filesize` (from metadata when stored, otherwise null; the file is never read from disk) and `duration` (seconds, for audio and video, otherwise null). It adds `description` (the content as plain text, cut at 5000 bytes on a UTF-8 boundary, with `truncated`) and `sizes` (the generated image sizes, at most 30, each with `name`, `url`, `width`, `height` and `mime_type`; an empty array for non-images).
  - Never returned: server file paths (`file`, `_wp_attached_file`, upload directories; only URLs), raw attachment metadata, `image_meta` (EXIF, IPTC and GPS fields such as camera, location, author and copyright), any post meta except the alt text, and user email or login.
  - The media rule (`MediaReader::within_rule()`): an attachment is listed and readable only when its own status is exactly `inherit` and its parent passes `MediaReader::parent_permits()`. That holds when the parent is 0, when the parent post no longer exists, or when the parent is of an allowed post type (`PostTypes::is_allowed()`) and is not in the trash. The parent's status is otherwise irrelevant (a draft, pending, private, future or published parent is fine), and so is its author. A private-status attachment, or one under a trashed post, a `wp_block`, a draft `wp_navigation`, or a private post of a registered type that is not allowed, is refused with the standard text by get-media and is neither listed nor counted by list-media. The parent's ID is returned; nothing else about the parent is.
  - `get-media` returns `url` as '' when `_wp_attached_file` is empty, blank or the falsy value `0` (core would fall back to the post GUID, which can be any stored string), when it is an absolute path (a leading slash, a backslash, or a Windows drive letter: core would embed that server path in the URL), and when core's URL is the post GUID but does not end with the stored file's name. Other hosts are not checked, because offloaded media uses them. Size URLs are the URL of the original with each size's own file name (`basename()` of the stored file), so `sizes` never holds a path.
  - Metadata is clamped, not trusted. A non-finite or negative `duration` is null. `width`, `height` and `filesize` are null unless they are positive integers, and dimensions are at most 1000000. A generated size whose name or MIME type is over 100 characters, or whose file name is empty, is skipped. A MIME type over 100 characters is cut to 100 and its `media_type` is ''; a malformed MIME type (not type/subtype of token characters) gives a `media_type` of ''. `title`, `alt` and `caption` are plain text, cut at 1000 bytes.
- `get-diagnostics`: built in M1 as follows. It takes `max_errors` (1 to 50, default 20) and nothing else: no path, URL or option name. It returns seven sections: `environment`; `theme`; `plugins` (active plugins by name and version, at most 100; update status comes only from the existing `update_plugins` transient, and no check is run); `php_errors`; `cron` (overdue counts and hook names, read from the stored option without writing it; hook arguments are never returned); `site_health` (the counts already stored in the `health-check-site-status-result` transient; no Site Health test is run); and `steadhand`, a self-check against core's ability registry, the MCP Adapter's server registry, the lockdown hooks, and whether the change-log table exists (`change_log_ready`). `php_errors` reads only the last 256 KB of the log that `WP_DEBUG_LOG` names. It never reads the server-wide `error_log` or any other file, and it refuses a symlink or a path outside `WP_CONTENT_DIR` or `ABSPATH` unless the owner configured that exact path. It keeps only standard PHP engine error lines, and skips and counts everything else, including stack traces and free-form `error_log()` output. Messages go through `Steadhand\Redactor`, which is best-effort (see §10). Site directories are removed from messages and every other absolute path in a message is reduced to its file name; a stack trace is cut at its first frame, so no call argument is returned; the database user and host in a connection error are masked. The `file` field is relative to the site, never holds a `..` segment or a leading slash, and is reduced to its base name otherwise. Identical entries are counted once, and the newest `max_errors` items are returned. The ability writes nothing and makes no outbound request: every HTTP request is blocked for the duration of the call by a guard that is removed in `finally`. Before any filesystem call, a `WP_DEBUG_LOG` value that core would not read as a plain path (a stream-wrapper or URL scheme, a relative path, a NUL byte) is refused, and so is any real path under `/proc`, `/sys` or `/dev`. The values core reads as the default log (`true`, `1`, `'1'`, `'true'`) mean `wp-content/debug.log`.
- `get-change-log`: built in M2 as follows. It shows the calling agent's own change-log entries (see §7).
  - Inputs: `page` (1 to 10000, default 1); `per_page` (1 to 50, default 20); `result` (`ok`, `blocked`, `fixed` or `error`); `ability` (a Steadhand ability name: `steadhand/` followed by up to 80 lowercase letters, digits or hyphens); `after` and `before` (ISO 8601 date-times, inclusive; read as instants, so a value without an offset is UTC). Any other argument is refused.
  - Output: `items`, `total`, `total_pages`, `page` and `per_page`. Each item has `id`, `created_at` (ISO 8601, UTC), `ability`, `object_type`, `object_id`, `result`, `message`, `guardrail_notes`, `undoable` and `undone`. `undone` is true when `undo-change` has undone the entry (its `undone_by` is above 0), and false otherwise. A page past the end is empty, not an error.
  - Own entries only. The query is bound to the calling user's ID, and no argument can widen it. Another agent's entries are never returned.
  - Never returns the stored `input` of a call.
  - Successful calls to this ability are not logged. Its refusals and failures are.
  - If the change-log table is missing, the ability itself returns `steadhand_log_unavailable` (503). Through the pipeline, though, the failed call is logged, that write fails too, and the caller receives `steadhand_log_failed` (see the known gaps in §7).

- `create-post` and `update-post`: built in M2 as follows. Both are writes, so they run the guardrails and the change log (§6, §7).
  - `create-post` takes `title`, `content`, `excerpt`, `slug`, `status`, `date` and `post_type`. The author is always the calling agent. `status` defaults to `draft` and may be `draft`, `pending`, `publish`, `future` or `private`. Any status other than `draft`, pending included, needs `steadhand_publish`; without it the call is refused. `date` (ISO 8601, read as UTC without an offset) is allowed only with status `future`, where it is required, and must be at least 60 seconds and at most 10 years ahead. `post_type` must be an allowed type (`post` and `page` by default). Title or content must be non-empty.
  - `update-post` takes `id` and at least one of `title`, `content`, `excerpt`, `slug`, `status` and `date`, with the same limits and status rules. It changes only the fields sent, and only where they differ from what is stored. `content` replaces the whole content; partial edits belong to `edit-blocks` (below). The post's type, author, password and parent cannot be changed.
  - Limits: title 400 characters, excerpt 5,000, slug 200 (lowercase letters, digits and single hyphens), content 262,144 characters and 256 KB in bytes (the content guardrail).
  - Output (both): `id`, `post_type`, `status`, `title`, `slug`, `link`, `modified`, `changed` (whether the write changed anything), `content_modified_on_save` (true when WordPress stored a title, content or excerpt that differs from what was sent, for example after KSES), `warnings` and `guardrail_notes`. `modified` is the last-modified time in UTC. When WordPress stores the GMT date as zero, as it does for a new draft, it falls back to the local modified date; the same fallback applies to `modified_gmt` in the post and media tools.
  - Refusals: a status other than `draft` without `steadhand_publish` (403); a post the caller may not edit, including one that is missing, trashed, of a type that is not allowed, or not readable, all with one text (403, `steadhand_forbidden`, at the permission check). If the post stops being accessible after that check, `update-post` refuses with the same text, code and status (`steadhand_forbidden`, 403) from its own re-check or from PostWriter's last re-check, and nothing is written (§14.1). `create-post` has no existing post to re-check, and a type that is not allowed is refused with `steadhand_forbidden` (403); a live status on a post the caller may not publish (403); invalid input, including a misplaced or out-of-range date, and a title and content that are both empty (400, `steadhand_invalid_input`); a guardrail block (422, `steadhand_guardrail_blocked`); a write whose row cannot be reserved (500, `steadhand_log_failed`, not performed); a write whose outcome cannot be recorded afterwards (500, `steadhand_log_incomplete`; the change was made). Added to `update-post` in review: `steadhand_refused_invalid_template` (409), for a post whose page template the active theme does not have, refused before any write; `steadhand_update_partial` (500), when WordPress reports an error after it has changed the post, or when a field the call did not send is changed after the write; `steadhand_update_failed` (500, "nothing was changed"), only when the post did not change. A caller who can read a published, scheduled or private post, and lacks `steadhand_publish`, gets the publish-needed refusal from the object check (see §14.1), not the generic one.
  - Not supported in M2: post meta (D18). No write tool accepts meta keys, and no allowlist is defined.
  - Post date: a write sets the post date only when a date is sent. WordPress gives a draft with no set date the time it is published, so publishing an old draft does not backdate it. A scheduled update keeps the requested date.
  - Warnings for values WordPress stores differently: `Making a post private removes its password.` when a post with a password is made private; `WordPress stored the status "<stored>" instead of "<requested>".` when WordPress stores another status. Both tools return the status warning. A publish with a future date is stored as `future`, so `update-post` cannot publish a scheduled post early. `This site keeps too few revisions for Steadhand to undo this change.` when the site keeps one revision or none (see §7).
  - Known limits of `update-post`: `wp_update_post()` re-normalises some values that an administrator stored in an unusual way, by a direct database write, whatever fields the call sends. An empty `comment_status` on an update becomes `closed`. A non-canonical slug is sanitised. A post with no category gains the default category when its type is `post`. `to_ping` is sanitised. Steadhand does not restore these values. The title, content, excerpt and filtered content it does not send are kept byte for byte, as described above.
  - Unsent fields and save filters: WordPress's `wp_update_post()` saves every stored field again, not only the fields a call sends. The four post-field KSES filters are in place for the whole write, for every field, as they are on create, and no Steadhand code removes a KSES filter or the Global Styles filter. So code that runs during the save (a `save_post` listener, a revision insert, a nested write) is filtered too. To keep the fields a call does not send byte for byte, `update-post` records their stored values (title, content, excerpt and filtered content) before the write. A `wp_insert_post_data` filter at `PHP_INT_MAX` then sets each one back, slashed as core expects, after the save filters have run. It acts only on this post's own update (the update flag, the ID and the stored post type must match), only once (it disarms on its first match, so a nested update of the same post is filtered as usual), and it is removed in `finally`. The fields the call sends keep the value the KSES filters compute. After the write, `update-post` reads each unsent field again. If one differs from the value stored before the write, the error is `steadhand_update_partial`, not a success. Remaining limit: code that changes the row after `wp_insert_post_data`, at the same priority or a later one, or that writes the table directly, can still change an unsent field. Steadhand reports that as `steadhand_update_partial`; it does not prevent it. See §14.1.
  - Execute failure: for `update-post`, when WordPress reports an error, or the write throws, the post is read again, uncached. If it changed, the error is `steadhand_update_partial` (500): "The post was changed, but the save did not finish as expected, so the change was at least partly applied. Check the post before you continue." The same error and message are returned when a field the call did not send differs from what was stored, after a write that reported no error. If it did not change, the error is `steadhand_update_failed` (500): "WordPress could not update the post, so nothing was changed. Try again." For `create-post`, a WP_Error from `wp_insert_post()` is returned before the row is written (for example `db_insert_error`), so its message says nothing was saved. The one core error that comes after the row is written, `invalid_page_template`, needs a `page_template` value, which `create-post` never sends. For any other write, when its execute step throws, the call fails with `steadhand_error` and the message "The change could not be completed and may have been partly applied. Check the result before you continue." The read path's message is unchanged.
  - Post fields and KSES: on create, every post-field KSES filter is in place for the save, so everything the agent sends is filtered. On update, the same four are in place for the whole write, for every field (added where they are missing, and removed afterwards only if this call added them). A filter another component added stays. Steadhand never removes a KSES or Global Styles filter during a write, and never calls `kses_init_filters()` or `kses_remove_filters()`. The fields an update does not send are put back by the restore described above.
- `edit-blocks`: built in M2 as follows. It changes some blocks of one existing post or page, by path, without resending the whole content. It is a write, so it runs the guardrails and the change log (§6, §7).
  - Inputs: `id`, and `operations`, one to 20 objects. Each has `op`: `replace` (the block at `path` becomes `markup`), `insert_before` or `insert_after` (`markup` is added next to the block at `path`), `remove` (the block at `path` is deleted), or `append` (`markup` is added at the end of the content). Every op except `append` takes `path` (a dot-separated index, as `get-blocks` returns it, at most 100 bytes and 20 levels) and `name` (the block name `get-blocks` returned at that path, or `null` for classic HTML, at most 200 bytes). `append` takes neither. `markup` is required except for `remove`, which takes none. It must not be blank, must be valid UTF-8, and is block markup or classic HTML.
  - Semantics: every path refers to the content as stored before the call, not to the content after the other operations, so the order of the operations does not change the result. A path may be named once, and no path may lie inside a block another operation names. Paths are the ones `get-blocks` gives. The edits are byte splices: everything outside the edited spans is kept byte for byte. Inserted and appended markup gets one `\n\n` between it and an adjacent piece of content, only where neither side of that boundary is whitespace. Replacement markup gets no separator. Replacing or removing a root classic-HTML node replaces the whole gap, including the whitespace around it.
  - Name check: an operation whose `path` names no block, or a block with another name, is refused. A stale path therefore cannot edit a different block that now sits at the same index.
  - Reused from `update-post`: the object check and the permissions (`steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` as for `update-post`), the revision rule, the template refusal, the partial-failure errors (`steadhand_update_partial`, `steadhand_update_failed`), `warnings`, `changed` and the output fields. `edit-blocks` delegates the write to `update-post`, so every rule `update-post` has applies. The write itself is `PostWriter::splice()`, which stores the kept bytes as they are and filters the sent runs (see the storage rule below).
  - Storage rule (decided by Rick, 2026-11-23): bytes the call does not send are stored exactly as they are, and are not passed through the save filters. Only the markup the call sends, and the separators Steadhand adds next to it, are filtered, and each run of adjacent sent text is filtered once, as one piece (`PostWriter::assemble()`). The filters are the ones a save runs on `post_content`: the KSES filter; the custom CSS strip, which removes the `css` in a block's `style` attribute (where WordPress has the strip, from WordPress 7.0; Steadhand then puts it in place for every write, at core's priority 8, also for an agent user that holds `edit_css`, which core would not do); the invalid entity conversion (`&#128;` becomes `&#8364;`); tag balancing, when the `use_balanceTags` option is on; the emoji step, on a utf8 or utf8mb3 column; and any filter a plugin adds to `pre_post_content` or `content_save_pre`. The filtered result is what is stored. The call still succeeds, with `content_modified_on_save` true and a warning that WordPress changed part of the markup sent. The guardrails see exactly the bytes that will be stored. A call whose new content equals the stored content writes nothing.
  - Complete blocks, per operation: the markup an operation sends must be complete blocks on its own. Every block it opens is closed in the same markup, and it closes no block it did not open. Otherwise the call is refused with `steadhand_invalid_input` (400). After filtering, each run of sent text must still be complete blocks, or the call is refused with `steadhand_refused_unsupported_markup` (409): the markup does not stay complete blocks once WordPress has filtered it.
  - Open HTML before a sent run: the content before each sent run is read with `WP_HTML_Tag_Processor` (WordPress 6.5 and later; this plugin needs 6.9, so the method is always there). If the HTML is left open there (an unterminated `script`, `style`, `textarea`, `title`, `xmp`, `iframe`, comment, tag or attribute value), the call is refused with `steadhand_refused_unsupported_markup` (409). The stored content is not changed, and the message says a person must fix the post in the block editor. A closed `<script>` in a block before the edit is not refused.
  - Structure of the result: the content the segments produce must be complete blocks that agree with core (the same check `apply` uses on the stored content). Every stored block the edit keeps must still be there, with the same name at its new offset; a block whose whole span is kept must keep its length. Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409). A block that is replaced or removed, or that lies inside one, is not checked.
  - Split delimiters (token alignment): the block delimiters of the final content are checked against the stored bytes and the sent runs. Every delimiter of the final content must lie wholly inside one kept range or one sent run. The delimiters inside each kept range must be exactly the stored delimiters that lie wholly inside it, with the same offsets and bytes, and no stored delimiter may be cut by a kept range's edge. The delimiters inside each sent run must be exactly the ones core finds when it reads that run alone. A sent run that leaves HTML open (an unclosed script, textarea or comment) is refused when stored content follows it, with the same code and a message of its own. Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409): the markup would form a block that neither is on its own. This stops a delimiter completed across two places, or one that is only whole once bytes from outside a run are joined to it (`BlockEditor::aligned()`).
  - No stray HTML comments: in each operation's markup (`steadhand_invalid_input`, 400), and again in each sent run after filtering (`steadhand_refused_unsupported_markup`, 409), every `<!--` must start a block delimiter, or be a break comment inside its break block. `<!--more…-->` (including `<!--more-->` with custom text) and `<!--noteaser-->` are allowed only as the content of a `core/more` block; `<!--nextpage-->` only as the content of a `core/nextpage` block. Every `-->` must lie inside a block delimiter or one of those comments. A bare break comment is refused, because core removes a break comment when it displays content, so bytes that were not adjacent at save time would become adjacent. The 400 message says to use the `core/more` or `core/nextpage` block for a break. Ordinary HTML comments such as `<!-- note -->` cannot be sent. Stored ones, in bytes the call does not send, are kept as they are, bare break comments included.
  - Preview check: the guardrails see the content as it will be stored. The guard records the SHA-256 of the content it returns to the guardrails. The plan refuses, with `steadhand_update_failed` (500), unless its own preview has that hash, and the write refuses when the content it assembles differs from the plan's preview. So nothing is written that the guardrails did not see. A call with no recorded hash (the per-operation fallback) is refused the same way.
  - A call that would leave the post with no title, no excerpt and no content is refused before the write with `steadhand_invalid_input` (400).
  - Joins over removed content: where two kept ranges are not contiguous, because the call removes the content between them, the stored bytes before the join must not leave HTML open (the check a sent run gets). Otherwise the call is refused with `steadhand_refused_unsupported_markup` (409): the stored content leaves HTML open where the edit removes the content between two of its parts. A remove-only call is checked this way too.
  - Break comments: a break comment (`<!--more-->`, `<!--more text-->`, `<!--noteaser-->` or `<!--nextpage-->`) is allowed only as the sole inner content of its owner block. `more` and `noteaser` need a `core/more` block, whose inner content must match `<!--more( [^>\n]*)?-->(\s*<!--noteaser-->)?`. `nextpage` needs a `core/nextpage` block, whose inner content must be `<!--nextpage-->`. Anywhere else it is refused: `steadhand_invalid_input` (400) in the sent markup, or `steadhand_refused_unsupported_markup` (409) in the sent run after filtering.
  - Display-time `more` split: WordPress shows a post by cutting its content at a `<!-- wp:more` delimiter (`get_the_content()`). The pattern Steadhand checks is `BlockEditor::DISPLAY_MORE`, copied from core. The check runs on the whole result, not only on sent runs: every match in the final content must be exactly one whole delimiter token, or lie wholly inside one kept range and be byte-identical to a match of the stored content at the offset that range maps to. Anything else would make WordPress drop stored bytes when it shows the post, so it is refused with `steadhand_refused_unsupported_markup` (409): "This edit would make WordPress drop part of the content when it shows the post, so nothing was changed. If you sent a core/more block, send it with its opening and closing comments, not as a self-closing block." The raw markup of each operation is checked the same way first (`steadhand_invalid_input`, 400: "The markup of operation N would make WordPress drop part of the content when it shows the post..."). A PCRE failure in either check refuses the call.
  - Known limits of the storage rule: stored bytes are kept as they are. Stored HTML that is closed but malformed, or that core reads differently from the tag processor, is kept and not reported. A plugin that changes the post during the save is reported by `content_modified_on_save`, not prevented. The filters run on the sent markup more than once per call (for the preview and for the save), with the same result each time.
  - Guardrails: they see the whole resulting content as `content`. When the operations cannot be applied, they see each operation's markup as `operations.<n>.markup`, so the rules still judge what was sent. Nothing is written in that case. The guardrails run before the checks below, so a markup the rules refuse gets a 422 even when its path would also be refused.
  - Refusals, all with nothing written: `steadhand_refused_unsupported_markup` (409: Steadhand cannot read the block structure the way WordPress does; use `update-post` with the complete content); `steadhand_refused_block_mismatch` (409: a path names no block with that name; call `get-blocks` again); `steadhand_refused_content_changed` (409: the post changed between the guardrail check and the write; call `get-blocks` again); `steadhand_refused_unsupported_markup` (409, from the complete-blocks, open-HTML and structure checks above; each has its own message). Shape errors are `steadhand_invalid_input` (400): the operation count, the fields each op takes or refuses, the path and name grammar, blank or missing markup, a path sent twice, and a path inside another named block. A guardrail block is `steadhand_guardrail_blocked` (422), as for `update-post`. A post the caller may not access is refused at the permission check with `steadhand_forbidden` (403). If it stops being accessible before the write, `edit-blocks` refuses with the same text, code and status (`steadhand_forbidden`, 403) from its own re-check or from PostWriter's last re-check, and nothing is written (§14.1).
  - Log: each call keeps the `op`, `path` and `name` of each operation. Each operation's markup is stored as a digest, not as text (§7). A refusal raised while the write is prepared (snapshot or execute) is logged with result `error`. A guardrail or input refusal is logged as `blocked`.
  - Limits: a post whose resulting content is over the content limits (§6.1: 2,000 blocks, 20 levels, 256 KB) cannot be edited with this tool, even for a small change. The tool cannot add the first child of an empty container block, because that block has no path: it replaces the container instead.
- `set-post-terms`: built in M2 as follows. It is a write, so it runs the guardrails and the change log (§6, §7).
  - Inputs: `id`; `taxonomy` (lowercase letters, digits, `_` and `-`, at most 32 characters); `terms`, an array of up to 100 distinct term IDs (positive integers, from `list-terms` or `get-post-terms`; it may be empty); and `mode`: `replace` (the default: the post's terms in the taxonomy become exactly `terms`), `add` (the current terms and `terms`) or `remove` (the current terms without `terms`). Names and slugs are refused by the schema. The tool never creates, renames or deletes a term.
  - Rules, all checked before a write and again immediately before it: the post must pass `update-post`'s object check, and its post type must register meta mapping (`map_meta_cap` true). The taxonomy must be allowed (§5, §14.1) and attached to the post's type. Every term ID must be a term of that taxonomy. A call may leave the post with at most 100 terms in the taxonomy only when it does not add terms: a `remove` from a post that already has more is allowed, and an `add` or `replace` that would take it over 100 is refused. A post format takes at most one term. A post that already has more than 500 terms in the taxonomy is refused until a person reduces them. Terms are written only when the final set differs from the current one.
  - Lost updates: the final set is computed from the terms read at the start of the call. Immediately before the write, the assigned IDs are read again; if they differ, nothing is written (`steadhand_refused_content_changed`). The post is read again before the write too, and the permission check runs on that fresh copy, so a status change made during the call (for example a publish) is refused.
  - Permissions: `steadhand_read` (to read the post), and `steadhand_write_drafts` for a draft, pending or auto-draft post, or `steadhand_publish` for a published, scheduled or private post, as `update-post` does. A taxonomy whose own assign capability is not core's default also needs that capability, held by the caller (D21). Steadhand never grants that capability, and adds no mapping to MetaCaps.
  - Refusals, all with nothing changed: a taxonomy that is not allowed, or not attached to the post's type (400, `steadhand_invalid_input`; the allowed taxonomies for the post's type are listed only when the caller may read the post; for a missing or unreadable post the refusal is `steadhand_forbidden`); a term ID that is not a term of the taxonomy, a repeated ID, two post formats, or a call that adds terms and leaves more than 100 (400, `steadhand_invalid_input`); a post that is missing, trashed, of a type that is not allowed, unreadable, not editable by the caller, or of a type that does not register meta mapping (403, `steadhand_forbidden`, one text, at the permission check; the one exception is a readable published, scheduled or private post when the caller lacks `steadhand_publish`, which gets the publish-needed text, §14.1). If that post stops being accessible after the check, `set-post-terms` refuses with the same text, code and status (`steadhand_forbidden`, 403) from its own re-check or from TermWriter's last re-check, and nothing is written (§14.1); a taxonomy whose assign capability the caller does not hold (403, `steadhand_forbidden`); the terms changing while the call runs (409, `steadhand_refused_content_changed`); a post someone is editing in the block editor, and the rate limit (422, `steadhand_guardrail_blocked`); more than 500 terms already in the taxonomy (409, `steadhand_refused_too_many_terms`). A schema violation (more than 100 IDs, repeats, a string, an extra property) is refused before any rule runs.
  - Refusal logging: refusals of the input and the permission check are logged as `blocked`. Refusals made at execute time, because they depend on the state of the post (the 500-term guard, the 100-term cap, the one-format rule, a change made during the call), are logged as `error`.
  - Output: `id`, `taxonomy`, `term_ids` (the result, ascending, at most 500), `terms` (`id`, `name`, `slug` and `parent`, in name order, at most 500), `previous_term_ids` (the IDs before the call, ascending), `changed`, `link` (the permalink after the call), `warnings` and `guardrail_notes`. `previous_term_ids` is what a caller uses to put the terms back. `link` is empty when WordPress cannot give the post a permalink.
  - Warnings: when `changed` is true and the state before the call could not be saved, "Steadhand could not save the state before this change, so it cannot be undone." When a published post's permalink changes, "This change moved the post to a new address. WordPress does not redirect the old one." (a permalink follows the categories with `%category%`). For a `post` that ends with no category, "WordPress gives a post with no category the default category the next time the post is saved."
  - Undo (M3). `snapshot()` saves the post's term IDs in the taxonomy before the call, as a row of `{prefix}steadhand_snapshots` (kind `post_terms`, state `{"taxonomy", "term_ids"}`, the IDs ascending and unique). `snapshot_after()` saves the state the call stored, and returns its row ID only when the output's `changed` is exactly true and the IDs the call reported as `previous_term_ids` equal the saved before IDs (as sets). Otherwise it returns 0, the call is not undoable, and the pipeline adds "Steadhand could not save the state after this change, so it cannot be undone." A call with `changed` false is not undoable and gets no warning; its before row is never used and is left for the prune job (§7). A post with more than 100 terms in the taxonomy before the call is not saved, because an undo could never put back more than 100, and the change is not undoable: "Steadhand cannot undo this change: the post had more than 100 terms in this taxonomy before it, and an undo can put back at most 100." A call whose before state cannot be saved (the snapshots table is not ready, or the state is over 16 KB) still succeeds, is not undoable, and carries the warning above. A call refused after its snapshot leaves its before row the same way. Undo is `undo-change` (§5), which puts the set back under its own rules.
  - Failures: `steadhand_update_partial` (500, "The terms were changed, but not as asked … Call steadhand/get-post-terms to check the post before you continue."), when WordPress reports an error from the write and the terms changed or cannot be read, when the terms cannot be read back after the write, or when the terms after the write are not the ones asked for (for example after a `set_object_terms` listener changed them). `steadhand_update_failed` (500, "WordPress could not set the terms, so nothing was changed. Try again."), when WordPress reports an error from the write and the terms did not change. A refusal made by the writer before any write is returned as it was, never as one of these two.
  - Known limits: `save_post` does not run, and the post's modified date does not change, so plugins that listen only to `save_post` (caches, search indexes, sitemaps) are not told. On a taxonomy registered with `sort`, the term order is rewritten, and `previous_term_ids` cannot restore it. WordPress's `wp_set_object_terms()` does no capability check of its own, so the checks above are Steadhand's. A taxonomy registered with its default capabilities is refused on a post type whose edit capability is not the one it assigns (for example a page, or a type with its own capabilities). That is the safe direction, and it is stated in the tool's description. A taxonomy whose assign capability is a meta capability is checked by WordPress with no term, which WordPress reports as an incorrect-usage notice. The call is still refused for an agent that does not hold it; Steadhand cannot detect that case precisely without core's internals. A new post may already hold the default category, so `previous_term_ids` can contain it. The compare and the write are not atomic. `TermWriter` reads the terms again just before its write and refuses (`steadhand_refused_content_changed`) when they differ from the set the call computed from. A change made by another request in the gap between that read and the write is overwritten by the full replace, and no error is reported for it: the read-back compares only the set stored after the write. The same gap applies to `undo-change`. Two calls that overlap in time can leave a post with more than 100 terms, because the comparison and the write are not atomic: the later call usually reports `steadhand_update_partial`, and further adds are then refused. `link` is empty when WordPress cannot give the post a permalink, and then no moved-address warning is given. The moved-address warning is given for published posts only.
- `upload-media` and `set-featured-image`: built in M2 as follows. Both are writes, so they run the guardrails and the change log (§6, §7). Media is written only by `Steadhand\Pipeline\MediaWriter`, the one place that creates an attachment or sets a featured image.
  - `upload-media` (base64 only; it does not fetch from a URL, see D22). Inputs: `filename` (1 to 200 characters, required), `data_base64` (required, at most 7,200,000 characters), `title` (at most 200), `alt` (at most 1,000), `caption` (at most 1,000) and `parent` (an integer of 0 or more, default 0). The schema is strict: no other property. `data_base64` must be standard base64 with padding and nothing else: no whitespace, no line break, no `data:` prefix, and a length that is a multiple of 4. The decoded image is 1 byte to 5 MB (5,242,880 bytes). Its type is read from its bytes and must be JPEG or PNG, a fixed list that no filter changes. GIF, WebP and SVG are refused, and so is an animated PNG. WebP is not accepted at all: a WebP whose VP8X canvas differs from its frame passes the header and container checks, and makes PHP's GD raise a fatal error when core decodes it. Each side is 1 to 8,000 pixels and the image has at most 16,000,000 pixels. The file name must be exactly one base name of 1 to 80 letters, digits, `_` and `-` (the first a letter or digit), then one dot and `jpg`, `jpeg` or `png` in any case; the extension is stored in lower case. The name must be what `sanitize_file_name()` returns unchanged, so spaces, accents, bidi and zero-width characters, a path, a second dot, a leading dash or dot, and a Windows device name as the base name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`) are all refused. The name's extension must match the type (`jpg` or `jpeg` for JPEG, and so on). Core's sideload stores the file under an explicit allowlist of the same two types. `title` defaults to the file name without its extension; `alt` and `caption` are plain text.
  - Checks, in this order, all before anything is written: the name rule; base64; the size; the bytes must not contain `<?php` in any case (a best-effort check, see below) (refused as "the file contains PHP code"); the header's type and the extension; the pixel limits; the container: a PNG is refused when it holds an `acTL` chunk. A PNG container that cannot be walked to its end (a chunk whose length runs past the end of the file, with the length read as unsigned, so a length that a 32-bit build would read as negative is malformed too; or no `IEND`) is malformed and refused. The `<?php` check is defence in depth, not a guarantee: other embedded text is stored as sent. What keeps a stored file from running as code is that its name always ends in `.jpg`, `.jpeg` or `.png` and its detected type is an image. No `<?=` check is made: in compressed image data a three-byte sequence occurs by chance far too often. A JPEG with more than 50 start-of-scan markers (`FF DA`) is refused, so a progressive-scan bomb is not decoded. The readers are `ImageFormat`; each stays inside the string it is given and stops after 4,096 chunks.
  - The memory check runs in `UploadMedia::validate_input()`, before the log row is reserved, so a too-large image is logged `blocked` and does not count toward the daily cap. `MediaWriter` runs the same check again, before the file is written and before core touches it, as a second layer. A decode needs about 8 bytes for each pixel, so the check refuses when `width × height × 8`, plus the memory the request already uses, plus 64 MB, is more than the limit core would raise to for images. That limit is `wp_convert_hr_to_bytes( apply_filters( 'image_memory_limit', WP_MAX_MEMORY_LIMIT ) )` as core's `wp_raise_memory_limit( 'image' )` ends up with it: core never lowers the limit, so a filter value below `WP_MAX_MEMORY_LIMIT` has no effect, and a PHP limit of -1 means there is no memory check, and only the pixel limits apply. The check does not apply to Imagick, whose memory is not counted against PHP's limit.
  - Steadhand does not decode the image itself. Core decodes it when it makes the sizes, and more than once for a large or rotated image, so the header checks above are the only checks Steadhand makes before core's first decode. An image whose metadata has no width or height is refused and its file and row are removed. After core stores the file, its type must be in the allowlist, its extension must be allowed, `wp_get_image_mime()` of the stored file must equal the type checked, and its real path must be inside the uploads directory, and its SHA-256 must be the payload's; otherwise nothing is kept (`steadhand_error`). The parent check runs again just before the row is made. On a fatal error during the write, Steadhand removes the files and the row from WordPress's fatal error handler: it hooks `wp_php_error_args`, which core applies immediately before it calls `wp_die()`. A shutdown function is the fallback, which also covers a site with `WP_DISABLE_FATAL_ERROR_HANDLER`. The cleanup removes the temporary file; the stored file only when its SHA-256 is the payload's; the generated sizes, and the copy core made when it scaled or rotated the image, when they are in the uploads directory and in the stored file's directory; and the row. WordPress's own deletion may remove only those files. If PHP runs out of memory the cleanup itself can fail, and then a file and an attachment row without metadata can remain. That is a known limit. Sizes core wrote before a fatal error, which the metadata does not yet list, are not known to the cleanup and can also remain.
  - Temporary file: created exclusively (`fopen` with `xb`), so an existing path is never written to or followed, with mode 0600. A name that is taken is tried again with a new random part, at most five times.
  - Daily cap: at most 100 uploads per agent in any rolling 24 hours (`DailyUploadLimit`, a guardrail rule, `LIMIT` 100). It counts the change log's `ok`, `fixed` and `error` rows for `steadhand/upload-media` (`DbLogger::count_recent()`), so a write that failed or crashed still counts. The count is read before the write's row is reserved, so calls that arrive at the same moment can pass together: the cap is best effort under concurrent requests. A refusal is the rate limit's refusal: 422, `steadhand_guardrail_blocked`, logged `blocked`. If the count cannot be read, the upload is refused.
  - Public at once: an uploaded file is public from the moment it is stored. WordPress serves it at its uploads URL, and on its attachment page where the site has one. This does not need `steadhand_publish`, which governs posts. Granting `steadhand_media` accepts this.
  - Permissions: `steadhand_media` and `steadhand_read`. An optional `parent` must pass `update-post`'s object check: it must be readable, of an allowed type, and editable by its status (`steadhand_write_drafts` for a draft, `steadhand_publish` for a live post).
  - Refusals, all with nothing stored (no file and no row): no `steadhand_media` (403); no `steadhand_read` (403, `steadhand_forbidden`); bad base64, a bad header, a file name outside the rule, a `<?php` tag, a size, type, extension, pixel, animation, malformed-container or scan limit (400, `steadhand_invalid_input`), refused at validation and logged `blocked`; a parent that is missing, trashed, of a type that is not allowed, an attachment, or not editable (403, `steadhand_forbidden`, one text; the one exception is a readable published, scheduled or private parent when the caller lacks `steadhand_publish`, which gets the parent publish-needed text, §14.1); a parent that stops being accessible after the permission check and before the write is refused with the same text, code and status (`steadhand_forbidden`, 403) and nothing stored, whether the ability's re-check finds it after the guardrails or MediaWriter's last re-check finds it (logged `error` in the second case, because it is found at the write; §14.1); the memory limit (400, `steadhand_invalid_input`, logged `blocked`, found at validation before the row is reserved); an image that core cannot process, found from its metadata at the write (400, `steadhand_invalid_input`, logged `error`); a stored file that is not what was checked (500, `steadhand_error`, logged `error`); the per-minute rate limit or the daily cap (422, `steadhand_guardrail_blocked`, logged `blocked`).
  - Output: the `get-media` fields of the new attachment (the same formatter), plus `warnings` and `guardrail_notes`. The warning says Steadhand cannot undo an upload yet. Not undoable: the snapshot is 0 and `undoable` is 0. If the new attachment cannot be read back, the error is `steadhand_update_partial` (500), because the file exists.
  - Log: `data_base64` is stored as the digest of its decoded bytes (`{"bytes", "sha256"}`), or, when the text does not decode, as the digest of the text sent. The payload is not stored on any path, including the schema refusal, the permission refusal and the guardrail refusal (`log_input()` is applied to the input as sent, before any check). Other text over 1,000 bytes is stored as a digest, and any input key that is not a field is stored as a digest. The object is `attachment`: ID 0 before the write, the new ID after it.
  - Known limits: EXIF and other image metadata, including a GPS position, and any other text in the file, are stored as sent. The only text refused inside the bytes is `<?php`, so other polyglot content is stored as sent. There is no malware scan. Only images are accepted. Not undoable until M3. Core makes the intermediate sizes, which takes time and disk. Core decodes each image in memory when it makes the sizes, so an image near the pixel limit can need more memory than a small host allows; the memory check refuses it before core decodes it, except under Imagick, which the check does not cover. An image core cannot process is refused where core reports an error (no width or height in its metadata). A decoder fatal error is handled by the cleanup above. Imagick was not tested: the test environment falls back to GD, so its behaviour on these files is not known. An image with a sound header and container whose pixel data is damaged is stored. Core's metadata reports the size from the header, and the only check that would catch the damage is a decode of Steadhand's own, which it does not make. Bad base64 and a bad header are refused at validation and logged `blocked`; only an image that core cannot process, found at the write, is logged `error`.
  - `set-featured-image` takes `id` (the post) and `media_id` (an attachment ID, or 0 to remove the featured image). Both are required and no other property is allowed. The post must pass `update-post`'s object check, and its type must support a featured image (`thumbnail`). A `media_id` above 0 must pass `MediaReader::readable_attachment()` (the media rule and `read_post`) and be an image (`wp_attachment_is_image()`). Permissions: `steadhand_media`, `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` by the post's status, as `update-post` requires. The edit lock and the rate limit apply, as for `set-post-terms`. The write goes through `MediaWriter::set_featured_image()`, which reads the thumbnail again, runs the permission check again on the post, and refuses with `steadhand_refused_content_changed` (409) when the stored thumbnail is not the one the call read. Asking for the image the post already has writes nothing and returns `changed` false.
  - Output: `id`, `featured_media` (after the call), `previous_featured_media`, `changed`, `link`, `warnings` and `guardrail_notes`. Warnings: when `changed` is true and the state before the call could not be saved (the snapshots table is not ready, or the state is over 16 KB), "Steadhand could not save the state before this change, so it cannot be undone." Undo (M3), as for `set-post-terms`: `snapshot()` saves `{featured_media}` before the call (kind `featured_image`), and `snapshot_after()` saves the stored image after it, only when `changed` is exactly true and the saved before image equals `previous_featured_media`. Otherwise the call is not undoable and the pipeline's after warning applies. `previous_featured_media` holds the image the post had before. Annotations: not readonly, destructive (it replaces the image the post had), idempotent (the same call twice leaves the same image).
  - Refusals, all with nothing written: a post that is missing, trashed, of a type that is not allowed, or not editable (403, `steadhand_forbidden`, one text, at the permission check; the one exception is a readable published, scheduled or private post when the caller lacks `steadhand_publish`, which gets the publish-needed text, §14.1). That text takes precedence when `media_id` names no attachment or one the caller cannot read, so granting `steadhand_publish` is necessary but may not be sufficient. A `media_id` that is readable but not an image is refused first, with the 400 text below. Failures: `steadhand_update_partial` (500) when the stored thumbnail after the write is not the one asked for; `steadhand_update_failed` (500, nothing changed) when the write failed and the stored thumbnail did not change.
  - Known limits: `save_post` does not run and the modified date does not change, so plugins that listen only to `save_post` are not told. The compare and the write are not atomic, as for `set-post-terms`: a change by another request in the gap between `MediaWriter`'s read and its write is overwritten, without an error.

- `undo-change`: built in M3 as follows. It reverses one change this agent made with `update-post`, `edit-blocks`, `set-post-terms` or `set-featured-image`, named by its change-log entry. It is a write, so it runs the rate limit, the edit lock and the change log (§6, §7).
  - Input: `id`, the change-log entry ID that `get-change-log` returns (1 to 2147483647). Any other argument is refused.
  - Output: `entry_id`, `object_type` (`post`), `object_id`, `undone` (true), `link`, `warnings` and `guardrail_notes`. For a terms undo, `warnings` are the warnings the direct `set-post-terms` call with the same set gives (`SetPostTerms::result_warnings()`: a moved permalink for a published post, and a post left with no category). The before-state warning of set-post-terms does not apply, because an undo is never undoable. For post text and the featured image, `warnings` is empty.
  - Principle, for terms and the featured image. An undo of `set-post-terms` or `set-featured-image` is exactly a call the agent could make itself. It runs, under the agent's rights now, every permission and input rule that a direct call by this agent would run: for terms, `set-post-terms` in replace mode with the before term IDs; for the image, `set-featured-image` with the before attachment, or removal when the post had none. It also checks that the post still holds the state the change left. So it gives the agent nothing it could not already do. Unlike post text, it has no newest-change-only rule. Its writes go through `TermWriter` and `MediaWriter` only. The guardrails see the same direct call as well: the undo is evaluated first as `steadhand/undo-change`, then as the direct call it amounts to, with the same input and no content for post text (`Ability::equivalent_call()`, and docs/HOOKS.md, "An undo is evaluated twice"). So a rule that limits the direct call limits the undo, and a rewrite of that call refuses the undo. The direct call is determined from the saved states at that moment, and if it cannot be (a read fails, or the entry is not usable), the undo is refused. Its digest is kept, and the undo writes only if the direct call built again just before the write is the same; otherwise it is refused as changed, and nothing is written.
  - What it restores, by kind. Post text (`update-post`, `edit-blocks`): the title, content and excerpt, to the text of the entry's before-revision (`snapshot_id`), as described below. Terms (`set-post-terms`): the set of term IDs the post had before the change, in the taxonomy the change named. Featured image (`set-featured-image`): the image the post had before, or none.
  - For post text: the title, content and excerpt, to the text of the entry's before-revision (`snapshot_id`). It does this only when the post's title, content and excerpt still equal the entry's after-revision (`after_snapshot_id`), and when no revision of the post was created after that after-revision. "Created after" is decided by creation order, the revision ID, never by date: a revision's date is site-local time and can move with a clock or time-zone change. The check is a direct query on the posts table that excludes autosaves by core's own rule (a `post_name` containing `{parent}-autosave`, as `wp_is_post_autosave()` decides it). A failed query refuses.
  - The restore is a WordPress save of those three fields only. The save is WordPress's own, as it is for `update-post`: the modified date changes, `save_post` runs, and the other stored fields are saved as they are stored, with the normalisations `update-post` documents (see its known limits above). Status, slug, date and author are not sent.
  - Which entries it can undo: only the calling agent's own entries, from `update-post` or `edit-blocks`, with result `ok` or `fixed`, `undoable` 1, `undone_by` 0, and a before-snapshot and an after-snapshot that differ from each other. In practice that is the agent's newest change to a post (post text only, see below). For terms and the featured image, both saved states must be rows of `{prefix}steadhand_snapshots` with the expected kind, whose `object_type` is `post` and `object_id` the entry's post, and whose `user_id` is the entry's user. Each must decode to exactly the expected shape: terms, `taxonomy` (a string) and `term_ids` (a list of distinct positive integers, at most 100), both naming the same taxonomy, and the two sets different; the image, `featured_media` (an integer of 0 or more), and the two images different. Any other state is refused as not undoable. After an undo, its older changes to that post cannot be undone, because the restore saves a newer revision.
  - Permissions: `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` decided by the post's status, exactly as `update-post` decides them. The object check is `update-post`'s own rule for that post, applied now. For terms and the featured image the caller must also hold one of the capabilities of the ability that made the entry (`steadhand_write_drafts` or `steadhand_publish` for terms, `steadhand_media` for the image). The pipeline accepts any one of the union of the three abilities' capabilities, so this is checked again by `UndoChange` itself, in its object check and again before the write. The undo then runs that ability's own input rule and object check on the equivalent input, and for an image other than 0 it requires the attachment to still exist and be an image the caller can read.
  - Refusals for terms and the featured image, all with nothing changed and the entry not marked: the terms or image changed since the change (`steadhand_refused_changed_since`, 409, "The post's terms were changed after that change, so it cannot be undone. Nothing was changed.", or the featured-image text), from the writer's compare made just before the write; a saved state that is missing, damaged, or names another post, user, kind or taxonomy (`steadhand_refused_not_undoable`, 409, "This change has no saved state that Steadhand can restore, so it cannot be undone. Nothing was changed."); what the saved state names that is no longer usable for this post, such as a term that was deleted, a media file that is no longer an image, a taxonomy that is no longer attached to the post's type, or a post that can no longer hold the state, and a post with more than 500 terms in the taxonomy (`steadhand_refused_not_undoable`, 409, "Steadhand cannot undo this change, because the state it would restore is no longer valid: a term or image it names is missing or not usable, or the post can no longer hold it. Nothing was changed."); the generic refusal (`steadhand_forbidden`, "Not found, or this agent may not access it.") when the object check refuses the restore: an image that was deleted or that the caller can no longer read under the media rule, a taxonomy whose assign capability the caller no longer holds, or a post type that is no longer allowed. A deleted image gets the generic text because the object check refuses it there, without a check of its own; a deleted term is found by the input rule and gets the not-undoable text. These are the same checks a direct call runs, so a direct call would refuse the same way; a post published since the change, for a caller without `steadhand_publish`, which gets the publish-needed text that `set-post-terms` and `set-featured-image` give; the capability and the input rules of the underlying call (generic text, or its own refusal for a missing `steadhand_read`). The rate limit and the edit lock apply as for post text.
  - Refusals, all with nothing changed and the entry not marked: another agent's entry, and an ID that does not exist, both give `steadhand_forbidden` (403) with the generic text "Not found, or this agent may not access it.", so an ID cannot be probed. For the caller's own entry: an entry already undone (`steadhand_forbidden`, "This change has already been undone, so it cannot be undone again."); an entry that is not undoable, is not from one of the four abilities above, or was not made (`steadhand_forbidden`, "Steadhand cannot undo this change. ..."); a post that needs `steadhand_publish` for the caller, with the publish-needed text `update-post` gives (`steadhand_forbidden`). A missing, trashed or not editable post gives the generic text. A before- or after-revision that is missing, belongs to another post, is an autosave, or holds the same text as the other; or revisions that are switched off now, or that the site keeps fewer than two of (`steadhand_refused_not_undoable`, 409, "This change has no saved state that Steadhand can restore, so it cannot be undone. Nothing was changed."). A post whose title, content or excerpt no longer equal the after-state, or that has a revision created after the change, including one with the same text (`steadhand_refused_changed_since`, 409). A post whose page template the active theme no longer has (`steadhand_refused_invalid_template`, 409, refused before any write, by the same check as `update-post`). A call over the rate limit, or while someone holds the edit lock on the post (`steadhand_guardrail_blocked`, 422). A caller who holds neither write capability (`steadhand_forbidden`). An input the schema refuses.
  - How the restore is saved (`PostWriter::restore()`, the only write it makes). The post must still hold the after-state's text, checked with an uncached read of the row before the save. The same check runs in a `pre_post_update` action for the post at `PHP_INT_MAX`, on every such action for the post during the restore. Core fires that action immediately before its `UPDATE` of the posts table, after the `wp_insert_post_data` filter, and before that point this post's row and its revisions are not written. Core can rename a trashed post with the same slug earlier in the save, as it does for `update-post`; that is another post's row. When the check fails, the action arms a `query` filter for the very next query. The filter blanks that query only when it is the `UPDATE` of this post's row (the statement starts with the posts-table UPDATE and ends with `WHERE ID = <post>`, as `wpdb::update()` builds it), so `wpdb::update()` returns false and `wp_insert_post()` returns `db_update_error` before the row is written, and no revision is made. If the next query is anything else, nothing is blanked and the call returns `steadhand_update_partial` with the text that the restore could not be stopped. Nothing is thrown through a hook, and both hooks are removed on every path. Outcome after a detected mismatch: `steadhand_refused_changed_since` only when the save returned an error and the row, read again uncached, does not hold the restored text; `steadhand_update_partial` in every other case. If the save reports success and the action never ran for the post, the call returns `steadhand_update_partial`. The restored bytes are stored as the before-revision holds them, after the save filters have run, so the KSES filters never change what an administrator stored. The row is read again afterwards and must hold the restored text, or the error is `steadhand_update_partial` (500).
  - Errors from the save: when WordPress reports an error and the post still holds the text it held before the call, the error is `steadhand_update_failed` (500, "nothing was changed"); otherwise it is `steadhand_update_partial`.
  - Then the entry's `undone_by` is set to the change-log row ID of this undo call, in one conditional update (`undone_by` 0 and `undoable` 1). If that update fails, the call returns `steadhand_update_partial`, and says the post was restored but the undo could not be recorded. A second undo of the same entry is refused as already undone.
  - Known limits, terms and featured image: the restore is a full replace through `TermWriter` or `MediaWriter`, compared with the state the change left just before the write. As for the forward call, a change by another request in the gap between that compare and the write is overwritten without an error. The restore does not run `save_post`, and the modified date does not change, as for `set-post-terms`.
  - Known limits, post text: the undo is not undoable: its own change-log row is stored with snapshot 0 and `undoable` 0. The restored text skips the content rules (`ContentLimits`, `BlockMarkup`), because it is the post's own earlier stored text; markup those rules would refuse comes back as it was. An undo saves a new revision, so the same post's older changes cannot be undone afterwards. When a mismatch is found and the abort cannot be applied, the overwrite still lands and is reported as `steadhand_update_partial`. Two causes are known: a posts table whose charset is not utf8, utf8mb3, utf8mb4 or latin1, for which wpdb issues a conversion query before its UPDATE (class-wpdb.php, `strip_invalid_text()` reached from `process_fields()`); and a `query` filter from another plugin that rewrites the statement. The window that remains: between the action's uncached read of the row and core's `UPDATE` statement, a concurrent request can change the row, and this save then overwrites that change. Nothing in this process can close that gap; `undo-change` reports `steadhand_update_partial` only when it sees the row differ after the save. The uncached read is a direct query on the connection WordPress uses for the post; on a site with database replicas it may not read the primary. This was not tested on such a setup. An edit made while revisions were switched off and then switched on again, or any other change that left no revision, is caught only by the text comparison. Revisions can be pruned after the change: then the entry is refused as not undoable, and nothing is restored. Entries of `create-post` and `upload-media` are still not undoable.

Explicitly **not** in v1: user create/update/delete, plugin/theme management, file editing, arbitrary option writes, raw SQL, permanent delete, comments (deferred to v1.1).

## 6. Guardrail engine

Runs on every write, before execution. Each rule has a **mode**: `block` (refuse, with a clear message the agent can act on), `fix` (rewrite input safely, then log what changed), or `warn` (allow, but flag it in the log and the response). A `fix` is checked again with the ability's schema, its input rule and its object check. A fix that changes `object_type` or `object_id` is refused with "A guardrail changed which object this call is about, so it was refused." A fix whose input fails the schema is refused with "A guardrail changed this call into one that is not allowed, so it was refused." (see `docs/HOOKS.md`, Rules of engagement).

### 6.1 Built-in rules (Free, always on)
| Rule | Mode | Why |
|---|---|---|
| Never write `widget_block`, `sidebars_widgets`, `theme_mods_*` | block | JSON-vs-serialized corruption; site-wide fatal errors |
| Never write options a plugin stores as PHP-serialized arrays (detected by reading the existing value) | block | The plugin silently ignores the value, or corrupts it |
| Option writes limited to the allowlist | block | Arbitrary options can break sites or escalate privileges |
| Block markup must re-validate (parse → serialize round-trip; block validation check) | block | Prevents "This block contains unexpected content" damage |
| Post content size and nesting limits | block | Runaway or looping agents |
| Rate limit per agent (writes/minute) | block | Runaway agents |
| Never touch `wp_users`, roles, capabilities, `active_plugins`, `siteurl`/`home` | block (hard-coded, not configurable) | Privilege escalation and takeover |
| A post that another user has open in the block editor (live `_edit_lock`); added in M2, not in the original table | block | Two people overwriting each other's open edit |

**Status in M2.** The built-in rules that exist, all in block mode (none uses `fix` or `warn` yet; the engine supports both, see `docs/HOOKS.md`):

- Post content size and nesting: `steadhand/content-limits`. Content over 256 KB (262,144 bytes), more than 2,000 blocks (nested blocks counted), nesting deeper than 20 levels, or content that is not valid UTF-8 is refused. Exactly at a limit passes. Only fields that hold block markup are checked: `content`, and for `edit-blocks` each `operations.<n>.markup` when the operations cannot be applied (see §5).
- Block markup: `steadhand/block-markup`. **Structural check only.** It checks that block comment delimiters are well formed and balanced, that each closing comment matches the block on top of the stack, and that each delimiter's JSON attributes decode. It cannot run the editor's JavaScript validation (the save-output comparison behind "This block contains unexpected or invalid content"), because that needs the block's JavaScript, and it does not check that a block name is registered or that attributes match a block's schema. The round-trip check in the table above is not built. Decision D17 (§14) records this. Delimiters are matched case-sensitively, with whitespace after `<!--`, as core's parser reads them, so `<!-- WP:Engine cache note -->` and `<!--wp:x-->` are not delimiters and are not refused. Known false positive: text that looks like a malformed delimiter (for example `<!-- wp:x` with no closing comment) inside a `core/html` block, or inside an ordinary HTML comment that starts with `<!-- wp:`, is refused.
- Rate limit: `steadhand/rate-limit`. 30 writes per agent in any rolling 60 seconds, counted from the change log. A reserved write counts, and a refused call does not. The count is read before the row is reserved, so writes that arrive at the same moment can pass together: the limit is best effort under concurrent requests. The `steadhand_rate_limit_per_minute` filter sets 1 to 600 and cannot turn the limit off.
- Daily upload cap: `steadhand/daily-upload-limit`. 100 `steadhand/upload-media` calls per agent in any rolling 24 hours, counted from the change log (`DbLogger::count_recent()`: `ok`, `fixed` and `error` rows, so a crashed write still counts). It applies to no other ability. A count that cannot be read refuses the call. Like the rate limit, it is best effort under concurrent requests. Its constant is `DailyUploadLimit::LIMIT`, not a filter.
- Edit lock: `steadhand/edit-lock` (added in M2). A write to a post that another user holds open in the block editor is refused while WordPress's lock is live. The window is WordPress's (150 seconds, changeable with `wp_check_post_lock_window`, 1 to 3,600 seconds). The lock is parsed as WordPress's `wp_check_post_lock()` parses it: the text before the first colon is the time and the text after it is the user, both read as numbers, so a lock with a leading space or a trailing newline means what WordPress makes of it. A lock in the older format (a timestamp with no user) takes its holder from `_edit_last`. A fresh one with no holder, holder 0 or another user blocks; the agent's own holder passes. A lock that is not a number is not live.

Not built yet:

- The option rules (no write to `widget_block`, `sidebars_widgets` or `theme_mods_*`; no write to plugin options stored as serialized arrays; option writes limited to the allowlist). They arrive with `update-option`, which does not exist yet.
- The hard-coded block on users, roles, capabilities, `active_plugins`, `siteurl` and `home`. No tool that could reach these exists yet, so the rule is not needed yet. It must be built before any tool can write to one of them.
- Block markup checks beyond the structural check above.
- Presets (§6.2) are not part of M2 (D23).

### 6.2 Presets (Free, toggleable)
- **Color slugs → hex** (`fix`): converts named color slugs in block attributes (e.g. `"backgroundColor":"white"`) to explicit hex `style` values. This catches a known cause of block validation errors with some themes.
- **Kadence preset:** block `theme_mods_kadence`; refuse unsupported attributes such as column `border.radius`.
- **Rank Math preset:** block writes to `rank-math-options-*`; route SEO meta through per-post meta keys only.

### 6.3 Custom rules (Pro)
Admin-defined rules: protected posts/pages (e.g. "never modify the homepage or legal pages"), option/meta allow and block lists, content rules (regex/blocklist), per-agent overrides, and scheduled "read-only windows".

## 7. Change log and undo

- Custom table `{prefix}steadhand_log`: `id`, `created_at`, `user_id`, `agent_label` (application password name), `ability`, `object_type`, `object_id`, `input` (secrets redacted, size-capped), `result` (ok / blocked / fixed / error), `guardrail_notes`, `snapshot_id`, `undoable`, `undone_by`.
- Snapshots: posts use **core revisions** (store the revision ID). Terms and featured images store a compact before state and after state as rows of `{prefix}steadhand_snapshots`, whose ID the log stores. Menus, options and meta are not built yet.
- **Undo** restores the snapshot if the object hasn't changed since (otherwise it refuses and explains, like AI Engine's "edited again since").
- Admin screen: filterable log (agent, tool, result, date) and a single-change view with a diff. The undo button is built (see Administrator undo below). Only an administrator (`manage_options`, and no agent role) sees and uses it, never an agent. The diff of post text, terms and featured image needs `edit_post` for that post; without it the diff is not shown. The message, the guardrail notes and the stored input of an entry about a post are also hidden from a viewer who may not edit that post: the list shows "Hidden: you are not allowed to edit this post." in the message column, and the single view shows the same text in place of those three fields. The agent label, tool, object, result and time are always shown. An entry about no post (object type other than `post`, or object ID 0) is always shown in full. An entry whose post no longer exists is hidden with the same text, for every viewer. An undo entry shows its details and says that an undo has no diff of its own.
- Retention: Free keeps 30 days; Pro is configurable, with CSV/JSON export.
- Logging must not fail open: if the log write fails, the change is rolled back or not executed. Refused calls are logged too (result `blocked`), including calls refused at the permission check before execution.

**Status in M3.** Undo exists for `update-post`, `edit-blocks`, `set-post-terms` and `set-featured-image` changes, through `undo-change` (§5). The admin log screen is built: the list, its filters and the single-change view with its diff. The undo button is built: an administrator can reverse one entry from its single view (see Administrator undo above). Apart from that, the log screen only reads; it writes nothing. The Agents screen (§4.1) is built as well. It creates and changes agent users, their capabilities and their Application Passwords, and it writes nothing to the change log.

- The table `{prefix}steadhand_log` (`includes/Log/Schema.php`), with the columns listed above: `id`, `created_at` (UTC), `user_id`, `agent_label`, `ability`, `object_type`, `object_id`, `input`, `result`, `message`, `guardrail_notes`, `snapshot_id`, `undoable`, `undone_by` and `after_snapshot_id`. It has keys on `created_at`, on `(user_id, created_at)` and on `(user_id, id)`. `snapshot_id` is the ID of the snapshot (a core revision for post text, a row of `{prefix}steadhand_snapshots` for terms and featured images; see below), or 0. `after_snapshot_id` is the ID of the snapshot that holds the state after the write, of the same kind, or 0. `undone_by` is 0 until the change is undone; then it is the ID of the change-log row that the `undo-change` call wrote (the call's own row, which `Pipeline::current_log_id()` names while the call runs). `guardrail_notes` holds the notes a write's guardrails recorded, joined by newlines, or is empty.
- What is logged, for every tool: every refused call (`blocked`), every failed call (`error`) and every successful write (`ok`, or `fixed` when a guardrail rewrote its input). A successful read call is not logged when its ability is read-only and needs `steadhand_read`, unless the `steadhand_log_read_calls` filter returns true (`docs/HOOKS.md`). Every other successful call is logged.
- Writes are recorded in two steps. Before the change, the write reserves its row: the row is stored with result `error` and the message "The call started, but no outcome was recorded.", so a crash leaves an honest row. After the change, the outcome is written to that row. If the reservation fails, the write is not performed and the caller gets `steadhand_log_failed`. If the change was made but the outcome cannot be recorded, the caller gets `steadhand_log_incomplete` and is told the change was made. A write refused by a guardrail, or at the permission check, writes one `blocked` row instead and reserves none.
- Snapshots for post text are core revisions. Each revision mirrors the post's row as it is stored when the revision is saved: its title, content and excerpt are read from the row, never from the call. The save filters therefore never change a revision, for `update-post` and `edit-blocks` alike, and an administrator's stored markup survives in every revision. Autosaves are not changed, and a revision of another post is filtered as usual. `update-post` saves a revision of the post immediately before it changes the post, when revisions are available. The snapshot is the newest non-autosave revision whose title, content and excerpt equal the post's current ones exactly, as they were before the change. The revision limit is ignored when it is looked up. The row's `snapshot_id` is that revision's ID whenever one is found, even when `undoable` is 0. `undoable` is 1 only when a revision was found, the call changes only title, content and excerpt (no status, slug or date key in the input), the state after the call was also saved (`after_snapshot_id` is above 0 and differs from `snapshot_id`), and both revisions still exist when the call ends (the revision limit, `wp_revisions_to_keep`, decides whether core keeps them). With one revision kept, WordPress removes the revision taken before a change on the save that follows, so no snapshot is taken and the call warns "This site keeps too few revisions for Steadhand to undo this change." `undoable` is 0 in every other case where no revision was found, for example when revisions are off for the post or the site, or the post type does not support them.
- `after_snapshot_id` is the ID of the core revision that holds the post's title, content and excerpt after the write, as stored. Only `update-post` and `edit-blocks` set it, and only for a call that changed the post (the output's `changed` is true) and whose before-snapshot is undoable. It is named by `Snapshots::post_revision_after()`, which accepts the newest non-autosave revision of the post only when all of these hold, checked in this order: (a) this write called `post_revision()` for the post, which opens a capture; (b) the post row, read again, holds exactly the title, content and excerpt that this write stored (`PostWriter` records them when it saves the row, and the record is cleared when the capture opens and when it closes), so if another request, or a plugin in this request, has changed the row before this read, nothing is named and nothing is saved; (c) the newest non-autosave revision holds the row's title, content and excerpt, and the same text this write stored, byte for byte. A revision of the current state is saved here whenever the newest non-autosave revision differs from the row as `wp_save_post_revision()` sees it. That is the case when core did not save the post-save revision (for example when a plugin removed core's hook). It is done only once (b) holds. The revision mirrors the row as it is read when the revision is inserted, so a change that lands between (b) and that insert leaves a revision of the other text. That revision is saved, and (c) rejects it, so it is never named; (d) this request created the revision during the write (a listener on core's `_wp_put_post_revision` action records each revision the request makes for the post), and it is newer than `snapshot_id`; (e) `snapshot_id` still names a non-autosave revision of this post, so core did not remove it during the save; (f) the title, content and excerpt of `snapshot_id` are not all equal to those of the after-revision, so a change the text does not show (for example one that the save filters turn back into the old text) is not undoable. A row change is caught when it lands before the after-check saves or compares its revision, and the call is then not undoable: a write by another person or agent that stores other text, or a same-request rewrite by a plugin. A change that lands after that point leaves the call undoable, and undo's own comparison of the row handles it. A concurrent save that stores the same text leaves the call undoable, and its after-state holds that text. This record does not guarantee that the row is unchanged when the call ends, that both revisions still exist later (core may prune either), or anything about fields other than title, content and excerpt. Undo must check these itself: that the row still holds the after-state's text, and that both revisions still exist, before it restores anything. When the call changed the post, its before-snapshot was undoable and the after-state is 0, the call's `warnings` say "Steadhand could not save the state after this change, so it cannot be undone." That warning is added unless `changed` is exactly `false`, so an output with no `changed` key is warned, and an output with no `warnings` list gets a list holding only that warning. When the list already holds `PostFields::MAX_WARNINGS` entries it replaces the last one. The revision is never an autosave, and it holds what the database stores, not what the agent sent. It is 0 in every other case: a call that changed nothing, a call that sets status, slug or date, a site that keeps one revision, a post type without revisions, a refused or failed call, and every other write (`create-post`, `set-post-terms`, `upload-media`, `set-featured-image`). A row whose `after_snapshot_id` is 0 is never undoable. Rows written before schema version 2 are set to not undoable when the table is upgraded (see Schema version). A snapshot is never an autosave. A revision does not restore status, slug or date; the snapshot table for those is later work. A call that changes nothing takes no revision. `Snapshots::post_revision()` returns the newest matching revision only: an older revision that matches does not count.
- **Administrator undo (the Undo button, M3).** The single view has an **Undo this change** button for an entry that `steadhand/undo-change` could reverse: the same four abilities, the same `undoable` and `undone_by` checks, and the same saved states. The button is shown only to a user who holds `manage_options`, holds no Steadhand agent role at all (a user who is both an administrator and a dedicated agent sees no button), may see the entry's post and may edit it (`edit_post`). The button is not an ability. `steadhand/admin-undo` is never registered with the Abilities API or the MCP server. `Pipeline::run()` and `Pipeline::check()` refuse any `AdminAction` ability, for every caller.
  - Who may undo: a logged-in user who holds `manage_options` and holds no Steadhand agent role (`Agents::holds_agent_role()` is false). The change-log screen itself is for `manage_options` users who are not dedicated agents, so an administrator who also holds the agent role can read the log but sees no button and cannot undo. Any other caller gets one fixed refusal, logged as `blocked`. The post must exist, must not be in the trash, must pass `edit_post`, and must be in a status the agent path edits (`PostFields::EDITABLE_STATUSES`). For terms, the caller must pass the taxonomy's `assign_terms`.
  - Which agent rules do not apply, and why: the Steadhand capabilities and the own-entry rule (an administrator may undo any agent's change); the guardrail engine (its rate limit, content rules and equivalent-call evaluation limit agents, so they are not run); the publish-capability rule (the native `edit_post` and `assign_terms` are checked directly instead; the undo never changes a post's status, so `steadhand_publish` is not asked for); and the media read rule (`MediaReader::readable_attachment()`, which lets an agent read an attachment only when it is inside the media rule: status inherit, and a parent that permits it). The administrator's undo of a featured image does not use that rule. It checks that the image to restore is still an attachment, is not in the trash, and is still an image.
  - The edit lock. While the post has a live edit lock, held by any user, the administrator's own session included, every kind of undo is refused with `steadhand_refused_locked` (the notice `locked`), and nothing is written. A lock is live as the agent's `EditLock` rule judges it (§6.1): its timestamp is inside the `wp_check_post_lock_window` window, clamped to 1 to 3,600 seconds, and a timestamp-only lock is live too. The rule's exemptions (the agent's own lock, a lock held by user 0, and a timestamp-only lock whose `_edit_last` names the agent) are the agent's alone and do not apply here. `EditLock::is_locked()` is the one definition both paths use. The guardrail itself is not run on this path. For post text the lock is checked at authorization and again in `execute()` immediately before the restore, which is the last check. For terms and the featured image it is checked at authorization and in `execute()`, and again inside the writer, just before its write, where a refusal is passed on as it is.
  - Which rules apply: the entry rules of `UndoRules` (the same as `undo-change`), an entry whose `user_id` is below 1 is refused before any write (so a restore can never be made that cannot be marked), the saved-state and unchanged-since rules, the template check, the status rule above, and, for terms, two rules of `set-post-terms` applied to the set the undo would restore: each saved term ID must still be a term of the taxonomy, and a post format is one term, so a saved set of more than one post format is refused as not undoable (`steadhand_refused_not_undoable`), as `set-post-terms` refuses that set. The count and the uniqueness of the saved IDs are checked by `UndoRules`. The taxonomy's assign capability is checked with `current_user_can()` directly, not with the agent's `may_assign()` shortcut, which is the agent's own rule. The shape check of the taxonomy name is not repeated: a name that is not allowed is refused by the allowlist check. The writers (`PostWriter::restore()`, `TermWriter::set()`, `MediaWriter::set_featured_image()`), with the same error mapping. A featured-image undo is refused, before any write, when the post type does not support a featured image or when the image to restore is no longer an image.
  - Availability. The undo works while the MCP Adapter or the Abilities API is missing. The admin wiring is registered before the dependency check (`Plugin::boot()`), and nothing on the undo path calls the Abilities API or the MCP Adapter: `UndoEntry` extends Steadhand's own `Ability` base, not `WP_Ability`, and it runs through `Pipeline::run_admin()` only.
  - Fail closed. When the change-log table is not ready, the undo is refused before any write, with no row and no change, and the caller gets a refusal rather than a change it cannot record.
  - Nothing new is granted. `MetaCaps` maps only for a dedicated agent, and `CapabilityGuard` gives no Steadhand capability to anyone who lacks it. The `Pipeline` brackets (`is_running()`, `is_write_call()`, `is_writing()`) change no answer for an administrator.
  - The checks that run in `Pipeline::run_admin()` before the ability's own rules, in this order: the input is prepared against the schema (an extra property or an ID above the maximum is refused); the caller check (`manage_options`, no agent role), which is wrapped so that a throwing filter refuses rather than fatals; then the ability's input rule and object check. A refusal at any of these is logged as `blocked`, and nothing executes. Only an exact `true` from the object check allows the call.
  - How it is logged: the undo writes its own row, with the administrator's user ID, `ability` `steadhand/admin-undo`, the entry's post as the object, the input `{ "id": <entry> }`, snapshot 0 and `undoable` 0. The entry it reversed gets `undone_by` set to that row. The mark uses the entry owner's user ID, which `DbLogger::mark_undone()` matches. The row is written before the change, as for any write. A failed reservation means no change.
  - The handler: the form posts to `admin-post.php` with the action `steadhand_undo_entry`, the field `entry` and a nonce bound to that entry ID. The handler checks, in order: the request is a POST; `entry` is digits only; the nonce for that entry; `manage_options`. Then it runs the undo and redirects to the entry's view with one short code: `done`, `changed`, `not_undoable`, `forbidden`, `partial`, `log`, `failed` or `locked`. The screen prints one fixed, translated notice for each code. An unknown code prints nothing, and nothing from the query string is ever printed.
  - Not undoable: an administrator's undo cannot itself be undone from the log.
- `create-post` rows are stored with `undoable` 0, because there is no earlier state to save. Steadhand does not undo a created post, and no revision is saved for it. The undo built in M3 does not cover it.
- **Undo (`undo-change`, §5).** It reverses one entry of the calling agent's `update-post`, `edit-blocks`, `set-post-terms` or `set-featured-image` change. Post text is restored from core revisions, as described here; a terms or featured-image change is restored from its saved states in `{prefix}steadhand_snapshots`, as described in §5. It restores the title, content and excerpt to the before-revision, only while the post's title, content and excerpt still equal the after-revision's text and no revision of the post was created after that after-revision (by creation order, the revision ID), and only while revisions are kept. Both revisions must still exist, belong to the post and not be autosaves. The check that the post is unchanged is made twice: an uncached read before the save, and the same read in a `pre_post_update` action for the post at `PHP_INT_MAX` (`PostWriter::restore()`), which core fires immediately before its UPDATE. A failed check blanks that UPDATE through a one-shot `query` filter, so the save writes no row or revision. Where that blank cannot apply, the overwrite lands and the call reports `steadhand_update_partial` (see §5). The undo's own row is stored with snapshot 0 and `undoable` 0, so an undo cannot itself be undone. `Pipeline::current_log_id()` gives the undo call the ID of its own row while it runs, and it is restored after a nested write, and cleared on every exit path, as the other per-write state is.
- The object an entry names. For `get-post`, `get-blocks`, `get-rendered` and `get-post-terms` the type is `post`; for `get-media` it is `attachment`. The ID is the one the caller asked for. It is recorded before the access check, so a refused call keeps the ID even when no such post exists, and the agent can read that ID back through `get-change-log`. For `create-post` the type is `post`, and the ID is the new post's ID once the write completes, or 0 when the call is refused or fails. For `update-post` the type is `post`, and the ID is the one the caller asked for.
- Input. It is redacted with `Redactor::value()`, with every key redacted as well as every value (a key that is a secret is masked, and two keys that redact to the same text both keep their values, the later as `#2`), and then capped at 16 KB of JSON. Input over 256 KB of JSON is not scanned at all. Larger input, and input that cannot be encoded, is stored as `{"truncated":true,"bytes":N,"keys":[...]}`, with the original size and up to 50 top-level key names, each key redacted. Input that passed schema validation is stored sanitized. A call refused for invalid input stores its input with the same digests, then redacted, so the text of its content is not kept either. Post content is stored as a digest, not as text, whatever its length: the stored `content` field is `{"bytes": <n>, "sha256": "<digest>"}`. The digest is of the text as submitted, before WordPress filters it on save, so it matches the stored content only when `content_modified_on_save` is false. An excerpt over 500 bytes is stored the same way; a shorter excerpt keeps its text. A value that is not text (an input that failed validation can hold one) is stored as `{"bytes": 0, "type": "<gettype>"}`. The digest is the SHA-256 written as eight groups of eight hex digits separated by colons (`PostFields::group_hex()`), so the log redactor does not mask it as a token or as a payment card number. Digests written before this format change keep the space-separated form. The revisions hold the text. `upload-media` stores its payload only as the digest of the decoded bytes (see §5). A field that is not text, and a `parent` that is not an integer, is stored as the digest of its JSON encoding; an unknown key is kept, after redaction, and its value is stored as a digest. An ability can change its log copy with `Ability::log_input()`, a public method of the internal base class, which is not an extension point. If it throws, an empty input is recorded and the row is still written.
- Refusal throttle. For each agent user, at most 60 refused calls (`blocked` entries only) are stored in any rolling minute. Then one marker row (`blocked`) is stored, and nothing more until the minute has passed. Errors are never throttled or dropped: an `error` entry is written after the call ran, and it is always stored. The count and the insert are not locked together, so concurrent requests can store slightly more than 60.
- Retention. Entries are kept 30 days, or the number of days the `steadhand_log_retention_days` filter returns (at most 3650). Pruning runs when an entry is written, at most once a day. A pass deletes in batches of 1,000 rows, up to 20 batches. A pass that ends on a short batch is recorded for the day. A pass that runs out of batches is not recorded, so the next write continues it. It does not use WP-Cron, so while nothing is written, entries past the period stay.
- Schema version. The option `steadhand_db_version` holds the layout version (`3`). Version 3 adds the snapshots table (below). An update from version 2 creates that table with `dbDelta()` and keeps every log row, including its `undoable` flag, because the rows that have an after-state are not changed. Version 2 adds the `after_snapshot_id` column. An update from version 1 adds it with `dbDelta()`, keeps the existing rows and sets every row that is undoable without an after-state (`undoable` 1 and `after_snapshot_id` 0) to not undoable. The version is recorded, and the back-off cleared, only when `Schema::ready()` and `Schema::snapshots_ready()` are both true: the log table exists and has every column in `Schema::REQUIRED_COLUMNS`, and the snapshots table exists and has every column in `Schema::SNAPSHOT_COLUMNS`, which the schema test compares with the real table. The reset is one statement that touches only those rows, so it is idempotent and runs on every install that succeeds. If the ALTER is refused, no version is recorded, the request-time retry waits an hour (a transient, `steadhand_schema_retry`), and the self-check reports `change_log_ready` as false; the next retry runs the reset. Activation always tries. The table is created by the activation hook. It is also created on the first request after the plugin is updated, whenever that option is missing or differs from the code's version, which covers an update from 0.1.0 (where the table did not exist). Database errors from the create and from the table check are never printed. Uninstall drops the table, removes the version and prune options, and removes the retry transient.
- Snapshots table `{prefix}steadhand_snapshots` (`includes/Log/Schema.php`, `includes/Log/SnapshotStore.php`): `id`, `created_at` (UTC), `user_id` (the user who saved the row), `kind` (`post_terms` or `featured_image`), `object_type` (`post`), `object_id` and `state` (JSON, at most 16 KB). `SnapshotStore::save()` runs only inside a write (`Pipeline::is_writing()`, otherwise it throws). It returns 0, and saves nothing, for an unknown kind, an object it cannot name, a state that is over the size cap, or a table that is not ready, and a write that gets 0 is not undoable. `find()` returns null for a missing row, a row whose state is not a JSON object, and a table that is not ready. A missing or broken snapshots table does not stop logging or writes: `Schema::ready()` is about the log only, and SelfCheck reports the snapshots table as `snapshots_ready`. Uninstall drops the table. Rows are pruned by the log's prune job, with the same cutoff (`steadhand_log_retention_days`, 30 days by default) and in the same batches; a row younger than the cutoff is never deleted. A before row of a call that changed nothing, or of a call that did not store an after state, is never used, and waits for that job.
- The agent label is the name of the Application Password used for the request, as stored in the entry. Redaction is best-effort (§10).
- Known gaps, open:
  1. Input rejected by core's own schema validation, before the permission callback runs, is not logged. The pipeline class docblock says so.
  2. Closed for writes: a write's row is reserved before the change (see above). Read calls still log after they run. For a read call that ran, a failed log write returns `steadhand_log_failed` in place of the result. That is harmless for reads, because nothing changed. The message says the action was not performed, which is true only for a refused call.
  3. With the table missing, the pipeline cannot store the entry for a failed call, so the caller receives `steadhand_log_failed` (over MCP, as the code at the end of the text; see §3.2). For a write, the write is then not performed. The tests cover this with the real logger and failing inserts. `get-change-log` returns `steadhand_log_unavailable` (503), not an empty list, when the log cannot be read: when the table check fails, or when its SELECT or COUNT fails. That error is itself a failed call, so one `error` row is stored for it. If that row cannot be stored either, the caller receives `steadhand_log_failed`.
  4. Revisions can be pruned. `wp_save_post_revision()` deletes old revisions beyond the site's revision limit, so an older log row's `snapshot_id` can point at a revision that no longer exists. `undo-change` checks that both revisions exist, belong to the post and are not autosaves before it restores anything (§5).
  5. Outside the MCP path, a schema refusal's message can contain a property name the caller sent. The MCP Adapter validates the schema first, so MCP calls do not reach it. To be fixed separately.

### 9.1 How Free and Pro relate (development model)
- **Pro is an add-on plugin, never a copy.** WordPress.org doesn't allow locked or trialware features in hosted plugins, so no Pro code ever ships inside Free. Pro declares `Requires Plugins: steadhand` and a minimum Free version, and contains only Pro features.
- **Free provides the extension points Pro plugs into:** tool registration, guardrail rule registration, a pre-execute interception point (for approvals), log retention/export filters, and admin screen slots. Free features reach Pro automatically because Pro runs on top of Free, so nothing is written twice.
- **The extension points are a public API.** They are documented in `docs/HOOKS.md`, covered by tests in Free, and never changed or removed without a deprecation period and a changelog entry. This is what keeps Pro from breaking, and third-party developers can build on them too.
- **Repo plan:** one repo now (this one). At M5, Pro gets its own private repo whose CI installs the latest Free and runs Pro's tests against it, so any Free change that breaks Pro is caught immediately. Revisit if that becomes painful.

## 10. Security requirements (non-negotiable)

- Every REST/ability entry point: capability check → schema validation → sanitization. Every output escaped by context.
- All SQL through `$wpdb->prepare()`; no dynamic table or column names from input.
- Admin UI: nonces on every form and action; `manage_options` required to manage agents and guardrails.
- No secrets in logs (redact any field matching password/token/key/secret patterns). The one redaction helper is `Steadhand\Redactor` (`includes/Redactor.php`). `text()` masks secrets inside free text: `Authorization` and `Cookie` header values, URL userinfo, sensitive key/value pairs (query, form, JSON, PHP array-dump and serialized shapes, with bracketed values masked whole), the authentication schemes Basic, Bearer, Negotiate and Digest, JSON Web Tokens, PEM private-key blocks, password hashes, GitHub, AWS, Slack, Stripe, Google, GitLab, Twilio, Mailgun, SendGrid, npm, Hugging Face, OpenAI and Anthropic tokens, WordPress application passwords, salt and key constants, long opaque strings that mix letters and digits (32 characters or more), payment card numbers that pass Luhn (as `[card]`), the database user and host in connection errors, and email addresses, including internationalised ones (replaced with `[email]`). It also removes control characters and ANSI escape sequences. The class docblock lists what it does not catch. `value()` walks an array and masks any value under a sensitive key. Redaction is best-effort pattern matching. It reduces the chance of a leak and cannot guarantee there is none, so callers must still avoid collecting secrets. A regular expression that fails masks the whole string rather than returning it. The change log uses the same helper.
- SSRF protection on any URL fetch (`wp_safe_remote_get`, block private/reserved ranges, size and type limits).
- No `eval`, no dynamic includes, no shell calls, no unserialize of untrusted input.
- The administrator's undo (§7) is an admin-post action: POST only, a nonce bound to the entry, `manage_options`, and no agent role, checked again in the pipeline.
- Uninstall (`uninstall.php`, which runs only when the Composer autoloader is present): remove our table (`{prefix}steadhand_log`), our options (`steadhand_db_version` and `steadhand_log_last_prune`) and the `steadhand_agent` role, strip every Steadhand capability from every user, and revoke the application passwords of users whose only role was the agent role (those credentials exist only for agent access). Users are never deleted, and users who also hold another role keep their application passwords. No orphans are left behind.
- `SECURITY.md` with a disclosure policy. GitHub private vulnerability reporting is available only once the repository is public (M4); until then reports go privately to the maintainers. Security fixes are released within 7 days of a confirmed report.
- Before each release: PHPCS (WordPress Coding Standards + security sniffs), Plugin Check, the test suite, and a MAKR pentest pass against a staging site (auth bypass, capability escalation, guardrail bypass, injection, SSRF).

The markup the call sends is filtered as for a user without `unfiltered_html`, and a filter that changes it is reported with `content_modified_on_save` true and a warning, not refused. Sent markup must be complete blocks with no stray HTML comment, no block delimiter may be completed across two places, and stored HTML left open before a sent run is refused (see §5). Revisions mirror the row, so the agent's filters never change them. Known limits: a plugin that changes the post during the save is reported, not prevented; stored closed but malformed HTML is kept as it is. See §5 |
| D21 | set-post-terms and the taxonomy assign capability | **Decided by the agent, as the conservative option, 2026-11-23. Confirmed by Rick, 2026-11-23.** `set-post-terms` needs the same capabilities as `update-post` for the post. A taxonomy's own assign capability is also checked. It passes only when that capability resolves to a non-empty list of primitive capabilities that is the same as the list the post type's edit capability resolves to, and that list does not contain `do_not_allow`. Core's own `assign_categories` and `assign_post_tags`, which core maps to `edit_posts`, therefore pass for `category` and `post_tag`, and the object check decides. Any other assign capability must also be held by the caller, through `current_user_can()`. An empty or `do_not_allow` resolution is refused. Steadhand adds no mapping to MetaCaps and grants no core capability. See §5 and §14.1 |
| D22 | Which image input upload-media accepts | **Decided (Rick, 2026-11-23): base64 only. `upload-media` does not fetch from a URL.** A URL fetch would let an agent make the server request any https address, which is also a way to send site data out inside the URL. ### 14.1 D6 — what an agent can edit

Edit rights depend on the post's status, not on who wrote it.

- **Post types:** `post` and `page` by default, through the filter `steadhand_allowed_post_types` (an extension point, documented in `docs/HOOKS.md`). Always excluded, even if added to that list: attachments (the media tools handle those), `wp_template`, `wp_template_part`, `wp_navigation`, `wp_block`, `wp_global_styles`, `nav_menu_item` and `revision`. In addition, every built-in post type other than `post` and `page` is excluded (every type WordPress registers with `_builtin` true, such as `custom_css`, `customize_changeset`, `oembed_cache`, `user_request`, `wp_font_family` and `wp_font_face`, and any core type added later). A custom type that is not built in can be added, but only if it is registered with `map_meta_cap` on. A type registered with `map_meta_cap` off is never allowed, even when the filter adds it (§14.1).
- **Taxonomies:** the term tools follow the post types. A taxonomy is readable only when it is attached to an allowed post type, is public, and is not in the fixed exclusions listed in §5. So changing `steadhand_allowed_post_types` changes the taxonomies too, and no separate filter exists for them. The menu types (`nav_menu`, `nav_menu_item`, `wp_navigation`) are read only by the menu tools, which do their own status and type checks.
- **`steadhand_read`:** read allowed-type posts in any status except trash.
- **Object check:** every single-post tool gets its post from one function, `PostReader::readable_post()`, both in its object check and in its execute step. The function returns the post only when all of these hold: it exists, it is not in the trash, its type is allowed, and the current user passes `read_post`. list-posts checks each row the same way. The type and trash rules live in that function because MetaCaps cannot always see them. A type registered with `map_meta_cap` false is never allowed, so the type rule refuses it. For such a type whose `read_post` capability is set to another one (here `read`), WordPress passes that capability to the `map_meta_cap` filter, not `read_post`, so MetaCaps never sees the call, and the type rule is the only layer for it. Where core keeps the name `read_post` for such a type, MetaCaps refuses it as a second layer. For any other name, the agent does not hold the renamed capability (see the bullet on those types below). Every refusal from these tools has one text, with one exception. When a post passes `PostReader::readable_post()` (the agent can read it) and is published, scheduled or private, and the caller lacks `steadhand_publish`, `update-post`, `edit-blocks`, `set-post-terms` and `set-featured-image` refuse with the publish-needed text (403, `steadhand_forbidden`) instead of the generic one. `upload-media` does the same for such a post sent as `parent`, with a text that names the parent. The exception is made by `Ability::object_refusal_detail()`, which the pipeline calls only after a failed object check and only these five abilities override. It is not a general mechanism: a missing, trashed, unreadable, disallowed-type or draft post, and a caller who holds `steadhand_publish`, keep the generic text.
- **`steadhand_write_drafts`:** create posts, saved as `draft` unless the agent also holds `steadhand_publish` (§5). Edit existing posts of any author while their status is `draft`, `pending` or `auto-draft`. May change a draft to pending, never to publish, future or private. May never change `post_author`.
- **`steadhand_publish`:** edit posts that are published, scheduled (`future`) or private, and set those statuses.
- **One refusal for an object the caller cannot access (every write tool):** every object refusal has one text, one code (`steadhand_forbidden`) and one status (403), at every stage. A post the caller may not access is refused at the permission check with that refusal. If it stops being accessible after that check and before the write, the call is refused with the same text, code and status, and nothing is written: by the ability's own re-check in its execute step (`update-post`, `edit-blocks`, `set-post-terms`, `upload-media` and `set-featured-image`), or by the writer's last re-check (`PostWriter`, `TermWriter` and `MediaWriter`). The code cannot show at which stage the object stopped being accessible, so a client needs no separate case for it.
- **`update-post` and `edit-blocks` also need `steadhand_read`:** their object check reads the post through `read_post`, which needs `steadhand_read`. They also need `steadhand_write_drafts` or `steadhand_publish`, as above.
- **`set-post-terms` follows the same rules:** the object check reads the post with `read_post` (`steadhand_read`), and the status decides between `steadhand_write_drafts` and `steadhand_publish`, as for `update-post`. Its taxonomy must be allowed and attached to the post's type (§5). A taxonomy with its own assign capability is checked as D21 says (§14).
- **Unsent fields (`update-post`):** WordPress re-saves every stored field on each save, and an agent's saves are filtered by KSES because it lacks `unfiltered_html`. `update-post` puts back the stored title, content, excerpt and filtered content of the post for each one the call does not send, after the save filters have run, so those bytes are kept (§5, Unsent fields and save filters). It does not refuse a call because of a filter on this site. A change to an unsent field that is made after the restore is detected after the write, and reported as `steadhand_update_partial`. `edit-blocks` applies the same principle to the blocks it does not name: they are stored as they are, and only the markup it sends is filtered (D20).
- **Invalid page template (`update-post`):** WordPress validates a page template after it has written the row, so a post whose template the active theme does not have would change and then be reported as an error. `update-post` checks the template the way core does, before any write, and refuses (409, `steadhand_refused_invalid_template`). An administrator must set a valid template.
- **Attachments (media tools):** media library items are readable through the media tools only, by two layers, and both apply the same media rule (`MediaReader::within_rule()`, described under §5): the attachment's own status is `inherit`, and its parent is none, missing, or of an allowed type and not trashed. Layer one is `MediaReader::readable_attachment()`, which returns an attachment only when it exists, its type is `attachment`, it passes the media rule, and the current user passes `read_post`. Layer two is the `map_meta_cap` rule in `MetaCaps`: inside a Steadhand call, for a dedicated agent, `read_post` on an attachment requires `steadhand_read` only and passes the media rule; otherwise it is refused. Core resolves an attachment to its parent's status and would refuse a draft parent, so the rule replaces that answer. Outside a call, and for every other user, core's answers stand for layer two, and layer one still applies the media rule. `edit_post`, `publish_post` and `delete_post` are never granted on an attachment by this rule. The post tools still refuse attachments, because `PostReader::readable_post()` checks the type itself, and `attachment` stays in `PostTypes::ALWAYS_EXCLUDED`.
- **Media writes (`upload-media`, `set-featured-image`):** both need `steadhand_media` and `steadhand_read`. `upload-media`'s optional parent must pass `update-post`'s object check. `set-featured-image` needs the post's status capability (`steadhand_write_drafts` or `steadhand_publish`), and a `media_id` above 0 must pass the media rule and be an image. Neither grants `edit_post` on an attachment: the writer does not need it, and `MetaCaps` is unchanged.
- **How:** a `map_meta_cap` filter maps `read_post`, `edit_post`, `publish_post` and `delete_post` to Steadhand capabilities for agent users. The role never gets WordPress's general editing capabilities (`edit_posts`, `edit_others_posts` and so on). The status of the mapping in M2 is set out in the table after this list.
- **Post types registered with `map_meta_cap` false are never allowed.** Such a type is never an allowed type, even when the owner adds it to `steadhand_allowed_post_types`. Core makes none of its per-post checks for such a type (author, status, privacy page), and for some of them core renames `read_post`, `edit_post` or `publish_post` to a capability the agent may hold (for example `read`), so the mapping would not see the call. So every Steadhand tool refuses its posts and the parents of its attachments. The allowlist (`PostTypes::allowed()`) decides this, and every list, count and check uses that one list. Where core keeps the capability names, MetaCaps refuses `read_post`, `edit_post` and `publish_post` for such a type as well, as a second layer. It never grants `delete_post`. A type registered with `map_meta_cap` on, as `post` and `page` are, is not affected. WordPress turns `map_meta_cap` off by default when a type sets `capabilities` or a `capability_type` other than `post` or `page`, so such a type needs `'map_meta_cap' => true` in its registration before it can be allowed.
- **Security requirement:** the mapping applies only while a Steadhand pipeline request is running (a context flag the pipeline sets and clears). Application Passwords also work against WordPress's own REST API; if the mapping applied everywhere, an agent could edit posts through `/wp/v2/posts` and skip the guardrails and the log. So in M1 agent users' credentials are refused everywhere except the Steadhand MCP endpoint (core REST, XML-RPC, wp-admin, and the MCP Adapter's default server at `/wp-json/mcp/mcp-adapter-default-server`). Negative tests cover both the mapping and the block. It is also off once WordPress is shutting down, so a shutdown hook that runs after a `wp_die()` or `exit` inside an ability does not see a call in progress. A `do_not_allow` from core or from an earlier `map_meta_cap` callback is returned unchanged, so Steadhand never turns another component's denial into a grant. The order of the pipeline steps is fixed: defaults, schema, sanitizing, the caller's identity and Steadhand capabilities, the ability's input rule, and then the object check. A caller without the capability learns nothing from the input rule.

**Mapping in M2** (`includes/MetaCaps.php`), for a dedicated agent during a Steadhand call. `edit_post` and `publish_post` are mapped only during a write call (an ability that is not read-only; the innermost Steadhand call decides, via `Pipeline::is_write_call()`). `read_post` is mapped in every Steadhand call:

| Capability | Post (not an attachment) | Attachment |
|---|---|---|
| `read_post` | `steadhand_read`, for any status except trash, of an allowed type | `steadhand_read`, when the media rule passes; otherwise refused |
| `edit_post` | `steadhand_write_drafts` for `draft`, `pending` and `auto-draft`; `steadhand_publish` for `publish`, `future` and `private`; refused for any other status | refused |
| `publish_post` | `steadhand_publish`, whatever the status | refused |
| `delete_post` | not mapped: core's answer stands, and the agent role holds nothing that grants it, so it is refused | refused |

A post that is missing, in the trash, or of a type that is not allowed is refused for every mapped capability. Outside a Steadhand call, WordPress's own answers stand. Inside a read tool, such as `get-rendered` when a shortcode runs, core's answers stand for `edit_post` and `publish_post`, so they are false for an agent. The mapping replaces only the post type's own capabilities. If core asks for anything else (for example `manage_privacy_options` for the privacy policy page, or a capability another plugin adds to `edit_post` or `publish_post`), the answer is refused, so a draft privacy policy page cannot be edited or published by an agent. The status-to-capability decision is in one place, `MetaCaps::edit_capability()`, which `UpdatePost` also uses.

Where Steadhand refuses edit, publish or delete on an attachment, or edit on a status it does not map, it returns the capability name `steadhand_no_grant` rather than `do_not_allow`. Core's `read_post` check, for a post that is neither public, private nor the agent's own, returns the answer it gets for `edit_post`, so a `do_not_allow` there would also refuse reads of such a post. The name `steadhand_no_grant` is held by no user, so it refuses in the same way without that side effect.
