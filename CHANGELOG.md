# Changelog

All notable changes to Steadhand are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html), starting at `0.1.0`.

## [Unreleased]

### Added
- Change log, in the table `{prefix}steadhand_log`. It records every refused call (`blocked`) and every failed call (`error`) to any Steadhand ability, including refusals at the permission check. Successful calls to read-only abilities that need `steadhand_read` are not recorded, unless the `steadhand_log_read_calls` filter returns true. Other successful calls are recorded. Each entry stores the time (UTC), the agent user ID, the agent label (the name of the Application Password), the ability, the object the call named (for `get-post`, `get-blocks`, `get-rendered`, `get-post-terms` and `get-media`: the ID the caller asked for, even when the call was refused), the result, the message, any guardrail note, and the call's input. The input is redacted, keys as well as values, and stored as JSON, capped at 16 KB. Larger input is stored as a summary (its original size and its top-level key names, each redacted), not cut in the middle. Input over 256 KB is not scanned at all.
- `steadhand/get-change-log` (`steadhand-get-change-log`), the thirteenth tool. It returns the calling agent's own entries, newest first, with paging and filters for result, ability and date. It never returns another agent's entries or any stored input. If the log cannot be read, it returns `steadhand_log_unavailable` (503) rather than an empty list.
- Retention of 30 days. Entries are pruned when a new entry is written, at most once a day, in batches of 1,000 rows and up to 20 batches per pass. A pass that runs out of batches is continued by the next write. Nothing runs on WP-Cron, so entries older than the period remain while nothing is being written.
- Three extension points, documented in `docs/HOOKS.md`: the filters `steadhand_log_read_calls` and `steadhand_log_retention_days`, and the action `steadhand_log_entry_stored`.
- `change_log_ready` in the self-check of `steadhand/get-diagnostics`: whether the change-log table exists.
- The change-log table is created on activation, and on the first request after an update when its recorded schema version is missing or different. If that create fails, the request-time retry waits an hour, and database errors from it are never printed.
- Uninstall drops the change-log table and removes its two options, `steadhand_db_version` and `steadhand_log_last_prune`. As with the rest of uninstall, this runs only when the Composer autoloader is present.
- `steadhand/create-post` (`steadhand-create-post`), the fourteenth tool, and `steadhand/update-post` (`steadhand-update-post`), the fifteenth. They are the first write tools. Both run through the write path described below. Neither can set a post's author, password, parent, terms or meta. Post meta is not part of M2 (SPEC §14, D18): no allowlist is defined.
  - `create-post` takes `title`, `content`, `excerpt`, `slug`, `status`, `date` and `post_type`. The author is always the calling agent. `status` defaults to `draft`. `pending`, `publish`, `future` and `private` need `steadhand_publish`. A `date` is allowed only with status `future`, where it is required. `post_type` must be an allowed type (`post` and `page` by default). Title or content must be non-empty.
  - `update-post` takes `id` and at least one of `title`, `content`, `excerpt`, `slug`, `status` and `date`. It changes only the fields sent, and only where they differ from what is stored. `content` replaces the whole content. A post's type cannot be changed. A scheduled post cannot be published early by this tool: WordPress keeps it scheduled, and the result says so in `warnings`.
  - Limits: title 400 characters, excerpt 5,000, slug 200 (lowercase letters, digits and single hyphens), content 262,144 characters and 256 KB in bytes (checked by the content guardrail). `date` is ISO 8601, read as UTC when it has no offset, at least 60 seconds and at most 10 years ahead.
  - Output: `id`, `post_type`, `status`, `title`, `slug`, `link`, `modified`, `changed`, `content_modified_on_save`, `warnings` and `guardrail_notes`. `content_modified_on_save` is true when WordPress stored a title, content or excerpt that differs from what was sent.
  - Publishing a draft needs both `steadhand_write_drafts` (to edit the draft) and `steadhand_publish` (to set the live status). Editing a live post needs `steadhand_publish`, and so does moving a live post back to draft. `update-post` also needs `steadhand_read`, to read the post it edits.
  - `update-post` saves a WordPress revision of the post before it changes the title, content or excerpt, when revisions are available. `warnings` says when none could be saved. The log row's `undoable` flag is 1 only when a revision was found, the site keeps two or more revisions (or unlimited ones), and the call changed only title, content and excerpt. With one revision kept, WordPress removes the revision on the save that follows, so the change is not undoable and `warnings` says so. Steadhand does not claim undo for status, slug or date. `create-post` rows are recorded with `undoable` 0, because there is no earlier state to save. Undo is milestone M3.
- `steadhand/edit-blocks` (`steadhand-edit-blocks`), the sixteenth tool and the third write tool. It changes some blocks of one post, by the path `get-blocks` returns, without resending the whole content. A call takes one to 20 operations: `replace`, `insert_before`, `insert_after`, `remove` or `append`. An operation that names a block must send that block's name, and a path whose block has another name is refused. Blocks that no operation names are stored byte for byte, and are not passed through the save filters. Only the markup the call sends, and the separators Steadhand adds next to it, are filtered by WordPress, as for a user without unfiltered HTML. A filtered result is what is stored; the call succeeds, with `content_modified_on_save` true and a warning. The markup of each operation must be complete blocks on its own, with no HTML comment that is not a block comment (a break comment is allowed only as the sole inner content of its `core/more` or `core/nextpage` block), and must still be complete blocks after filtering. The block delimiters of the final content must come only from the stored blocks kept and the markup sent, so a delimiter cannot be completed across two places. Markup that leaves HTML open (an unclosed script or textarea) is refused when stored content follows it, and so is a removal that joins HTML left open to the content after it. A stored post whose HTML is left open before the place of the edit (an unclosed script, comment, textarea or attribute value) is refused, and so is an edit that would change blocks it does not name, with `steadhand_refused_unsupported_markup` (409), each with its own message. The guardrails see exactly the bytes that will be stored: the guard records a hash of the content it checked, the plan refuses unless its own preview has that hash, and the write refuses if the content it assembles differs. WordPress's display split cuts the post at a `wp:more` delimiter, and its pattern can run past a void delimiter. The check covers the whole result: every match must be one whole delimiter, or an untouched match inside one kept range. A sent markup that fails it is refused with `steadhand_invalid_input` (400), and an edit whose result fails it with `steadhand_refused_unsupported_markup` (409). Where WordPress has the custom-CSS strip for blocks (WordPress 7.0 and later), it runs on every Steadhand write, also for a user who holds `edit_css`; on WordPress 6.9 there is no such strip, so none runs. It uses the permissions, revision, partial-failure and output rules of `update-post`. It refuses, with nothing written: `steadhand_refused_block_mismatch`, `steadhand_refused_content_changed` and `steadhand_refused_unsupported_markup` (409), `steadhand_invalid_input` (400), and `steadhand_update_failed` (500) when the content changed between the check and the write. A refusal raised while the write is prepared is logged as `error`, and a guardrail or input refusal as `blocked`. The change log stores a digest of each markup, not its text. A post over the content limits cannot be edited with this tool. The first child of an empty container block cannot be added: replace the container instead.
- Revisions mirror the post's row. A revision of a post, saved before an edit or after it, takes its title, content and excerpt from the stored row, read again when it is saved, never from the call. The save filters therefore never change a revision: an administrator's stored markup, and the bytes an edit does not touch, survive in every revision, and `undoable` stays 1 on a second edit. This applies to `update-post` too. Autosaves are not changed.
- Capability mapping for dedicated agents, during Steadhand calls only. `read_post` needs `steadhand_read` in every Steadhand call. `edit_post` and `publish_post` apply only during a write call, so inside a read tool (such as `get-rendered`, where a shortcode runs) core's answers stand and an agent is refused. `edit_post` needs `steadhand_write_drafts` for draft, pending and auto-draft posts, `steadhand_publish` for published, scheduled and private posts, and is refused for any other status. `publish_post` needs `steadhand_publish`. `delete_post` is not mapped, so it is refused. Attachments are readable only through the media rule, and edit, publish and delete are refused on them. Outside a Steadhand call, WordPress's own answers stand.
- Write path. A write runs in a fixed order: validate, authorize, guardrails, log reservation, snapshot, execute, log completion. Its log row is reserved before the change. If the row cannot be reserved, the write is not performed and the call fails with `steadhand_log_failed`. If the change is made but its outcome cannot be recorded, the call fails with `steadhand_log_incomplete`, and the message says the change was made. A refused write is recorded as `blocked` and does not run.
- Guardrail engine (`Steadhand\Guardrails`). A rule returns allow, block (refuse, with a message), warn (allow and record a note) or fix (run with a rewritten input, which is checked again before use). Built-in rules cannot be removed. A rule that throws, or returns anything other than a result, blocks the call. A blocked write fails with `steadhand_guardrail_blocked` (HTTP status 422) and the rule's message.
- Built-in guardrail rules. All four block. None rewrites or warns yet.
  - `steadhand/content-limits`: refuses content over 256 KB, more than 2,000 blocks (nested blocks count), nesting deeper than 20 levels, and content that is not valid UTF-8. Content exactly at a limit passes.
  - `steadhand/block-markup`: refuses block comment delimiters that are malformed, unbalanced or out of order, and attributes that are not valid JSON. This is a structural check only. It does not run the editor's save-output validation, does not check that a block name is registered, and does not check attributes against a block's schema.
  - `steadhand/rate-limit`: at most 30 writes per agent in any rolling 60 seconds, counted from the change log. A write counts from its reservation, including a write that then fails. Refused calls do not count. The `steadhand_rate_limit_per_minute` filter can set the limit from 1 to 600. It cannot turn the limit off.
  - `steadhand/edit-lock`: refuses a write to a post that another WordPress user has open in the block editor. The window is WordPress's, 150 seconds by default, and the `wp_check_post_lock_window` filter can change it. The refusal does not name the other user.
- Extension points, documented in `docs/HOOKS.md`: the action `steadhand_register_guardrails`, the filter `steadhand_rate_limit_per_minute`, and the public classes `Steadhand\Guardrails\Rule`, `Context`, `Result` and `Registry`.

### Changed
- Steadhand can now change posts. Release 0.1.0 wrote nothing to a site. An agent that holds `steadhand_write_drafts` or `steadhand_publish` can create and update posts. A new agent holds `steadhand_write_drafts` by default. The read tools are unchanged.
- For a write, the change-log row is reserved before the change and completed after it. For a read call, the single entry is still written after the call has run.
- Snapshots are never autosaves. The snapshot is the newest non-autosave revision whose title, content and excerpt equal the post's current ones exactly. The revision limit is ignored when it is looked up. A snapshot ID is kept whenever a revision was found, even when `undoable` is 0.
- A call that sets status, slug or date gets the warning "This change includes status, slug or date, which Steadhand cannot undo yet."
- A write sets the post date only when a date is sent. WordPress gives a draft with no set date the time it is published, so publishing an old draft does not backdate it. A scheduled update keeps the requested date.
- Post content in the change log is stored as a digest of the text as submitted, before WordPress filters it on save: its byte count and SHA-256, written as eight groups of eight hex digits, whatever its size. An excerpt over 500 bytes is stored the same way. The digest matches the stored content only when `content_modified_on_save` is false. The revisions hold the text. A call that fails validation is logged with the same digests, so its content text is not kept either, and a value that is not text is logged as its type.
- If a write's execute step throws, the caller and the change log get "The change could not be completed and may have been partly applied. Check the result before you continue." The code is `steadhand_error`. The read path's message is unchanged.
- `update-post` handles its own write errors. When WordPress reports an error, or the write throws, the post is read again. If it changed, the error is `steadhand_update_partial` (500): "The post was changed, but the save did not finish as expected, so the change was at least partly applied. Check the post before you continue." The same error and message are returned when a field the call did not send differs from what was stored after a write that reported no error. Only when nothing changed is the error `steadhand_update_failed`, with "nothing was changed".
- `update-post` refuses, with `steadhand_refused_invalid_template` (409), a post whose page template the active theme does not have. WordPress validates the template after it has written the row, so this is refused before any write. Nothing is changed.
- New warnings. `Making a post private removes its password.` when a protected post is made private. `WordPress stored the status "<stored>" instead of "<requested>".` when WordPress stores another status, in both tools. `This site keeps too few revisions for Steadhand to undo this change.` when the site keeps one revision or none.
- Known limits of `update-post`: `wp_update_post()` re-normalises some values an administrator stored in an unusual way by a direct database write. An empty `comment_status` on an update becomes `closed`, a non-canonical slug is sanitised, a post with no category gains the default category, and `to_ping` is sanitised. Steadhand does not restore them.
- The block markup check's loose delimiter test is case-sensitive and needs whitespace after `<!--`, as WordPress's parser does. So `<!-- WP:Engine cache note -->` and `<!--wp:x-->` are no longer refused. Known false positive: text that looks like a malformed delimiter inside a `core/html` block, or inside an ordinary HTML comment that starts with `<!-- wp:`, is still refused.

### Security
- Refusal throttle. For each agent user, at most 60 refused calls are stored in any rolling minute. Then one marker row records that further refusals are not being logged, and nothing more is stored until the minute has passed. The refusals themselves are still returned to the caller. Errors are never throttled or dropped. The count and the insert are not locked together, so concurrent calls can store slightly more than 60.
- Successful calls are logged unless they go to a read-only ability that needs `steadhand_read`. An ability that is marked read-only but needs a write capability is logged on success too.
- Keys in logged input are redacted as well as values, so a token used as a key does not reach the log.
- Logging does not fail open. On the call path, when a call's entry cannot be stored, the call returns `steadhand_log_failed` in place of its result. On the permission-check path, a refusal is returned whether or not its entry is stored, so a refused call is never allowed through.
- Redaction of logged fields is best-effort. It uses the same helper as `get-diagnostics`, and it cannot catch a secret that no pattern recognises (see the class docblock of `Steadhand\Redactor`).
- The block markup check is structural only. Content that passes it can still show a block-validation warning in the editor, and block names and attributes are not checked against the site's registered blocks.
- Content saved by a write is filtered by WordPress's post KSES rules for the agent, which does not hold `unfiltered_html`. A tag that WordPress does not allow for the agent is removed on save, and the text between tags is kept. `content_modified_on_save` reports when the stored text differs from what was sent. A field the call does not send is not filtered: it is saved as stored.
- The post capability mapping applies only during a Steadhand call, so an agent cannot edit posts through core's REST API. The existing lockdown still refuses its credentials there.
- The rate limit is 30 writes per agent per minute by default. The filter can change it but cannot turn it off.
- The edit lock refuses a write to a post that another user has open in the block editor, so one person's save does not overwrite another's open edit. The lock is read as WordPress's `wp_check_post_lock()` reads it: the text before the colon is the time and the text after it is the user, with numeric casts, so a lock with a leading space or a trailing newline is read as WordPress reads it. A lock in WordPress's older format (a timestamp with no user) takes its holder from `_edit_last`. A fresh one with no holder, holder 0 or another user blocks. The agent's own lock passes.
- Capability guard. Steadhand's own capabilities are set by a `user_has_cap` filter at the last priority, so no other plugin's filter can grant or remove one. Other capabilities are not changed. "The value stored for the user" means the user's capabilities as WordPress loaded them: code that runs inside the site and rewrites them is trusted. Multisite is not supported: a super admin passes core's checks before the guard runs.
- `edit_post` and `publish_post` are mapped only during a write call. If core asks for anything beyond the post type's own capabilities, the answer is refused. So a draft privacy policy page cannot be edited or published by an agent. A post type registered with `map_meta_cap` false cannot be edited through Steadhand either: WordPress renames the capability before the mapping sees it, so the check fails closed.
- On update, the post-field KSES filters are in place for the whole save, for every field, as on create. No Steadhand code removes a KSES filter or the Global Styles filter during a write, so code that runs during the save, such as a `save_post` listener, is filtered too. A field the call does not send is put back, byte for byte, as it is stored, for that one post, after the save filters have run. The restore acts once, on that post's own update, and is removed afterwards. The fields the call sends are filtered. This is safe because the agent cannot influence an unsent value (the update allowlist does not include it), and every value the agent has sent was filtered when it was stored. A save filter on this site that would change an unsent field no longer refuses the call: the field is kept as stored. A change to an unsent field made after the restore is reported as `steadhand_update_partial`. Steadhand never calls `kses_init_filters()` or `kses_remove_filters()`.
- A guardrail's fix is checked again with the ability's schema and object check. A fix that changes the object the call is about is refused with "A guardrail changed which object this call is about, so it was refused."

## [0.1.0] - 2026-11-22

First tagged build, for internal testing. It is read-only: an agent can connect and read, and nothing in it writes to a site.

### Added
- Plugin bootstrap with dependency checks. If the Abilities API or the MCP Adapter is missing, Steadhand shows an admin notice and does nothing else; it never fatals.
- `steadhand_agent` role and Steadhand capabilities, created on activation. Uninstall removes the role, strips every Steadhand capability from every user, and revokes the application passwords of users whose only role was the agent role. Users are never deleted, and users who also hold another role keep their application passwords.
- `steadhand` ability category and the Steadhand MCP server at `/wp-json/steadhand/mcp`, gated by `steadhand_connect`.
- `steadhand/get-site-info` ability, running through the shared pipeline (validate, authorize, execute, log). The log step is a no-op until M2.
- Admin notice instead of a fatal error on PHP older than 8.1 or when the Composer autoloader is missing.
- Refused calls will be logged as `blocked` once the change log lands in M2; until then the log step is a no-op.
- PHPCS and PHPUnit integration tests.
- Continuous integration: PHPCS, PHPUnit integration tests on PHP 8.1 and 8.4 against WordPress 6.9 and latest, Plugin Check on the WordPress.org build, and the release-zip build.
- Two release zips: a dev zip (with the dev-only updater) and a WordPress.org zip. A `vX.Y.Z` tag publishes both as a GitHub release.
- WordPress.org build check that fails if the build contains any update-checker code or dev/test tooling. CI runs it on every build.
- Dev-only updater for internal builds. It serves updates from this repository's release assets only (never the source archive) and does nothing unless a token is set as a constant in the site's configuration. It is not part of the WordPress.org build.
- Local development script that creates an agent user and an Application Password on the wp-env development site. Local development only.
- Documentation: disclosure policy (`SECURITY.md`); developer documentation in the repository.
- `steadhand_allowed_post_types` filter, the first public extension point, for choosing the post types the post tools may use. The default is `post` and `page`. Attachments, block templates, reusable blocks, navigation menus and revisions are always excluded, and so is every other built-in WordPress post type (for example custom CSS, privacy requests and the oEmbed cache), whatever the filter returns.
- Agents can read allowed post types in any status except trash (drafts, pending, private, scheduled, published and password-protected posts, by any author), but only inside a Steadhand call. Outside Steadhand, WordPress's own rules are unchanged.
- Four read-only post tools, each through the shared pipeline: `steadhand/list-posts` (paged, filtered by status, search and date; allowed post types only), `steadhand/get-post` (one post with its raw content as stored), `steadhand/get-blocks` (the block tree, with the index path each block is addressed by) and `steadhand/get-rendered` (the HTML a post renders to, through the content filters). Content over 256 KB is cut on a UTF-8 boundary and flagged. Refused, trashed and missing posts get the same message.
- Four read-only term and menu tools, each through the shared pipeline: `steadhand/list-terms` (a page of the terms of one allowed taxonomy, with counts, search, parent and ordering), `steadhand/get-post-terms` (the allowed terms of one post, grouped by taxonomy, at most 500 per taxonomy, with a `total` and `truncated` for each), `steadhand/list-menus` (classic menus and block navigation menus, with the item count WordPress stores for each classic menu and theme locations) and `steadhand/get-menu` (one classic menu as a flat list of up to 500 items, or one block navigation post with its content and block tree).
- A taxonomy is readable only when it is public, attached to an allowed post type, and not a navigation, link or theme taxonomy. The allowed post types decide the taxonomies, so the existing `steadhand_allowed_post_types` filter covers them too, and no new filter was added.
- Two read-only media tools, each through the shared pipeline: `steadhand/list-media` (a page of media library items, newest first, filtered by media type, search, parent post and date range) and `steadhand/get-media` (one item, with its description as plain text and its generated image sizes). Both return public URLs and never server file paths, image metadata (EXIF, IPTC, GPS) or user email or login. Only media the media rule allows is returned: its own status must be `inherit`, and it must be unattached, attached to a post that no longer exists, or attached to a post of an allowed type that is not in the trash. Trashed media is never listed, and `total` counts only the media that is listed.
- Media output is clamped: a title, alt text or caption is plain text cut at 1000 bytes, a MIME type longer than 100 characters is cut, and metadata that is not a finite, non-negative duration or a positive dimension or file size is returned as null. A generated size with an overlong name or MIME type, or with no usable file name, is left out. One odd attachment therefore never fails a call.
- Media URLs are returned only for stored, relative file locations. A file with no stored location, or with an absolute server path, has an empty `url` and no sizes.
- Classic menu item titles are plain text, cut at 1000 bytes.
- `steadhand/get-diagnostics`, a read-only health report through the shared pipeline: the environment (versions, limits, debug flags as on or off, object cache, https, timezone and locale; never database credentials or paths), the active theme, the active plugins by name and version (update status only from the existing update check; no check is run), recent PHP engine errors from WordPress's own debug log (the last 256 KB only; stack traces and free-form log output are skipped and counted, never returned; messages redacted on a best-effort basis and cut to 500 bytes; site directories removed and other absolute paths in messages reduced to their file names; the database user and host in connection errors masked; the arguments of a stack trace cut off; duplicates counted; newest first), overdue cron events by hook name (no arguments), the Site Health counts already stored (no test is run) and Steadhand's self-check. It makes no outbound request and writes nothing.
- `Steadhand\Redactor`, the redaction helper: `text()` masks secrets in free text (authorization and cookie headers, URL credentials, sensitive key/value pairs, JSON Web Tokens, PEM private keys, password hashes, common API token formats, application passwords, define() constants, long opaque strings, payment card numbers, database identities in connection errors and email addresses), and `value()` masks values under sensitive keys. It is best-effort: it reduces the chance of a leak and cannot guarantee there is none, and the class docblock lists what it does not catch. It fails closed.

### Security
- Redaction in `get-diagnostics` is best-effort. It masks common secret formats and reduces absolute paths, but it cannot guarantee that a log message holds no secret or path, and the tool's description says so.
- Media is read through two layers that apply the same rule. The rule: the attachment's own status is `inherit`, and its parent is none, missing, or of an allowed post type and not trashed. A file attached to a trashed post, to a post of a type that is not allowed (including a registered custom type, a block or a navigation post), or with its own status set to private, is refused with the standard text. Inside a Steadhand call, for an agent, the rule replaces WordPress's answer for the parent's status; outside a call, and for other users, WordPress's own rules still apply, and the attachment rule is still checked. The post tools still refuse attachments.
- The menu tools have their own checks. `get-menu` returns a classic menu only for a term with the requested ID in the menu taxonomy, and a block navigation post only when it has one of the statuses publish, draft, pending, future or private. Trashed and auto-draft navigation is refused and never listed. `list-menus` lists block navigation in those same five statuses, from the same list. Refusals use the same text as the other tools.
- A classic menu item's title and URL are the ones the public menu prints. Its linked object may be a draft, a private post or a type the post tools refuse; only its type, its ID, and that title and URL are returned.
- The read tools share one object check, which allows only a post that exists, is not trashed, has an allowed type and passes `read_post`. Custom CSS posts, privacy requests and private posts of a type registered with `map_meta_cap` off are refused, whether published or trashed.
- `get-rendered` blocks outbound HTTP requests, oEmbed fetches and oEmbed cache writes while it renders, so rendering a post does not contact other hosts or change its meta. It omits login/logout and navigation blocks whose output would reveal data the agent cannot read directly, and it suppresses user avatars wherever they are printed, so no Gravatar hash of an email address appears in the output.
- The post capability mapping never turns another component's `do_not_allow` into a grant, and it is off once WordPress is shutting down.
- The input rule for a tool runs only after the caller's Steadhand capability is checked, so a caller without `steadhand_read` learns nothing about the allowed post types.
- The agent lockdown is registered even when the MCP Adapter or the Abilities API is missing, and a later `rest_pre_dispatch` filter can no longer lift it.
- A user that holds the agent role and another role can no longer use its Application Passwords anywhere. Its cookie sign-in is unchanged.
- Agent credentials are refused everywhere except the Steadhand MCP endpoint: core REST routes, the batch endpoint, the abilities API, the MCP Adapter's default server, XML-RPC, `wp-login.php` and wp-admin. An agent's Application Password no longer works outside Steadhand, and an agent cannot sign in with its account password.
- Only a dedicated agent can connect: a user whose sole role is `steadhand_agent`. A user who also holds another role, such as an administrator given the agent role, is refused at the endpoint and in the pipeline, even if it holds the Steadhand capabilities.
