# Changelog

All notable changes to Steadhand are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html), starting at `0.1.0`.

## [Unreleased]

### Added
- `steadhand/update-menu` (SPEC section 5, D25): adds, renames, moves, hides and shows the items of a classic navigation menu, one operation per call. It needs `steadhand_menus`, `steadhand_read` and `steadhand_publish`, because a change is live on every page at once. It never deletes an item or a menu and never changes a theme location. `hide` sets an item to draft, which takes it off the public menu, and `show` brings back only an item that Steadhand hid. Saving the menu in Appearance > Menus shows a hidden item again, and the tool warns of that. Block navigation is refused. A move changes an item's parent and its place among its siblings, takes the item's children with it, and is refused when more than 50 items would change order. Its changes cannot be undone with `steadhand/undo-change`; each operation has an opposite call, and a rename is refused when the agent could not put the present title back. If an add fails after WordPress created the row, the error and the change log name the row.
- The Agents screen offers `steadhand_menus`, with a sentence saying it changes the public site at once and needs `steadhand_publish`.
- Uninstall removes the three menu marker keys from every menu item.
- `steadhand/get-menu` returns hidden items of a classic menu, and every item has a `hidden` field. A hidden item is one in the draft status, which the public menu does not print. This is the first step towards `steadhand/update-menu` (SPEC section 5, D25), which is not built yet.

### Changed
- The output of `steadhand/get-menu` has a new field, so an MCP client that connected before the update must reconnect.
- In `steadhand/get-menu`, an item's `order` now counts hidden items too.

### Security
- The capability mapping for `steadhand/update-menu` applies only inside a call of that ability (SPEC section 14.1). It grants `assign_term` on a menu and `edit_post` on a menu item, each only with `steadhand_menus` and `steadhand_publish`, and never `edit_theme_options`. The post meta capabilities on a menu item, and the comment capabilities for a comment on one, stay refused.
- A menu item's stored title, content and excerpt are kept byte for byte when an agent hides or shows it, so an administrator's markup in a title is not rewritten by the agent's save.
- `SECURITY.md` gives one way to report a vulnerability, GitHub private vulnerability reporting, now that the repository is public.
- `README.md` and `readme.txt` say to reconnect the MCP client after an update. A client that connected before the update keeps the old list of tools, so it does not see new tools and may reject a result that has a new field.

## [0.4.0] - 2026-11-25

### Added
- `steadhand/trash-post` and `steadhand/restore-post` (SPEC section 5). The first moves one post or page to the trash, and the second restores a post that the same agent trashed, and only while that trash is the current one. Both need `steadhand_trash`, which is off by default, and a restore to draft or pending also needs `steadhand_write_drafts`. Neither deletes permanently. Trashing a published, scheduled or private post also needs `steadhand_publish`. The restore brings a live post back as a draft unless the agent holds `steadhand_publish`.
- The Agents screen offers `steadhand_trash`, with a plain description of what it allows.
- Uninstall removes the four trash marker keys from every post.
- `steadhand/trash-post` refuses a sticky post with `steadhand_refused_sticky_post` (409), because core removes a post from the sticky posts when it is trashed and a restore does not put it back. The writer refuses it too.
- `steadhand/restore-post` sets a post that WordPress restores live to draft, with a status-only save, when the agent may not publish. A post that stays live is refused with `steadhand_update_partial`, and the message says an administrator should check it. The restore's own save and the slug save after it hold a live status down to the one the restore asked for, so a plugin's publish filter cannot make the post live. They leave a status that is not live as a plugin set it, and never raise a status. The draft save is only the backstop, and it runs before the slug save. A restore that fails after WordPress removed its trash time reports `steadhand_update_partial`, clears the markers and does not say "try again".

### Changed
- The dev-only updater needs no GitHub token now that the repository is public. It is turned on by a constant in the site's configuration (see `README.md` in the repository). It then sends no credentials and installs only the dev zip from this repository's release download URL. The release tag and the zip's name must carry the same version, and so must the plugin header when it can be read, or the release is skipped. A site that has the token constant and has not turned the new one on keeps updating with that token. With neither constant, the updater does nothing, as before. It is not part of the WordPress.org build.
- `readme.txt` opens its description with a pre-release warning, as `README.md` does: Steadhand has been tested only on its maintainers' own sites and has had no outside security review.

### Security
- WordPress deletes a trashed post permanently after `EMPTY_TRASH_DAYS` days, which is the site's trash period, unless it is restored. `steadhand/trash-post` refuses, with nothing changed, when that setting is zero or not a positive number, because WordPress would then delete the post at once.
- `delete_post` is granted to an agent only inside `steadhand/trash-post` and `steadhand/restore-post`, and only as those two abilities need it (SPEC section 14.1). Restoring a post clears its trash markers, so an administrator's later trash of the same post cannot be restored by the agent that trashed it earlier.
- `steadhand/restore-post` restores only a post the calling agent trashed itself, and only while that trash is the current one. The rule now needs exactly one row of each trash key, so a post an administrator moved out of the trash with a status update and trashed again is refused, even when the markers were left behind. Trashing stores four markers (the agent, the trash time, the post's modified time and its own ID), each closing a route the others do not: the modified time also refuses a post a later save changed, even with the listeners absent, and the ID refuses a copy of a trashed post.
- The trash markers are cleared by every route out of the trash and at the start of every new trash, not only by `wp_untrash_post()`. Stale WordPress trash keys are removed only once WordPress has allowed the trash, so a refused trash changes nothing. The listeners are registered whatever the dependency state, as the lockdown is.
- `delete_post` is refused, inside a Steadhand call, for the front page, the posts page and the privacy policy page, and for any post that the caller did not trash, inside `restore-post`. The front page is protected whenever `page_on_front` is set, whatever `show_on_front` says.
- A stored previous status that is not exactly one record restores the post as a draft.

## [0.3.2] - 2026-11-25

### Added
- The Agents screen can disable, enable and delete an agent (SPEC section 4.1). **Disable** stores the agent's `steadhand_connect` as false and revokes every Application Password, then checks both. **Enable** turns `steadhand_connect` back on and creates no password. **Delete** needs a confirmation box and the `delete_user` capability. It is refused, with nothing changed, when posts, revisions or links are attributed to the agent. Content that appears during the delete stops it before anything is removed: the user stays, and its connections stay revoked (`delete_has_content_revoked`). A successful delete removes only the user account, and its change-log entries are kept. The list gains a Status column (Disabled, Disabled (N connections remain), No connections or Active). Three new actions for extensions, documented in `docs/HOOKS.md`: `steadhand_agent_disabled`, `steadhand_agent_enabled` and `steadhand_agent_deleted`. A role added to the user during the delete stops it the same way (`not_agent_revoked`). The delete is guarded in the code that calls WordPress: no post is deleted with the user, and the checks run again as the first and the last listener of core's `delete_user` action. A disabled agent that still holds connections shows "Disabled (N connections remain)".
- The Agents screen shows how to connect an MCP client (SPEC section 4.1). An agent's detail view has a **Connect a client** section with the endpoint, the transport, the username, the Claude Code command with a placeholder for the Base64 value, help for other clients, and how to check the connection; it never shows a password. The one-time panel after a create or an add shows the finished Claude Code command and the header value, once, with the password. The command is printed only for an endpoint on an allowlist of plain characters (no `!`, `%`, `$`, quotes or other shell-special characters, and no IPv6 host), and the endpoint is always in double quotes; for a login with a colon, which HTTP Basic cannot carry, neither the command nor the header value is shown. The warning says not to add `--scope project`, which would write the password into a `.mcp.json` file. Rendering only: no hook, option or stored value is added.
- `readme.txt`, the WordPress.org readme. It fills the plugin details popup in wp-admin and ships in both release zips. `bin/build.sh` fails if its `Stable tag` differs from the version being built.

### Changed
- Adding a connection to a disabled agent is now refused (`agent_disabled_no_password`), before any password is made. Unticking Connect in the capabilities form still does not revoke the agent's connections; the status shows how many remain, and Disable revokes them.
- Creating an agent with Connect unticked is now refused (`connect_required`), before any user or password is made, and the add form is redrawn with the posted values. A new agent makes its first connection, so it must be able to connect. To make an agent that cannot connect, create it and then disable it. A create that leaves other capabilities unticked still works.
- The rollback of a refused create never deletes a post: the delete it makes is guarded the same way as the Delete action (SPEC section 4.1). A create whose rollback finds content only during its own delete keeps the user (`create_failed_user_kept`) where it reported a cleanup failure.

## [0.3.1] - 2026-11-25

### Changed
- The Agents screen has three views (SPEC section 4.1): the list of agents, which has no forms; one agent's detail (`agent=<id>`), with its capabilities, its connections and the link to its change-log entries; and the add form (`view=new`). A detail request for an ID that is not a dedicated agent shows the "not a dedicated agent" notice and the list, and nothing about that user.
- Creating an agent sets its capabilities. The form has one checkbox for each offered capability, checked as the role's defaults say. Only offered capabilities are read from the form, and any other name is ignored. Each offered capability is written to the user as true or false before the Application Password is made, and read back. Every other Steadhand capability is written as false, so a grant something else gave the agent role never reaches a new agent. A refused create redraws the form with the choices as posted, not with the defaults. The final check compares the user's stored capabilities with the chosen ones, and a difference is refused and rolled back, with no password shown. A form without the capability marker keeps the role's defaults. Creating an agent does not fire `steadhand_agent_capabilities_changed`.
- On the Agents screen, the name of an Application Password is called the "connection name", where it was "label". The agent label in the change log is unchanged.
- Revoking a password, revoking all of them and saving an agent's capabilities return to that agent's detail view, not to the list.
- **Behaviour change to a public action:** `steadhand_admin_agent_row` (released in 0.3.0) now runs once, in the detail view of the agent shown, after its sections. In 0.3.0 it ran once for each dedicated agent in the list. It does not run in the list view or the add view. Its name and its parameter (`$agent`) are unchanged, but a listener that printed one block per listed agent now prints once, in the detail view (`docs/HOOKS.md`).

## [0.3.0] - 2026-11-24

### Added
- An **Agents** screen under **Steadhand** in the admin menu (SPEC section 4.1). An administrator creates an agent, a user whose only role is `steadhand_agent`, with its first Application Password. The password is shown once, in the response to that form, and is stored nowhere else. The administrator adds or revokes an agent's Application Passwords (at most 10 per agent) and turns its Steadhand capabilities on and off, for the capabilities a registered ability uses. Every action needs a nonce, `manage_options`, `list_users`, no agent role on the caller, and the native capability for the act (`create_users`, or `edit_user` for the agent). On a multisite network every action is refused and the screen shows only a notice (D13). A new agent is checked again after its user and its password are written: it must hold only the agent role under the posted login, or the create is refused and no password is shown. A refused create is rolled back: its passwords are revoked, and its user is deleted, unless posts or links are attributed to that user, in which case the user is kept with no role and no password (`create_failed_user_kept`), so no content is ever deleted. A listener that throws during a create is caught and refuses the create. Notices that said too much are corrected: a revoke that fails says so (`revoke_failed`), and so does capabilities saved for a user who is no longer an agent (`capabilities_unverified`). The label is counted in characters and refuses invisible, control and separator characters. Only a dedicated agent can be changed: an administrator, an editor or a user who also holds another role is refused, and no Steadhand capability or password reaches such an account. Application Passwords need HTTPS, and the screen says so when they are not available.
- Three admin extension points for Pro and third parties: the actions `steadhand_agent_created`, `steadhand_agent_capabilities_changed` and `steadhand_admin_agent_row` (`docs/HOOKS.md`).
- An **Undo this change** button on the change-log screen's single-entry view. An administrator who holds no agent role can reverse one change made by `update-post`, `edit-blocks`, `set-post-terms` or `set-featured-image`, under the same unchanged-since rules as `steadhand/undo-change`. The undo is recorded in the change log under the administrator's user ID. It is not an ability and is not reachable over MCP. It is refused while the post has a live edit lock, held by any user, the administrator's own session included, and it is not offered to a user who holds the agent role.
- A read-only change-log screen under **Steadhand** in the admin menu (SPEC section 7). It shows a filterable list (agent, tool, result, and date in the site's timezone), 50 entries a page, and a single-entry view with the entry's stored fields, its input and a diff of the change. Only an administrator sees it, never an agent. The diff of post text needs `edit_post` for that post; without it the diff is not shown. The message, guardrail notes and input of an entry about a post are hidden from a viewer who may not edit that post (the list and the single view show a note instead). An entry about no post is always shown. The undo button is added by the entry below. The screen is registered before the dependency check, so the log can be read while the MCP Adapter is missing.
- Two admin extension points for Pro: the actions `steadhand_admin_log_toolbar` and `steadhand_admin_log_entry` (`docs/HOOKS.md`).
- `steadhand/undo-change` reverses a `steadhand/set-post-terms` change, which puts the post's terms in that taxonomy back to the set they had, and a `steadhand/set-featured-image` change, which sets the image back to the one the post had or removes it. An undo of these is a call the agent could make itself: it runs under the rights and input rules of the original call, under the rights the agent holds now, and it refuses, with nothing changed, if the terms or image changed since, or if a term or image the saved state names no longer exists. The undo's own refusals are listed in SPEC §5.
- A snapshots table, `{prefix}steadhand_snapshots` (SPEC §7), holds the before and after state of a terms or featured-image change. Its rows are pruned with the change log, on the same retention. The schema version is `3`; an update from version 2 keeps every log row.
- The self-check and `steadhand/get-diagnostics` report `snapshots_ready`, the state of the snapshots table, on its own.
- `steadhand/undo-change` reverses one `update-post` or `edit-blocks` change of the calling agent, by its change-log entry. It restores the post's title, content and excerpt to the before-revision, and only when the post still holds the text the change left and no revision of the post was created after the change's after-revision (creation order, by ID, never by date). The check is made before the save, and again in a `pre_post_update` action, which core fires immediately before its UPDATE of the posts table. When a mismatch is found, a query filter blanks that one UPDATE, so the save writes no row and no revision. Two causes can stop that blank from applying: a posts table whose charset is not utf8, utf8mb3, utf8mb4 or latin1 (wpdb issues a conversion query first), and another plugin's `query` filter that rewrites the statement. In either case the overwrite may land, and the call returns `steadhand_update_partial` with the text that says the restore could not be stopped. Between the action's read of the row and core's UPDATE statement, a concurrent request can change the row, and the save then overwrites that change; nothing in this process closes that gap. The undo is not itself undoable. Status, slug, date and author are not sent; the save is WordPress's own, as for `update-post`. The restored text is stored as it was, without the content rules, and the save filters do not change it. An undo saves a new revision, so the same post's older changes cannot be undone afterwards. It marks the entry with the ID of the undo's own change-log row, so `get-change-log` shows it as `undone`.
- The change log records the state a write leaves, in a new column `after_snapshot_id`. For an update that changes the post, it is the ID of the core revision that holds the post's title, content and excerpt after the write, as stored. It is preparation for undo (M3): undo will use it to check that the post has not changed since the write. It names only a revision this request created during the write that holds exactly the text the write stored, so the state after is always the text the call stored. A save by another person or agent that changes the post before the after-state is checked, or a plugin that rewrites it in the same request, makes the call not undoable. A change that lands after that check leaves the call undoable, and undo checks the post itself. The table gets a new layout version (2). An existing table gains the column on the first request after the update, and its rows are kept. Rows written before this version have 0 there and are set to not undoable.

### Changed
- The guardrails evaluate an undo twice: first as `steadhand/undo-change`, then as the direct call it amounts to (`steadhand/set-post-terms` or `steadhand/set-featured-image` with the input the undo writes with, or `steadhand/update-post` with no content for post text). A rule that limits the direct call now limits the undo, and a rewrite of that call refuses the undo. Other abilities are evaluated once, as before. See `docs/HOOKS.md`.
- An undo whose direct call cannot be determined is refused, and the guardrails' second evaluation is never skipped. The direct call the guardrails checked is checked again before the write, and the undo writes nothing if it changed.
- Notes from the second evaluation no longer cut the block note of the direct call, and a note both evaluations produce is recorded once.
- A terms undo returns the warnings the direct `set-post-terms` call with the same set gives (a moved permalink, a post left with no category).
- A post with more than 100 terms in the taxonomy before a change is not saved as undoable, and the call says so.
- An undo refused for an image the caller can no longer read, a taxonomy whose assign capability was revoked, or a post type no longer allowed gets the generic refusal, as a direct call would.
- `steadhand/set-post-terms` and `steadhand/set-featured-image` record the state before and after a change that changes the post, so the change is undoable. Their warnings no longer say "Steadhand cannot undo this change yet" (or "a post's terms yet"). A call that changes nothing stays not undoable. If the state before cannot be saved, the call still succeeds, is not undoable, and says so in its warnings.
- `steadhand/undo-change` accepts an entry of either tool. The pipeline's capability check for it is the union of what the three underlying abilities need, and the undo itself checks the capability of the ability that made the entry, so an agent holding only a capability one of them does not need cannot undo that entry.
- `steadhand/get-change-log` reports `undone` as true once `undo-change` has undone an entry. Before, it was always false.
- A write is recorded as undoable only when the state after it was also saved (`after_snapshot_id`). Before, an update was undoable when its before-state was saved. Nothing else about the undoable flag changes.
- A change that was undoable before the change but whose state after could not be saved is not undoable, and its `warnings` say so: "Steadhand could not save the state after this change, so it cannot be undone." The warning is added unless the output says the call changed nothing (`changed` is exactly `false`), so a call whose output has no `changed` key is warned too. When the list of warnings is already full, the last warning is replaced by this one, so the count stays within its cap.
- The change log's table is recorded as upgraded only when it has every column the code writes (`Schema::ready()`). Before, the version was recorded as soon as the table existed, so an upgrade whose `ALTER` was refused was never retried, and every later write failed. The self-check's `change_log_ready` uses the same check, and a refused upgrade is retried after an hour.

## [0.2.1] - 2026-11-23

### Security
- An exception thrown during Steadhand's permission check could reach the agent. The check calls the ability's input and object rules, and `current_user_can()`, which runs other plugins' `map_meta_cap` and `user_has_cap` filters. Steadhand did not catch a throw from those calls, so the exception's message reached the agent as the tool's error text, and that message can contain a file path or internal detail. The text came through WordPress core's ability callback wrapper or the MCP Adapter's guard. Affects 0.1.0 and 0.2.0, which both run the same unguarded `authorize()` call in `check()` and `run()`.
- Fixed: a throw during the permission check now fails closed. The call is refused with `steadhand_error` (500) and the fixed message "The permission check could not be completed, so the call was refused. Another plugin or the site raised an error during the check. Ask the site administrator.", and it is logged once as `blocked` with that message. A refused call is not counted toward the rate limits (30 writes a minute, 100 uploads a day), so a call that never ran uses none of the budget. Nothing runs after the throw. A throw that escapes the pipeline entirely is turned into an error by the ability callbacks and is not logged: the generic `steadhand_error` text for reads and for permission checks, and the "may have been partly applied" text for the execute callback of a write. The exception message is never returned or logged.
- Fixed: an input rule that returns anything other than `true` or a `WP_Error`, such as `false`, now refuses the call with `steadhand_invalid_input` (400), "The input was refused.", and it is not run. Before, `false` was accepted.

### Changed
- Over MCP, the text of a refusal or failure that Steadhand returns now ends with its error code in parentheses, for example `(steadhand_forbidden)`. The MCP Adapter passes only the text and `isError` to the client, so the code was lost. The change log stores the message without the code. Refusals from WordPress's own input-schema check, and errors raised by the MCP Adapter itself, carry no code.
- The execute-time refusal for an object that stops being accessible during a call changed from `steadhand_not_found` (404) to `steadhand_forbidden` (403), with the same text as the permission-stage refusal. `steadhand_not_found` was in release 0.2.0. The code is now visible to the agent, so it must not show that an object changed during the call; every object refusal now has one code and one status.
- For `update-post`, `edit-blocks`, `set-post-terms`, `set-featured-image`, and `upload-media` with the post as `parent`: when the agent can read a published, scheduled or private post and does not hold `steadhand_publish`, the refusal now says that the post needs `steadhand_publish`, instead of "Not found, or this agent may not access it." An agent that holds `steadhand_publish` always gets the generic text for these posts. The other capabilities the agent holds do not change this (`steadhand_write_drafts` and `steadhand_media` are not part of the condition). The code (`steadhand_forbidden`), the status (403) and the rule are the same, nothing is changed, and the change log still records the call as blocked. A missing, trashed, unreadable or disallowed post, and a draft, keep the generic text.

### Fixed
- The refusal for a status other than draft, sent without `steadhand_publish` to `create-post` or `update-post`, said the post was saved as a draft. The call is refused and nothing is saved, and the text now says so.
- `modified` in the create-post and update-post output, and `modified_gmt` in the post and media tools, were null for a new draft, because WordPress stores its GMT date as zero. They now fall back to the local modified date, so a new draft has a date.

## [0.2.0] - 2026-11-23

### Added
- Change log, in the table `{prefix}steadhand_log`. It records every refused call (`blocked`) and every failed call (`error`) to any Steadhand ability, including refusals at the permission check. Successful calls to read-only abilities that need `steadhand_read` are not recorded, unless the `steadhand_log_read_calls` filter returns true. Other successful calls are recorded. Each entry stores the time (UTC), the agent user ID, the agent label (the name of the Application Password), the ability, the object the call named (for `get-post`, `get-blocks`, `get-rendered`, `get-post-terms` and `get-media`: the ID the caller asked for, even when the call was refused), the result, the message, any guardrail note, and the call's input. The input is redacted, keys as well as values, and stored as JSON, capped at 16 KB. Larger input is stored as a summary (its original size and its top-level key names, each redacted), not cut in the middle. Input over 256 KB is not scanned at all.
- `steadhand/get-change-log` (`steadhand-get-change-log`), the thirteenth tool. It returns the calling agent's own entries, newest first, with paging and filters for result, ability and date. It never returns another agent's entries or any stored input. If the log cannot be read, it returns `steadhand_log_unavailable` (503) rather than an empty list.
- Retention of 30 days. Entries are pruned when a new entry is written, at most once a day, in batches of 1,000 rows and up to 20 batches per pass. A pass that runs out of batches is continued by the next write. Nothing runs on WP-Cron, so entries older than the period remain while nothing is being written.
- Three extension points, documented in `docs/HOOKS.md`: the filters `steadhand_log_read_calls` and `steadhand_log_retention_days`, and the action `steadhand_log_entry_stored`.
- `change_log_ready` in the self-check of `steadhand/get-diagnostics`: whether the change-log table exists.
- The change-log table is created on activation, and on the first request after an update when its recorded schema version is missing or different. If that create fails, the request-time retry waits an hour, and database errors from it are never printed.
- Uninstall drops the change-log table and removes its two options, `steadhand_db_version` and `steadhand_log_last_prune`. As with the rest of uninstall, this runs only when the Composer autoloader is present.
- `steadhand/create-post` (`steadhand-create-post`), the fourteenth tool, and `steadhand/update-post` (`steadhand-update-post`), the fifteenth. They are the first write tools. Both run through the write path described below. Neither can set a post's author, password, parent, terms or meta. Post meta is not part of M2 (SPEC §14, D18): no allowlist is defined.
  - `create-post` takes `title`, `content`, `excerpt`, `slug`, `status`, `date` and `post_type`. The author is always the calling agent. `status` defaults to `draft`. `pending`, `publish`, `future` and `private` need `steadhand_publish`. A `date` is allowed only with status `future`, where it is required. `post_type` must be an allowed type (`post` and `page` by default). Title or content must be non-empty.
  - `update-post` takes `id` and at least one of `title`, `content`, `excerpt`, `slug`, `status` and `date`. It changes only the fields sent, and only where they differ from what is stored. `content` replaces the whole content. A post's type cannot be changed. A scheduled post cannot be published early by this tool: WordPress keeps it scheduled, and the result says so in `warnings`.
  - Limits: title 400 characters, excerpt 5,000, slug 200 (lowercase letters, digits and single hyphens), content 262,144 characters and 256 KB in bytes (checked by the content guardrail). `date` is ISO 8601, read as UTC when it has no offset, at least 60 seconds and at most 10 years ahead.
  - Output: `id`, `post_type`, `status`, `title`, `slug`, `link`, `modified`, `changed`, `content_modified_on_save`, `warnings` and `guardrail_notes`. `content_modified_on_save` is true when WordPress stored a title, content or excerpt that differs from what was sent.
  - Publishing a draft needs both `steadhand_write_drafts` (to edit the draft) and `steadhand_publish` (to set the live status). Editing a live post needs `steadhand_publish`, and so does moving a live post back to draft. `update-post` also needs `steadhand_read`, to read the post it edits.
  - `update-post` saves a WordPress revision of the post before it changes the title, content or excerpt, when revisions are available. `warnings` says when none could be saved. The log row's `undoable` flag is 1 only when a revision was found, the site keeps two or more revisions (or unlimited ones), and the call changed only title, content and excerpt. With one revision kept, WordPress removes the revision on the save that follows, so the change is not undoable and `warnings` says so. Steadhand does not claim undo for status, slug or date. `create-post` rows are recorded with `undoable` 0, because there is no earlier state to save. Undo is milestone M3.
- `steadhand/edit-blocks` (`steadhand-edit-blocks`), the sixteenth tool and the third write tool. It changes some blocks of one post, by the path `get-blocks` returns, without resending the whole content. A call takes one to 20 operations: `replace`, `insert_before`, `insert_after`, `remove` or `append`. An operation that names a block must send that block's name, and a path whose block has another name is refused. Blocks that no operation names are stored byte for byte, and are not passed through the save filters. Only the markup the call sends, and the separators Steadhand adds next to it, are filtered by WordPress, as for a user without unfiltered HTML. A filtered result is what is stored; the call succeeds, with `content_modified_on_save` true and a warning. The markup of each operation must be complete blocks on its own, with no HTML comment that is not a block comment (a break comment is allowed only as the sole inner content of its `core/more` or `core/nextpage` block), and must still be complete blocks after filtering. The block delimiters of the final content must come only from the stored blocks kept and the markup sent, so a delimiter cannot be completed across two places. Markup that leaves HTML open (an unclosed script or textarea) is refused when stored content follows it, and so is a removal that joins HTML left open to the content after it. A stored post whose HTML is left open before the place of the edit (an unclosed script, comment, textarea or attribute value) is refused, and so is an edit that would change blocks it does not name, with `steadhand_refused_unsupported_markup` (409), each with its own message. The guardrails see exactly the bytes that will be stored: the guard records a hash of the content it checked, the plan refuses unless its own preview has that hash, and the write refuses if the content it assembles differs. WordPress's display split cuts the post at a `wp:more` delimiter, and its pattern can run past a void delimiter. The check covers the whole result: every match must be one whole delimiter, or an untouched match inside one kept range. A sent markup that fails it is refused with `steadhand_invalid_input` (400), and an edit whose result fails it with `steadhand_refused_unsupported_markup` (409). Where WordPress has the custom-CSS strip for blocks (WordPress 7.0 and later), it runs on every Steadhand write, also for a user who holds `edit_css`; on WordPress 6.9 there is no such strip, so none runs. It uses the permissions, revision, partial-failure and output rules of `update-post`. It refuses, with nothing written: `steadhand_refused_block_mismatch`, `steadhand_refused_content_changed` and `steadhand_refused_unsupported_markup` (409), `steadhand_invalid_input` (400), and `steadhand_update_failed` (500) when the content changed between the check and the write. A refusal raised while the write is prepared is logged as `error`, and a guardrail or input refusal as `blocked`. The change log stores a digest of each markup, not its text. A post over the content limits cannot be edited with this tool. The first child of an empty container block cannot be added: replace the container instead.
- Revisions mirror the post's row. A revision of a post, saved before an edit or after it, takes its title, content and excerpt from the stored row, read again when it is saved, never from the call. The save filters therefore never change a revision: an administrator's stored markup, and the bytes an edit does not touch, survive in every revision, and `undoable` stays 1 on a second edit. This applies to `update-post` too. Autosaves are not changed.
- `steadhand/set-post-terms` (`steadhand-set-post-terms`), the seventeenth tool and the fourth write tool. It sets which existing terms of one allowed taxonomy a post has, by term ID, with `replace` (the default), `add` or `remove`. It never creates, renames or deletes a term, and it refuses names. It runs through the write path, the guardrails and the change log. It needs `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` by the post's status, as `update-post` does. A taxonomy whose own assign capability is not core's default must also be held by the caller (decision D21). Steadhand checks the permission again immediately before the write, and refuses the call if the terms changed while it ran. Steadhand cannot undo a term change yet, so the result returns `previous_term_ids`, and the result returns the post's `link`. A published post that moves to a new address gets a warning. Details in `docs/SPEC.md` §5.
- `steadhand/upload-media` (`steadhand-upload-media`), the eighteenth tool and the fifth write tool. It adds one image to the media library from a base64 payload (`data_base64`). It does not fetch from a URL. Accepted: JPEG and PNG, judged from the bytes, with a file name extension that matches, 1 byte to 5 MB decoded, each side 1 to 8000 pixels, and at most 16 million pixels. The file name is one base name of letters, digits, `_` and `-` (at most 80 characters) and one extension, with no spaces, accents, paths, second dots or Windows device names. GIF, WebP and SVG are refused (WebP is not accepted at all: a WebP whose canvas differs from its frame makes GD raise a fatal error when core decodes it); so are an animated PNG, a damaged PNG container, a JPEG with more than 50 scans, and any file that contains `<?php` (a best-effort check). The memory the decode needs is checked before the row is reserved, and again before the file is written. A file is public at once at its uploads URL. It needs `steadhand_media` and `steadhand_read`, and an optional `parent` must pass the `update-post` check. The change log keeps the digest of the decoded bytes, never the payload. Steadhand cannot undo an upload yet. Details in `docs/SPEC.md` §5.
  - Upload hardening, before the release: the file is written to an exclusively created temporary file; core's sideload result is checked again (type, extension, content type, location inside the uploads directory and SHA-256 of the payload); the parent is checked again just before the row is made; core's metadata must have a width and a height, or the file and row are removed; a PHP fatal error during a write is cleaned up by a filter on WordPress's fatal error handler (`wp_php_error_args`, which core applies before it calls `wp_die()`), with a shutdown function as the fallback. The stored file is removed only when its SHA-256 is the payload's, and the temporary file is named from `random_bytes()`. Steadhand does not decode the image itself; core decodes it when it makes the sizes.
- `steadhand/set-featured-image` (`steadhand-set-featured-image`), the nineteenth tool and the sixth write tool. It sets or removes (`media_id` 0) a post's featured image, to an image the agent may read. It needs `steadhand_media`, `steadhand_read`, and `steadhand_write_drafts` or `steadhand_publish` by the post's status. It refuses a change if the featured image moved while the call ran, and reports `previous_featured_media`. Steadhand cannot undo this change yet. Details in `docs/SPEC.md` §5.
- `includes/Pipeline/MediaWriter.php`, the only place that creates an attachment or sets a featured image. It runs only inside a write, and removes what a failed store left behind.
- Capability mapping for dedicated agents, during Steadhand calls only. `read_post` needs `steadhand_read` in every Steadhand call. `edit_post` and `publish_post` apply only during a write call, so inside a read tool (such as `get-rendered`, where a shortcode runs) core's answers stand and an agent is refused. `edit_post` needs `steadhand_write_drafts` for draft, pending and auto-draft posts, `steadhand_publish` for published, scheduled and private posts, and is refused for any other status. `publish_post` needs `steadhand_publish`. `delete_post` is not mapped, so it is refused. Attachments are readable only through the media rule, and edit, publish and delete are refused on them. Outside a Steadhand call, WordPress's own answers stand.
- Write path. A write runs in a fixed order: validate, authorize, guardrails, log reservation, snapshot, execute, log completion. Its log row is reserved before the change. If the row cannot be reserved, the write is not performed and the call fails with `steadhand_log_failed`. If the change is made but its outcome cannot be recorded, the call fails with `steadhand_log_incomplete`, and the message says the change was made. A refused write is recorded as `blocked` and does not run.
- Guardrail engine (`Steadhand\Guardrails`). A rule returns allow, block (refuse, with a message), warn (allow and record a note) or fix (run with a rewritten input, which is checked again before use). Built-in rules cannot be removed. A rule that throws, or returns anything other than a result, blocks the call. A blocked write fails with `steadhand_guardrail_blocked` (HTTP status 422) and the rule's message.
- Built-in guardrail rules. All five block. None rewrites or warns yet.
  - `steadhand/content-limits`: refuses content over 256 KB, more than 2,000 blocks (nested blocks count), nesting deeper than 20 levels, and content that is not valid UTF-8. Content exactly at a limit passes.
  - `steadhand/block-markup`: refuses block comment delimiters that are malformed, unbalanced or out of order, and attributes that are not valid JSON. This is a structural check only. It does not run the editor's save-output validation, does not check that a block name is registered, and does not check attributes against a block's schema.
  - `steadhand/rate-limit`: at most 30 writes per agent in any rolling 60 seconds, counted from the change log. A write counts from its reservation, including a write that then fails. Refused calls do not count. Both rate rules read the count before the row is reserved, so they are best effort under concurrent requests. The `steadhand_rate_limit_per_minute` filter can set the limit from 1 to 600. It cannot turn the limit off.
  - `steadhand/daily-upload-limit`: at most 100 `steadhand/upload-media` calls per agent in any rolling 24 hours, counted from the change log with the same count as the rate limit. Like the rate limit, it is best effort under concurrent requests. A refused upload is logged as blocked, with the rate limit's error. A count that cannot be read refuses the upload. The limit is a class constant, not a filter.
  - `steadhand/edit-lock`: refuses a write to a post that another WordPress user has open in the block editor. The window is WordPress's, 150 seconds by default, and the `wp_check_post_lock_window` filter can change it. The refusal does not name the other user.
- Extension points, documented in `docs/HOOKS.md`: the action `steadhand_register_guardrails`, the filter `steadhand_rate_limit_per_minute`, and the public classes `Steadhand\Guardrails\Rule`, `Context`, `Result` and `Registry`.

### Changed
- Steadhand can now change posts. Release 0.1.0 wrote nothing to a site. An agent that holds `steadhand_write_drafts` or `steadhand_publish` can create and update posts. A new agent holds `steadhand_write_drafts` by default. The read tools are unchanged.
- For a write, the change-log row is reserved before the change and completed after it. For a read call, the single entry is still written after the call has run.
- Snapshots are never autosaves. The snapshot is the newest non-autosave revision whose title, content and excerpt equal the post's current ones exactly. The revision limit is ignored when it is looked up. A snapshot ID is kept whenever a revision was found, even when `undoable` is 0.
- A call that sets status, slug or date gets the warning "This change includes status, slug or date, which Steadhand cannot undo yet."
- A write sets the post date only when a date is sent. WordPress gives a draft with no set date the time it is published, so publishing an old draft does not backdate it. A scheduled update keeps the requested date.
- Post content in the change log is stored as a digest of the text as submitted, before WordPress filters it on save: its byte count and SHA-256, written as eight groups of eight hex digits separated by colons, whatever its size. An excerpt over 500 bytes is stored the same way. The digest matches the stored content only when `content_modified_on_save` is false. The revisions hold the text. A call that fails validation is logged with the same digests, so its content text is not kept either, and a value that is not text is logged as its type.
- If a write's execute step throws, the caller and the change log get "The change could not be completed and may have been partly applied. Check the result before you continue." The code is `steadhand_error`. The read path's message is unchanged.
- `update-post` handles its own write errors. When WordPress reports an error, or the write throws, the post is read again. If it changed, the error is `steadhand_update_partial` (500): "The post was changed, but the save did not finish as expected, so the change was at least partly applied. Check the post before you continue." The same error and message are returned when a field the call did not send differs from what was stored after a write that reported no error. Only when nothing changed is the error `steadhand_update_failed`, with "nothing was changed".
- `update-post` refuses, with `steadhand_refused_invalid_template` (409), a post whose page template the active theme does not have. WordPress validates the template after it has written the row, so this is refused before any write. Nothing is changed.
- New warnings. `Making a post private removes its password.` when a protected post is made private. `WordPress stored the status "<stored>" instead of "<requested>".` when WordPress stores another status, in both tools. `This site keeps too few revisions for Steadhand to undo this change.` when the site keeps one revision or none.
- Known limits of `update-post`: `wp_update_post()` re-normalises some values an administrator stored in an unusual way by a direct database write. An empty `comment_status` on an update becomes `closed`, a non-canonical slug is sanitised, a post with no category gains the default category, and `to_ping` is sanitised. Steadhand does not restore them.
- The block markup check's loose delimiter test is case-sensitive and needs whitespace after `<!--`, as WordPress's parser does. So `<!-- WP:Engine cache note -->` and `<!--wp:x-->` are no longer refused. Known false positive: text that looks like a malformed delimiter inside a `core/html` block, or inside an ordinary HTML comment that starts with `<!-- wp:`, is still refused.

### Fixed
- A content digest in the change log could be partly masked as `[card]` when its digits looked like a payment card number, because the digest's groups were separated by spaces. Digests are now grouped with colons (`PostFields::group_hex()`). Rows written before this change keep the space-separated form. The change log first ships in this release (0.1.0 has none), so only development installs can hold rows in the old form.

### Security
- `get-rendered` could print data the agent may not read, in two ways. Core's `[gallery]` and `[playlist]` shortcodes listed media that `get-media` refuses (through `ids`, `include`, or the children of `id`) and the children of a post that `get-post` refuses. Some core blocks also printed data outside the agent's read grant: legacy widgets (a stored widget, or a media gallery widget that bypasses the shortcode guard), blocks bound to post meta, breadcrumbs (the title and link of every ancestor), author biographies and author archive links, and the width and height of a video attachment the agent may not read. Now such a shortcode or block renders as nothing, and the rest of the post still renders. Blocks nested in navigation, navigation submenu, navigation link or widget group blocks were not omitted, including the logout link, because those blocks render their children without the block filter. The guard now also runs on each block's rendered output, and navigation links and submenus bound to post or term data are omitted. Affected 0.1.0.
- Refusal throttle. For each agent user, at most 60 refused calls are stored in any rolling minute. Then one marker row records that further refusals are not being logged, and nothing more is stored until the minute has passed. The refusals themselves are still returned to the caller. Errors are never throttled or dropped. The count and the insert are not locked together, so concurrent calls can store slightly more than 60.
- Successful calls are logged unless they go to a read-only ability that needs `steadhand_read`. An ability that is marked read-only but needs a write capability is logged on success too.
- Keys in logged input are redacted as well as values, so a token used as a key does not reach the log.
- Logging does not fail open. On the call path, when a call's entry cannot be stored, the call returns `steadhand_log_failed` in place of its result. On the permission-check path, a refusal is returned whether or not its entry is stored, so a refused call is never allowed through.
- Redaction of logged fields is best-effort. It uses the same helper as `get-diagnostics`, and it cannot catch a secret that no pattern recognises (see the class docblock of `Steadhand\Redactor`).
- The block markup check is structural only. Content that passes it can still show a block-validation warning in the editor, and block names and attributes are not checked against the site's registered blocks.
- Content saved by a write is filtered by WordPress's post KSES rules for the agent, which does not hold `unfiltered_html`. A tag that WordPress does not allow for the agent is removed on save, and the text between tags is kept. `content_modified_on_save` reports when the stored text differs from what was sent. A field the call does not send is not filtered: it is saved as stored.
- The post capability mapping applies only during a Steadhand call, so an agent cannot edit posts through core's REST API. The existing lockdown still refuses its credentials there.
- The rate limit is 30 writes per agent per minute by default. The filter can change it but cannot turn it off.
- The edit lock refuses a write to a post that another user has open in the block editor, so one person's save does not overwrite another's open edit. The lock is read as WordPress's `wp_check_post_lock()` reads it: the text before the colon is the time and the text after it is the user, with numeric casts, so a lock with a leading space or a trailing newline is read as WordPress reads it. A lock in WordPress's older format (a timestamp with no user) takes its holder from `_edit_last`. A fresh one with no holder, holder 0 or another user blocks. The agent's own lock passes.
- Capability guard. Steadhand's own capabilities are set by a `user_has_cap` filter at the last priority, so no other plugin's filter can grant or remove one. Other capabilities are not changed. "The value stored for the user" means the user's capabilities as WordPress loaded them: code that runs inside the site and rewrites them is trusted. Multisite is not supported: a super admin passes core's checks before the guard runs.
- `edit_post` and `publish_post` are mapped only during a write call. If core asks for anything beyond the post type's own capabilities, the answer is refused. So a draft privacy policy page cannot be edited or published by an agent. A post type registered with `map_meta_cap` false is never allowed (see the fix below).
- On update, the post-field KSES filters are in place for the whole save, for every field, as on create. No Steadhand code removes a KSES filter or the Global Styles filter during a write, so code that runs during the save, such as a `save_post` listener, is filtered too. A field the call does not send is put back, byte for byte, as it is stored, for that one post, after the save filters have run. The restore acts once, on that post's own update, and is removed afterwards. The fields the call sends are filtered. This is safe because the agent cannot influence an unsent value (the update allowlist does not include it), and every value the agent has sent was filtered when it was stored. A save filter on this site that would change an unsent field no longer refuses the call: the field is kept as stored. A change to an unsent field made after the restore is reported as `steadhand_update_partial`. Steadhand never calls `kses_init_filters()` or `kses_remove_filters()`.
- A guardrail's fix is checked again with the ability's schema and object check. A fix that changes the object the call is about is refused with "A guardrail changed which object this call is about, so it was refused."
- Fixed: once a site owner allowed a post type registered with `map_meta_cap` false through `steadhand_allowed_post_types`, Steadhand could reach its posts. `create-post` could create them (published too), `update-post` and `edit-blocks` could change them, the read tools could read them in any status, `list-posts` could count them in `total`, and `get-media` could serve a file whose parent was one of them. Core makes none of its per-post checks for such a type, and for some types it renames the capability to one the agent holds. A type registered with `map_meta_cap` false is now never allowed, whatever the filter returns, so none of these paths reaches it (SPEC §14.1). A type that sets `capabilities` or its own `capability_type` needs `'map_meta_cap' => true` in its registration to be allowed. MetaCaps still refuses it as a second layer. Nothing was exposed by default: the default post types are still `post` and `page`, and a type with `map_meta_cap` on is not affected.

Content over 256 KB is cut on a UTF-8 boundary and flagged. Refused, trashed and missing posts get the same message.

Both return public URLs and never server file paths, image metadata (EXIF, IPTC, GPS) or user email or login. Only media the media rule allows is returned: its own status must be `inherit`, and it must be unattached, attached to a post that no longer exists, or attached to a post of an allowed type that is not in the trash. Trashed media is never listed, and `total` counts only the media that is listed.

A generated size with an overlong name or MIME type, or with no usable file name, is left out. One odd attachment therefore never fails a call.

It is best-effort: it reduces the chance of a leak and cannot guarantee there is none, and the class docblock lists what it does not catch. It fails closed.

### Security
- Redaction in `get-diagnostics` is best-effort. It masks common secret formats and reduces absolute paths, but it cannot guarantee that a log message holds no secret or path, and the tool's description says so.
- Media is read through two layers that apply the same rule. The rule: the attachment's own status is `inherit`, and its parent is none, missing, or of an allowed post type and not trashed. A file attached to a trashed post, to a post of a type that is not allowed (including a registered custom type, a block or a navigation post), or with its own status set to private, is refused with the standard text. Inside a Steadhand call, for an agent, the rule replaces WordPress's answer for the parent's status; outside a call, and for other users, WordPress's own rules still apply, and the attachment rule is still checked. The post tools still refuse attachments.
- The menu tools have their own checks. `get-menu` returns a classic menu only for a term with the requested ID in the menu taxonomy, and a block navigation post only when it has one of the statuses publish, draft, pending, future or private. Trashed and auto-draft navigation is refused and never listed. `list-menus` lists block navigation in those same five statuses, from the same list. Refusals use the same text as the other tools.
- A classic menu item's title and URL are the ones the public menu prints. Its linked object may be a draft, a private post or a type the post tools refuse; only its type, its ID, and that title and URL are returned.
- The read tools share one object check, which allows only a post that exists, is not trashed, has an allowed type and passes `read_post`. Custom CSS posts, privacy requests and private posts of a type registered with `map_meta_cap` off are refused, whether published or trashed.
- `get-rendered` blocks outbound HTTP requests, oEmbed fetches and oEmbed cache writes while it renders, so rendering a post does not contact other hosts or change its meta. It omits login/logout and navigation blocks whose output would reveal data the agent cannot read directly, and it suppresses user avatars wherever they are printed, so no Gravatar hash of an email address appears in the output.
- The post capability mapping never turns another component's `do_not_allow` into a grant, and it is off once WordPress is shutting down.
- The input rule for a tool runs only after the caller's Steadhand capability is checked, so a caller without `steadhand_read` learns nothing about the allowed post types.
- The agent lockdown is registered even when the MCP Adapter or the Abilities API is missing, and a later `rest_pre_dispatch` filter can no longer lift it.
- A user that holds the agent role and another role can no longer use its Application Passwords anywhere. Its cookie sign-in is unchanged.
- Agent credentials are refused everywhere except the Steadhand MCP endpoint: core REST routes, the batch endpoint, the abilities API, the MCP Adapter's default server, XML-RPC, `wp-login.php` and wp-admin. An agent's Application Password no longer works outside Steadhand, and an agent cannot sign in with its account password.
- Only a dedicated agent can connect: a user whose sole role is `steadhand_agent`. A user who also holds another role, such as an administrator given the agent role, is refused at the endpoint and in the pipeline, even if it holds the Steadhand capabilities.
